# 跨市场固定 180 题评价：性能诊断与保守优化

## 范围与结论

2026-09-27 用户要求“分析性能瓶颈，尝试优化”。本次只诊断已经启动的 `evaluation_01`，并给后续新启动的 worker 增加独立运行适配层。九个 step240 参数点、180 题、两次随机采样加一次 greedy、总计 4,860 会话以及全生成封存后的私有评分隔离均不变。没有新训练、没有 API 调用，也不读取未封存的私有评分或答案来选择优化对象。

证据支持以下判断：

1. 组成题的多回合长上下文生成是主要耗时来源。每个工具回合都重新渲染、分词并送入完整累计提示；`use_cache=True` 作用于一次 `model.generate` 内，并不是跨工具回合复用 KV。当前观测尚不能把 prefill、逐 token forward 和其他生成内部开销精确分离，不能声称某一个 CUDA kernel 已被定位为唯一瓶颈。
2. 随机 decoder 在一次生成后逐 token 转 Python float，存在可以消除的逐 token GPU→CPU 同步。只优化这一后处理，不改变采样过程和逐行 FP32 `log_softmax` 运算。
3. 共享 GPU 的容量波动已导致两次资源退出；引入会话边界的有限宽限等待，以减少短暂不足造成的退出重载。暂时不降低原 48 GiB 门槛。
4. 当前磁盘、会话间处理和 coordinator 开销较小，没有证据支持把它们当成首要瓶颈。持久化和预算审计不减配。

## 优化一：合并采样后 logprob 的回传

新文件 `cross_market_logprob_collection_20260927.py` 从冻结 decoder 创建私有子类，只替换唯一的 `logps` 赋值。通过原文件 SHA256、唯一 AST 匹配、反向恢复后完整 AST 相同进行约束。原文件、原类及模块 globals 均不修改。

原实现为每个 token 执行 `float(torch.log_softmax(score[0].float(), -1)[token])`。新实现保留相同形状、相同 FP32 和相同逐行运算，选出的零维标量先 `.clone()`，最后把小标量向量一次回传并转为 Python float 列表。克隆避免零维 view 把整行词表概率长期保留；不堆叠 token×vocab 的大矩阵。

改变位于模型采样完成之后：不改变 `model.generate` 参数、输入、随机数、beam／temperature、FlashAttention、精度或模型权重。Greedy 路径不需要这一 logprob 收集，不宣称它也因此提速。

CPU／mock 共 16 项定向测试通过，包含严格长度不符拒绝、空输入、逐 float 完全相等、RNG 不变、标量存储与一次 host transfer，以及完整 mock callback 的生成参数和 receipt 相等。

合成测试的 PyTorch peak allocated 为 74.83 MiB，peak reserved 为 86 MiB；这是该合成进程自启动的累计峰值，包含 scores 输入与新旧两种收集方法，不是 helper 的增量内存或两实现间的内存比较，也不含 CUDA context 的全部 NVML 驻留开销。共享 GPU 干扰明显，例如最后一组旧方法样本从约 10.7 ms 到 323.8 ms，不能把中位倍数直接解释成稳定内核加速，更不能称整轮快了同样倍数。测试证明的是这些有限负值输入上的逐值完全一致、无 RNG 消耗和后处理改善，不是所有 NaN／signed-zero 位模式的广义测试；没有进行新的 Student A/B 推理，也不声称完整生成轨迹已经逐条对比过。

原始微基准、所有七次时间值、脚本及 helper 哈希保存在 `evaluation_01/performance_benchmark_20260927.json`。其中 `anchor_decoder_sha256` 是 helper 声明的预期源哈希；登记时另外读取真实冻结源并通过工厂验证，不能只靠微基准中的常量证明原文件未变。运行登记必须绑定该文件，校验通过及 helper hash 一致才允许启用；缺省不自动开启未验证的 helper。

## 优化二：保持门槛，增加有限容量宽限

新运行适配器 `run_cross_market_performance_20260927.py` 保持启动门槛和会话边界门槛均为 49,152 MiB。首次加载前不足仍退出；已经加载的 worker 若在会话边界短暂不足，最多等待 120 秒、每 10 秒复查，容量恢复后继续。仍先执行原 `empty_cache`，不在会话中途强行迁移，不忽略真实 OOM，不返还预算，也不增加尝试上限。

目的只是减少短时资源波动造成的重载和 attempt 消耗。若不足持续超过宽限，照旧产生 `RESOURCE_RETRY`；该策略不保证解决持续资源争用，在资源长期不足时还可能额外等待两分钟。不能把“等待”报告成“GPU 正在计算”。

新增遥测记录 allocator peak allocated／reserved，不重置峰值；正常运行低频记录，容量不足及退出另行记录，避免逐 token 或每题额外写盘。原计量及完成数据不改。

适配器沿用现有 CUDA 恢复协议，只保留此前登记的 12 个 CuBLAS 首调用失败的精确恢复范围，不能把新的 FATAL 泛化成可重试。原科学协议及其 source binding 返回原值，不伪造修改 scheduling 后仍使用旧 ID 的协议对象。
