## 2. 既有 A 证据及其边界

用户审计对既有 A 阶段作出 `PASS_AS_SCOPED` 的范围内接受。可核验的既有结果见 [Delayed-C 三种子最终审计报告](fixed_kernel_delayed_C_audit_report_20260922.md)：Delayed-C 相对 Static 在固定开发题上的汇总净增为 **6/540，即 +1.1111 个百分点**；三个种子的净差分别为 **−1、−7、+14**。因此，既有证据支持选择 Delayed-C 作为固定候选继续确认，并不支持“跨种子一致提升”“稳定优于 Static”或“统计显著提升”。

这 540 条记录是同一 180 道开发题在三个训练种子下的评分，不能当作 540 道独立题。开发题参与了反馈元优化，并有既有开发分析曝光；旧 A 汇总不是未参与学习的独立测试。原 Full 的负结果仍然保留，Delayed-C 的开发方向也不能改写为 Full 或 Novelty 成功。

本轮直接冻结候选，不再要求每个种子都正向，不用 B 最终开发集成绩进行二次筛选。A 的 +1.1111 个百分点不是 B 的预期实测值；B 可能为正、接近零或为负，本文不对方向作保证。

## 4. 每个种子的真实共享前缀与两条尾段

每个种子从配对初始化和空 Adam 开始，在 B 的 π₀ 上实际训练 200 步，仅执行一次。该前缀的完整保存状态包括真实 LoRA 参数、Adam 一阶与二阶矩、每参数 step、优化器配置、Python RNG、NumPy RNG、Torch CPU RNG、CUDA RNG 和训练日程游标。两条尾段从同一个已经落盘的 step200 状态恢复。

```text
B 配对初始化、空 Adam、固定 π₀
                │
       实际执行共同前缀 200 步
       保存参数 + Adam + 全部 RNG + 游标
                │
        ┌───────┴─────────────────────┐
        │                             │
     Static                        Delayed-C
 保持 B 的 π₀                在该 step200 点计算一次 G
        │                    虚拟 Adam 点 → 360 随机反馈
        │                    封存 → 独立评分 → 一次 C-only
        │                    通过新点数值门后恢复真实前缀状态
        │                             │
  实际尾段 200 步                实际尾段 200 步
        │                             │
 唯一 step400 模型               唯一 step400 模型
        └──────────────┬──────────────┘
              固定 720 题确认
```

这里的配对来自同一完整 checkpoint，而不只是“相同 seed”或“相同训练策略”。两尾段的来源绑定包含同一前缀 checkpoint SHA 和 optimizer snapshot ID；任何恢复都必须匹配这些身份。Delayed-C 的虚拟点仅用于反馈与贡献计算，不作为尾段 SFT 的起点。外层通过原 Adam 绑定校验确认没有污染真实参数或优化器，恢复全部前缀 RNG，并检查 Torch CPU/CUDA RNG 一致；尾段 worker 随后再次从真实前缀恢复。

训练日程、基座/分词器、LoRA、优化器配置、裁剪、精度和原执行核均沿用冻结绑定。每个最终模型具有有效 400 步训练历史。由于三个前缀物理共享，有效更新总数为 `6×400=2,400`，无中断时的物理更新基数为 `3×200+6×200=1,800`。不把共享的 600 次前缀更新重复计为六次独立执行，也不把资源失败的局部尝试藏在有效更新数内。

具体恢复及尾段分布准入见 [fixed_kernel_B_training_worker_20260922.py](../scripts/fixed_kernel_B_training_worker_20260922.py) 和 [fixed_kernel_B_common_20260922.py](../scripts/fixed_kernel_B_common_20260922.py)。

## 5. Delayed-C 的唯一外层更新

外层实现见 [fixed_kernel_B_outer_worker_20260922.py](../scripts/fixed_kernel_B_outer_worker_20260922.py)。每个种子只有一次 step200 外层更新，分为可恢复的 `prepare` 与 `replay` 两个阶段；反馈生成和独立评分在两阶段之间完成。

`prepare` 在真实 step200 参数及 Adam 状态上，对 B 的 **全部 3,529 包、1,645 状态**计算类梯度。设 `g_xz` 为当前 LoRA 坐标中的原包类内平均 NLL 梯度，`U` 为包含实际 Adam 历史与裁剪规则的虚拟更新量，则：

\[
G=\sum_x\mu(x)\sum_z\pi_0(z\mid x)g_{xz},
\qquad \bar\theta=\theta-U(G).
\]

完整 CPU FP32 类梯度矩阵、G 及其材料/前缀绑定以 `population.pt` 原子提交。只有完整提交后的文件可被恢复复用；若已经完整存在，后续尝试不重复计算这一 population pass。`full_G.json` 保留实际 G 摘要、完整 optimizer snapshot、虚拟步诊断和前缀身份，`virtual_point` 保存适配器及参数点记录，`prepare_report.json` 完成准备阶段封口。

反馈仅使用固定 dev180：每题两次随机轨迹，每种子 360 条，三个种子共 1,080 条。它只服务于 Delayed-C 的 step200 反馈；Static 不消费反馈更新，本轮也不增加 B 的 step400 dev180 评测。每个种子的全部 360 条反馈须完整封存后，才交给独立 CPU 评分进程。

反馈梯度保持原 score-function 定义：

\[
\widehat g_J=\frac{1}{360}\sum_{i=1}^{360}Q_i
\nabla_{\bar\theta}\log P_{\bar\theta}(\tau_i),\qquad
a=DU(G)^\top(-\widehat g_J),
\]

\[
C(x,z)=\mu(x)\left\langle a,
g_{xz}-\sum_{z'}\pi_0(z'\mid x)g_{xz'}\right\rangle.
\]

仅对 `Q=1` 的轨迹回放梯度；`Q=0` 项仍占据固定 360 分母。正奖励轨迹包含全部实际采样响应及其错误、恢复和 EOS token，不按轨迹长度归一化，也不以 SFT 正样本 mask 替代。逐响应回放使用原 `segmented_logp`、block size 8、FLASH 后端；按原轨迹/响应顺序在 GPU FP32 中执行 `sum.add_(gradient, alpha=1/360)`。

每完成一个响应，原子保存累计和的 CPU 镜像、游标、token 会计、累计摘要与固定反馈身份。恢复只读取已有封存反馈，从最后一个提交点继续，不能重新生成反馈以改变奖励。实际所需回放响应数 R 由封存的正奖励响应清单确定，须先登记再回放。无正奖励时得到经验零 gJ，并沿用原“无信息、π 不变”的处理；不能据此声称理论贡献恒为零。

C-only 沿用原贡献指数 0.8、Novelty 指数 0、current/prior 双 KL 系数 4/1，贡献尺度采用非控制任务 `C/μ` 的 μ·π 加权 RMS，floor 为 `1e-8`，逐任务温度为任务权重乘以该全局尺度。控制任务保持原先验，不参与非控制贡献温度和势优化。不得增加概率 clipping、按结果重缩放 C 或替换已冻结 Adam 表达式。

原始 `C.json`、`pullback.json`、`gJ.json`、`distribution_update.json` 和 `numeric_guard.json` 均保存。`C_scale.json` 另保存原始 RMS（字段 R）、T_C、floor 及完整温度记录；这里的尺度 R 与“回放所需响应数 R”含义不同，读取时必须依字段所在工件区分。

新 step200 点继续使用原数值门：非控制 `C/μ` 相对加权 RMS 误差不超过 `1e-3`，参考与实际更新分布的加权 TV 不超过 `1e-5`。稳定参考只用于核对，不能替换实际公式。门失败时不发布外层成功报告、不放行 Delayed-C 尾段，也不自动尝试另一数学实现。

RMS 是映射与数值比较的尺度，不是置信度或方向可靠性的估计。数值门通过也不证明该代理预测最终 greedy 或多步效用。仅从已有评分追加正反馈任务数、CIK 数、各任务/CIK 正项计数及最大份额等集中度；不追加梯度来计算跨重复方向检验。**新点 cross-repeat reliability 明确标记 `NOT_MEASURED`**，不能把旧 A 点的代理审计结果转移到 B 新点。

## 7. 主效应与 CIK 配对区间

统计实现为 [fixed_kernel_B_confirmation_statistics_20260922.py](../scripts/fixed_kernel_B_confirmation_statistics_20260922.py)。输入必须是完整 720 题注册表，以及两臂、三个固定种子对应的全部 4,320 个二值 Q；缺失、重复、未知 task/seed/arm、非二值奖励或配额不符均不进入正常分析。

对任务 i 先计算三个种子的配对均值：

\[
d_i=\frac13\sum_{s\in\{11,29,47\}}
\left(Q_{i,s,Delayed-C}-Q_{i,s,Static}\right).
\]

主效应先在每组的 240 题内平均，再对三组等权平均：

\[
\widehat\Delta=\frac13\sum_{g=1}^{3}\frac1{240}\sum_{i\in g}d_i.
\]

720 是固定任务数，4,320 是评分记录数。种子数、模型数和共享任务重复评分均不扩增为独立题量。效应可换算为百分点展示，但计算及判据使用原比例单位。

CIK bootstrap 规则在查看确认结果前固定如下：

1. 将 71 个唯一 CIK 标准化为十位数字并按字典序排列。随机发生器为 Python `random.Random`，种子 **20260922**。
2. 每次从这 71 个 CIK 中有放回抽取 71 次，得到各簇重复次数。一次抽样的同一组簇权重同时应用于两臂、全部训练种子和三个任务组。
3. 每组使用本次抽样中实际加权任务数作为分母，而不是对公司均值等权，也不是沿用未经加权的 240 分母。
4. 若某次抽样使任意组为空，丢弃整个抽样并记录原因；不能删去空组后重新归一化。是否接受抽样只取决于组是否为空，与效应大小、正负或显著性无关。
5. 目标为 **20,000 个有效抽样**，最多尝试 **200,000 次总抽样**。达到总上限但有效次数不足时，输出 `INCOMPLETE`，不输出正向确认结论；不追加抽样预算。
6. 使用 95% percentile 区间，端点分位数精确为 `1/40` 和 `39/40`，按 `(n−1)p` 做线性插值。簇内充分统计量先用整数累加，任务/种子/组均值和分位数插值采用 `Fraction` 精确有理数。浮点数仅供展示，严格正下界判据使用精确端点。

唯一正向确认规则是：区间计算完整且 **精确下界严格大于 0**。区间包含零（包括端点恰为零）表示本次未确认正向效应，不能解释为等效、无效或已经证明无差异。不得据此追加任务、种子、替换方向或调整推断规则。

该区间描述在固定训练总体、固定 B 材料核和这三个已经训练的 checkpoint 条件下的来源簇重采样变化；不覆盖所有可能的训练随机性。剔除空组后的 bootstrap 分布还条件于三个组均保留，报告须保留该条件与实际弃样数。

## 8. 预算：有效工作、物理基数与硬上限

本轮计划的有效工作为六模型各 400 步、三个 Delayed-C 外层各 360 条反馈、六模型各 720 条确认。无故障时新会话共 **5,400** 条，其中反馈 1,080、确认 4,320。固定每会话32响应上限对应已提交会话最多 **172,800** 次模型生成调用；这不是预计实际调用数。

| 物理执行项目 | 硬上限 | 计数含义 |
| --- | ---: | --- |
| optimizer 尝试 | 1,980 | 无中断基数1,800；执行前记账，局部失败尝试也占预算 |
| full population pass | 6 | 必需完整pass为3；完整`population.pt`可复用 |
| 反馈响应回放尝试 | 34,944 | 全局上限；同时受每seed实际R+128约束 |
| 每seed额外反馈响应尝试 | 128 | 在该seed已封存的实际R之外计费，不能生成新反馈 |
| 模型生成调用尝试 | 190,080 | 原会话上限172,800加失败恢复余量17,280 |
| 未提交生成调用差额 | 17,280 | 已记账调用数减去已提交会话调用数，不是新增任务额度 |
| CPU 评分 case 尝试 | 6,480 | 完整5,400 case之外允许有限资源恢复，已提交case不重评 |
| worker 启动 | 512 | 所有工作单元合计 |
| 每工作单元启动 | 8 | 达到上限即停止该单元的自动恢复 |

反馈响应全局上限 `34,944 = 3×(360×32+128)` 是最坏结构上限；正常预算仍由每种子实际正奖励响应数 R 控制。两种门须同时满足，不能以全局还有额度为理由突破某个种子的 `R+128`。

原包长度给出的无故障物理 SFT 基数为 801,526,230 序列 token、44,193,960 监督 token；六模型有效训练历史合计为 1,068,701,640 序列 token、58,925,280 监督 token。三个必要全类 pass 另有 53,435,082 序列 token。以上数值不包括生成、反馈梯度回放和失败中的额外局部计算；不能当作最终实际总算力、GPU-hours 或能耗。

预算账本在执行前进行 reservation；若 reservation 和后续落盘之间中断，允许保守多计，不回退为未发生。已经原子提交的训练步、生成会话、回放响应和评分 case 有各自身份与游标，恢复只补缺失工作。所有实际物理尝试与有效工作应分开汇总。

## 9. 资源准入、自动恢复与停止条件

调度及守护实现见 [run_fixed_kernel_B_confirmation_20260922.py](../scripts/run_fixed_kernel_B_confirmation_20260922.py)。GPU 租约只协调本实验进程，不承诺整机独占，也不驱逐其他任务。

“自身容量”定义为当前 CUDA 空闲显存加本进程 PyTorch 已保留显存，避免将本进程缓存误判为外部占用。运行中的检查位于已保存边界；容量不足时等待有限次数后让位，随后依调度预算恢复。被识别的资源失败可提高该工作单元后续门槛，每次增加4 GiB、最高76 GiB，并采用有限退避。原 A 的个别 32 GiB 最终生成续跑成功不能推导为本轮全部长上下文生成均已在32 GiB准入，因此本轮不全局采用该门槛。

最多并行八个 GPU worker，population 与 replay 各最多一个；CPU 评分不占 GPU，每评分 cohort 最多十二个并发 case。启动前的主机可用内存门槛为 SFT/生成64 GiB、外层128 GiB。实际并发数受 GPU容量、主机内存、任务依赖和预算共同限制，不预先承诺八卡持续满载。

自动恢复只面向容量让位、GPU OOM、主机内存不足、评分子进程资源中断等已识别的执行问题；无结果记录的异常进程消失按未完成尝试处理并保留证据，不当作数值通过。数值门失败、源码/材料/身份不匹配、评分协议错误和硬预算耗尽均停止对应流程，等待审查；不能自动更换公式、修补答案、减少分母或扩大预算。

本轮使用独立 watchdog/coordinator 和持久化进程身份、租约、状态账本实现进程级恢复。没有安装机器启动服务，**不保证服务器重启后自动拉起**。磁盘上完整提交的保存点可供后续验证恢复，但这不等于对机器重启、磁盘损坏或全部外部进程行为作可用性承诺。
