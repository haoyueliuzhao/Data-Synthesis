# V10 同一审阅矩阵的局部代理恢复

## 原因、证据与授权边界

9月30日凌晨原生产客户端采用应用层直连：HTTPX client/transport均关闭环境代理自动继承，TLS校验开启，传输自动重试为0。连续两次系统DNS查询 `api.deepseek.com` 返回 EAI_AGAIN；当次恢复没有新增正常返回，却新增16项网络UNKNOWN。因此停止派发并等原进程退出，没有释放UNKNOWN预留。不能由这两次诊断追溯断言此前每个ConnectError都是DNS所致。

用户随后明确回复“授权现有代理验证并恢复”，授权仅本批DeepSeek改用现有代理：先不带密钥、无计费验证，通过后按原矩阵恢复，不改全局网络、模型、预算或审阅规则。

本轮只发出一次无Authorization的HEAD到 `https://api.deepseek.com`，显式使用既有 `http://127.0.0.1:7897`。HTTP/1.1 401，耗时0.374秒，默认证书校验通过，没有模型调用。401是未带认证请求的正常响应，证明当时代理TCP/TLS/HTTP可达，既不验证生产密钥，也不保证持续并发稳定。记录保存这次观察结果与登记时间，不伪造未留存的探测精确时刻。

## 实现与保留项

仅生产审阅、既授权网络attempt2和任务映射使用独立的显式代理参数。仍保持client/transport `trust_env=False`、`verify=True` 和 `retries=0`；不启用全局环境代理自动继承，不改DNS/Clash/SSH转发，不配置其他端口，不在失败时自动回退直连。环境中指定HTTPS_PROXY的实际字符串必须匹配事前记录的SHA256，错误或缺失即停止。

代理配置只适用于 `finqa-v10-20260929-new8000-01` 与同一protocol_id。生成已完成，不重采。源版本迁移只允许 `v10_generation.py` 的精确版本选择、`v10_production.py` 的客户端接线和 `v10_review_provider.py` 的显式代理工厂；新传输/迁移模块逐文件登记hash。旧父修订 `466d07ee54b3b57e10fc72a1b479802a14afc703b4bd87f696485e94c0b2af26`、所有历史源码、账本、原始审阅、UNKNOWN、预留和授权记录均保留，不修改通用完整性验证规则。

模型始终为deepseek-flash，HTTP endpoint、请求字节、提示词、输出上限、并发16、评分/资格/监督规则、钱包总上限2000元、审阅映射子额1300元及请求数上限不变。原11438侧的分母不变。主矩阵全部终态后，按既有授权对本批全部网络UNKNOWN各唯一attempt2；旧失败与全额预留保留，没有attempt3、择优返回或旧批混入。达到原网络保护阈值仍保存停止。
