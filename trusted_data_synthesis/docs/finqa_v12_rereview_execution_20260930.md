## 2. 为什么需要重新登记，而不是修补旧返回

前一轮全量审计发现，A 侧 5719 次审阅中，5246 次以 `finish_reason=length` 达到输出上限，约占 91.73%。这是本批 A 侧主要损失，不能仅用“辅助坐标错误抹掉过程判断”解释。旧 A 侧低容量档实际分布为：2048 档 5193 次，其中 5115 次 length；4096 档 525 次，其中 131 次 length；8192 档 1 次，无 length。正常结束中仍存在额外 JSON、重复键、结构和证据绑定问题，因此提高容量也不是语义正确性的保证。

V11 的分层合同可避免已经可读且关键证据可绑定的过程结论被辅助投影失败一起抹除，但不能恢复已截断或损坏的 JSON。V12 同时处理输出重复、定位表示和容量规划；**不补全旧 JSON、不猜缺失引号或括号、不重写旧 valid/invalid/unknown，也不把 V11 离线检查冒充真实新审阅。**

本轮新增结果与全部旧结果分开保存。旧返回、旧 UNKNOWN、旧预留、旧统计和失败证据全部保留。既有 V10/V11 记录的含义不因新代码发生追溯变化。

## 4. 新 wire 表示与四层结果

新请求保留原问题、公共来源、全部实际公开正文、原工具参数、真实观察及历史顺序。主机提供稳定短 unit ID、真实 action/event 关联；每段原文在模型载荷中保留一次，不通过反复复制正文、坐标和 quote 增大输出义务。物理单元覆盖原始字符，动作参数保持完整原串；不删错误历史、不截断原文、不按旧结果改写解释。

模型可引用整个 ID，必要时提供部分 quote。部分 quote 只有在原段中连续、逐字且唯一匹配时才可绑定；不做金额模糊匹配、大小写归一化、删限定词或猜位置。唯一匹配仅证明位置可机械还原，**不证明引用没有遗漏语义限定条件**。完整上下文仍保留供审阅。

A 判断四项关键过程维度并给出自己的监督选择；B 只判断关键过程维度，不产生第二套 mask，也不要求 A/B mask 求交。未批准的公开内容默认不进入正向监督，不强制模型枚举所有 `context_only` 坐标。A 批准某个实际 action 不能扩大成整条 assistant 消息均获批准。

结果分层记录如下：

1. 原始模型返回、原始声明及解析状态；声明不等同于财务真值。
2. 关键证据是否可绑定，以及合同校验后的过程结果。关键证据缺失或定位不明仍为 unknown；有据的关键错误仍为 invalid。
3. A 的监督投影是否可用。投影失败不抹除可独立读取的过程声明和核心绑定结果；不可用投影的正向字符统计记为未知，不伪装成实际零 mask。
4. 新流水线候选状态和后续准入边界。可读的 length 返回也保留，但其新流水线过程候选不可用，不因 JSON 恰好完整而放行。

外层 `v12_paid_process_review.v1` 只有在原钱包确有实际模型返回且 usage、原始字节和请求身份一致时，才设置 `actual_model_call_receipt_verified=True`。内层 V11 inspection 的离线来源标记与 `production_admitted=False` 保持原样。wire 到合同表示的机械展开单独标识，不伪装成第二份模型响应，也不补充语义判断。

配对统计还区分内层 `offline_A_reason_projection` 与新流水线有效 `A_reason_projection`：即使机械展开后的内层合同计算出字符数，只要外层原 wire 的监督无效，有效正向字符数和 `all_masked` 就必须为 `None`。不能将内层统计当作真实可用监督量；这一统计修正不改变原请求、原模型返回或已完成的离线准备。

全部新 A/B 终态齐全后，才生成本轮配对结果。共同过程候选中的 A 投影失败包必须保留并列为阻塞项，不能只取投影成功子集冒充完整共同核。单包 reason0 不新增淘汰规则；只有整个必需共同池所有公开 reason 均被投影为零时，才报告原有全池表示阻塞。过程候选、可表示投影与真实可训练材料不是同一个结论；状态/χ、编码和训练准入仍未在本轮执行。

付费前的独立接口审查发现一项实质缺陷：A 整个 `supervision` 缺失时，第一版 V12 把它列为 envelope 失败，从而仍会污染可独立判断的过程层。正式版已修正为：非 JSON object 才列为 envelope；缺失 `process` 属于过程错误；缺失或损坏监督属于 projection；多余顶层字段单列 auxiliary，不自动改变关键过程结论。新增 3 项反例控制通过。此修复发生在钱包登记和真实调用前，不是对已付费返回事后放宽。

## 5. 输出容量如何确定

新容量模块为 `v12_review_capacity.py`，允许档位为 8192、16384、32768、65536。它不根据旧模型成绩选档，而根据当前题实际保留的单元、正文和动作结构构建一个只在主机侧使用的序列化输出规划场景：

- 四项过程检查均计入完整单元 ID 列表的规划空间，各预留 1024 UTF-8 字节 summary；这些是假设性规划占位，不是要求模型必须输出这些引用或字符。
- 为四项检查加入按 JSON 转义字节长度排序的最长四个原始单元的部分引用场景。
- A 侧另计所有公开正文单元的正向 ID、实际动作 ID，以及全部正文部分引用的规划场景；B 不承担 A 的监督字段。
- 对场景实际 JSON UTF-8 序列化字节加 1024 字节工具信封余量，再乘 5/4，向上选容量档。
- 若规划值超过 65536，离线准备失败；不直接压到上限、不裁原文、不漏包，也不发起该付费请求。

这是一项可复现的前瞻容量规则，**不是 DeepSeek tokenizer 的精确计数、不是输出长度数学保证，也不是语义可靠率预测**。summary 和引用预留未转化为新的 `maxLength`／`maxItems` 语义限制。模型实际输出仍可能冗长、截断或格式错误，这些结果需要原样保留。

最终完整 HTTP 输入还检查“输入 UTF-8 字节数 + 输出 Token 上限”小于已登记的 1048576 边界。这是实现中的保守混合单位保护条件，不应报告为实测模型输入 Token 数。

## 9. 故障与恢复：终态不等于实际返回

- `SETTLED`：只从原请求、响应、usage、坐标和证据精确恢复，不新增 HTTP、不重复结算；原标注字符串损坏也不修补。
- `RESERVED` 且确认未派发：允许在相同坐标、同原请求字节下继续原 reservation，不新增计数或 attempt。
- `DISPATCHED` 未解决：不能推定请求没发出，不能直接重发；保存待排查。
- 确属本 V12、无 HTTP 状态、无响应体、无 usage 且异常属于登记连接白名单的 `UNKNOWN`：先停止新增并等待 pending0，再对精确 invocation/request-hash 集合追加网络终态确认。原 UNKNOWN 行与全额预留永久保留；没有响应就没有模型结论，也不能构造假 inspection。
- 仅清除确由该组网络异常导致且被完整覆盖的 halt。HTTP 429、其他服务响应或 usage/模型合同问题不因“看起来像网络问题”被自动确认或解除。
- 同波达到 3 项连接 UNKNOWN，控制器保存停止，不自动重启。账本仍可记录真实 UNKNOWN 终态并清精确网络 halt；控制器安全退出与财务终态是两件事。

所有新调用仅一次 attempt1，没有自动重审、第二 attempt、模型回退或择优取旧结果。本轮不沿用旧 V10 网络补发授权。

进度必须分别报告已处理终态、实际模型返回、无模型返回的网络 UNKNOWN、未发送/未解决数。11438 项全部新矩阵终态齐全后才封存；不得用有效子集或成功前缀宣布完成。模型实际返回完整也只表示本轮审阅执行完成，不等于已经形成可训练共同核。

## 10. 实现与必要验证

主要模块分工：

- `v12_review_capacity.py`：按当前原文与结构规划输出档位。
- `v12_review_protocol.py`：短 ID wire、全部原文载荷、独立 A/B 合同和明确的机械展开。
- `v12_review_registration.py`：全部请求离线准备、不可变新计划、源码及代理绑定。
- `v12_budget.py`：追加请求调拨、新名单、精确未派发恢复及网络终态。
- `v12_review_provider.py`：原请求字节派发、实际 usage 结算、精确原件回放与外层付费凭据。
- `v12_review_controller.py`：固定矩阵调度、按结算升档、预算等待、故障保存、完整终态封存；终点止于审阅报告。
