# FinQA固定四卡运行范围

2026年10月8日，用户要求“约束任务只在这四张卡上运行”。当时实际占用的是物理GPU3、4、5、7，本次将它们设为固定白名单，覆盖此前六卡上限及让出卡空闲时可重用的执行策略。GPU0、1、2、6即使空闲，也不再承接本轮训练、恢复或评价任务。

## 固定白名单与接续方式

补充执行策略位于原V29队列下的 `four_gpu_release_01/gpu_scope_01/`，固定允许卡号及UUID，最多同时4个worker，CPU初始化中的已派发进程也计入。候选显卡查询只向调度器提供这四张卡，实际派发前再次拒绝白名单外卡号或第五个worker；恢复已有进程时也核对资源范围。

原V29队列、job attempt、完成结果和科学协议继续使用，不复制整轮任务，也不回写原历史资源登记。新控制器校验冻结V29实现，并对本次运行施加更严格的白名单；普通新任务、行政断点续跑和通过证明的OOM恢复均经过同一派发检查。

控制器交接只替换调度进程，保留上表四个worker。交接前核验PID/birth、原命令、控制器等待边界及子进程集合，保存当时状态的独立快照。新策略在原实时状态中明确写出实际 `allowed_gpu_indices=[3,4,5,7]`、`max_gpu_workers=4` 及补充策略引用，避免把历史六卡策略误认为当前限制。

原24项工作、训练预算、模型、seed、反馈与test分母、统计方法不变。空卡高缓存、共享资源门槛、完整断点及禁止重采样的规则保留，但仅在白名单内运行。没有外部API调用。之前按当前四卡给出的完成时间估计仍可作为条件估计；额外获得两张卡的加速情景不再适用。

## 验证与部署

补充策略21项CPU测试及V29控制器24项回归测试全部通过，共45项，用时0.41秒；新增脚本与测试Ruff通过。覆盖白名单过滤、拒绝其他卡和第五个worker、现有进程接管、有效状态字段及控制器交接身份。没有为验证重新加载GPU模型。

本次先停止旧控制器的新派发，再提交并冻结新实现后接管。实际接管结果将在执行后补入；原四项训练仍在运行。

实时进度路径不变：`four_gpu_release_01/queue/status.json`；补充策略及其启动记录单独位于 `gpu_scope_01/`。实验只有在原所有任务及评分完成后才算完成，限制显卡范围不等于实验结束。
