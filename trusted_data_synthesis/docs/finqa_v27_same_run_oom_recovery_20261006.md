后续状态：10月7日seed137 C-only已完成首次outer，实际跨过本次OOM位置；但seed251 C-only在GPU5遇到另一次共卡OOM。用户授权的新[V28双模式显存与断点恢复](finqa_v28_high_memory_recovery_20261007.md)已接管，当前进度改读 `resource_recovery_02/queue/status.json`。本篇运行状态和V27路径保留为当时记录。

## 失败事实

失败分支于18:04:14在物理GPU7启动，18:27:52写出失败审计，18:28:05被控制器记录退出。错误栈位于 `class_gradients` 的 `torch.autograd.grad`，属于真实计算失败，不是此前的启动前显存准入拒绝。

OOM记录显示，本进程当时占用约54.19 GiB，同卡另一进程占用约24.99 GiB，空闲仅61.38 MiB，下一次分配需要104 MiB。另一个进程属于同账户的ProWorkSim项目，18:05:02启动。本次不停止、移动或调整该项目。

V26正确拒绝将此次失败当作“零计算拒绝”自动重排，并停止派发新任务。20:03检查时，原C-only seed47测试、seed137 Static和Full三个worker仍在运行，三个新seed的共同前缀均已完成。本次恢复不能以重启整轮代替接续这些状态。

## 为什么可以从原检查点恢复

恢复前核对范围限于这一次seed137 C-only失败，不将结论推广为任意OOM均可自动恢复。

| 恢复依据 | 恢复前已验证状态 |
| --- | --- |
| 最后持久点 | 原分支 `step0298_branch` |
| 已完成optimizer更新 | 298，与原共享前缀一致 |
| 已提交outer | 0，`outer_done=[]` |
| 失败阶段 | `capture_pre_outer_state` 后的 `full_class_gradients` |
| 后续阶段 | 尚未进入virtual Adam、反馈生成、logP回放或outer提交 |
| 已有反馈 | 无feedback目录、样本、调用intent或receipt |
| 恢复状态 | 模型参数及buffer、Adam、Python/Torch/CUDA随机状态、pi/prior、步数、材料与批次顺序绑定齐全 |
| 原失败进程 | 已退出；不与旧进程并行恢复同一分支 |

对原分支和共享检查点的CPU状态比较显示，唯一差异是分支标签由shared变为C-only。112个LoRA参数及112份Adam状态一致，Adam步数全部为298，pi与prior一致。分支Tensor文件SHA256为 `f16ef5cc4b9739713e2b66c1330e4ea8ab8f506b65761c0e52f49f4708fbf24f`；恢复证据绑定该实际文件及对应审计，而不是仅检查文件名。

原冻结worker已经支持 `train --seed 137 --arm c_only --resume`。其恢复逻辑检查材料、模型、适配器和计划身份，然后完整装入已提交状态；`run_until` 会在离开step298之前重新执行尚未提交的outer。发生OOM的临时梯度不被接受为完整梯度，也不会跳过该outer。

因此，本次会**重新计算未提交的梯度**，不能称为“没有计算重试”。但没有任何已生成反馈被丢弃或重采样，没有换seed、换模型、增加样本或改变最终更新数。原失败attempt和日志永久保留，新attempt记录显式断点恢复。

## 控制器交接

新的执行目录为原V25下的 `same_run_recovery_01/`。原V25和V26的协议、源码、attempt与退出记录保持原样，原科学worker继续使用原冻结版本。

旧控制器遇失败后只收尾，不会继续派发；简单发SIGTERM会让它等待长时间运行的worker全部结束。本次使用受限的控制器交接：先验证旧PID、进程birth、命令、失败状态和子进程集合，在循环等待边界暂停并核对一致快照，随后只终止旧控制器PID、释放调度锁。不向任何GPU worker或其他项目进程发送信号，也不按进程组终止。

交接前验证失败则恢复旧控制器运行；进入已终止阶段后若新控制器不能启动，已分离会话的GPU worker仍独立运行，交接证据用于继续接管，不能重新创建相同worker。

新控制器同时取得V25、V26和新队列的控制器锁。对运行中的worker只登记接管记录，沿用原PID/birth、命令和科学输出路径，不再次创建进程。接管后的退出观察写在新执行目录，不回写旧attempt。若交接期间worker已正常完成，则接受同运行的完整完成记录。

## 更保守的资源准入

原科学协议的最低门槛和worker代码不变。新执行层对尚未启动的C-only/Full自动分支，包括本次恢复，追加75 GiB空闲显存门槛；test、共同前缀和Static分别保留24、32和48 GiB。仍要求连续资源观察、派发前复查、每张卡最多一个本轮worker。

提高门槛的依据是已观察到的实际峰值，而不是效果或测试成绩：本次C-only在OOM前已使用约54.19 GiB，运行中的Full在反馈生成阶段也曾占用约68.35 GiB。原48 GiB准入不能保证与另一个25 GiB任务共卡安全。本次不据此改变模型、精度、batch、目标序列或科学预算。

20:05时GPU3仅运行即将结束的原C-only seed47测试；其退出后若没有其他新任务，预计可恢复约79.25 GiB空闲，足以承接新门槛。GPU7仍被其他项目使用，不满足追加门槛，队列等待合适设备，不抢占其他作业。

75 GiB是保守的执行条件，不是峰值上界证明，也不能阻止其他项目在本轮启动后使用同一设备。若再次发生真实计算失败，新队列仍停止新派发并保留状态，不无条件循环重算outer或重采样反馈。
