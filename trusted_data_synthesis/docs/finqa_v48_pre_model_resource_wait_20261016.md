# FinQA 模型加载前资源等待与恢复修订

本次修订处理共享GPU的显存竞争在模型加载前误停整个任务池的问题。用户于2026年10月16日明确要求修复，并指出自动恢复应覆盖此类问题，或不应由此阻塞任务池派发。新运行独立登记于 `production_resume_01/resource_deferral_recovery_01/`；旧V47停止记录、冻结源码和已提交训练保持原样。

本次不增加实验剂量，不重启旧监督器。模型加载前的可观测显存不足转为同进程资源等待；正常worker及其他GPU派发继续。模型开始加载后的资源失败仍走真实断点恢复，状态绑定、数值、未知未返回反馈及非法运行配置错误不能被当作资源等待放行。

## 修订后的资源合同

### 模型加载前等待

预留与CPU状态载入期间发生的真实显存不足必须附带实际观测和阶段身份，不再仅留下通用异常字符串。资源不足时保留同一进程和GPU项目租约，按固定轮询间隔等待；每次观察继续核验设备身份、allocated历史峰值、主存和停止请求。等待过程不能加载模型、执行forward、调用反馈provider或提交训练。

等待记录和科学阶段成功记录分开。等待时观测到free不足2GiB不会被改写成通过，只有重新达到规定资源门后才能进入模型加载。模型开始加载后不得使用这一等待路径回滚或重试科学操作。合法停止仍须生效，明确停止监督器后不得自动拉起。

同进程等待仍占该GPU的本项目名额，不宣称等待卡还能同时运行另一个本实验worker。控制器不阻塞等待该进程，而是继续观察其心跳、其他worker和其余GPU；这消除了由该类预加载资源不足触发全池停止的路径，不保证共享GPU一定很快释放资源。

新增等待只处理有实测依据的GPU容量不足：物理free不足、CUDA初始化后的容量竞争，以及本进程预留warm或anchor分配处的实际CUDA OOM。OOM后只清理尚未完成的预留，等待可用容量实际增加至少1GiB才再次尝试预留；不重置历史峰值，也不重做科学操作。主存或RSS硬门违约、读数缺失、设备身份变化和预留结构错误仍失败关闭，不在本次新增等待的放行范围内。

### 保持不变的限制

GPU0至7均可选择，不设独立总worker上限，每卡最多一个本实验worker；初始化和draining继续持有租约。沿用V47分阶段共享准入与同进程native allocator预留，GPU6本就处于授权范围。不得干预其他项目进程或改变设备独占模式。

allocated生命周期峰值仍不超过76GiB，预留warm allocation和模型加载均计入，不能为了等待或重试重置峰值。科学边界physical free至少2GiB；分片RSS限160GiB，其余阶段192GiB，全机有效可用RAM至少96GiB。V45经验主存启动预算、原数学81文件和R3后端绑定保持不变。

不新增资源、阶段或outer截止时间，累计历史用时继续继承。未知反馈、参数点绑定、数学比较和不支持的allocator配置错误仍停止，不能用“自动恢复”吞掉程序错误。正式新目录仅从原真实保存点接续，不裸用旧 `--resume`、旧handoff或旧migrate。
