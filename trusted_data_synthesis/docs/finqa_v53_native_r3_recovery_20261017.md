# FinQA V53 原生显存分配修订与断点恢复

用户于2026年10月17日明确要求“尽快恢复任务，同时修复此问题”。本次针对V52中R3大块显存预留与原始物理空闲检查之间的冲突，取消R3的暖分配及锚定预留，恢复原生按需分配。原回放数学、700分母、反馈及奖励、参数点、KV与非KV保存预算，以及显存和主存硬门均不改变。新运行独立登记在 `production_resume_01/r3_native_recovery_01/`，不修改父V52的冻结实现或失败记录。

恢复以实际保存的response128累计梯度为准。父进程虽计算到137，但129至137没有保存为累计梯度断点，因此需要按原序重新计算这9条；不能把本次接续描述为完全没有重复forward，也不能从137的实时游标直接继续。

## 停止原因与已保存进度

2026年10月17日20:12:34北京时间，父V52在GPU4执行下一条R3响应之前触发 `R3CapacityError`。该条响应尚未执行forward，先前本进程已成功执行16条，从继承的121推进至137。最近实际保存的梯度为response128，记录ID为 `94dbec3c99469a1f1fc172789f8f692e47f166b1848d8be2ca7324414fb07068`。

当时实际分配显存为28.492GiB，allocator保留显存61.066GiB，其中32.574GiB属于进程内部可复用缓存；物理空闲仅2.415GiB。R3所需的物理空闲为4GiB加本条KV估计，共4.272GiB，因此原始物理空闲条件未通过。另一方面，物理空闲加可复用缓存为34.989GiB，高于20.272GiB的总可用预算要求，生命周期allocated峰值61GiB也低于76GiB上限。此次是计算前的资源保护拒绝，不是实际CUDA OOM，也不是数值不一致。

大块暖分配使用同一native segment中的小锚点保持整块预留；即使调用原始 `empty_cache()`，仍有活跃分配的segment也不能完整归还。因而内部缓存充足并不等于物理空闲充足。本次修订消除R3启动时人为建立的巨大锚定segment，不伪造物理显存观测，也不以缓存容量替代原始物理空闲条件。共享卡上的其他负载仍可能使未来资源条件失败，取消预留不是对未来容量的保证。

父控制器于20:13停止，监督器判定资源失败满足安全断点恢复条件，但原策略要求新可用容量较失败时增加4GiB，折算为空闲显存至少67.482GiB。当时GPU4空闲60.657GiB，故监督器保持等待，没有自动启动第二次attempt。

新修复授权到达后，已核验旧控制器和科学worker退出、队列无活跃子进程、旧监督器仍停留在第一次attempt的资源等待状态。20:20:07，仅向身份匹配的旧监督器PID1595842、birth `466258973`发送SIGTERM；它以 `STOPPED_BY_EXPLICIT_REQUEST` 正常处理停止并退出，没有向科学worker发送信号，没有创建新父attempt，也没有干预其他项目进程。

本次仅改变R3的资源管理壳。其他阶段仍使用已登记的预留策略；原81个科学实现文件保持逐字不变。R3仍使用原2GiB保存KV驻留预算、16GiB非KV保存激活预算、8GiB完整KV上限及原存储与计算路径；不改变梯度、采样、奖励、C、π或optimizer更新数学。

修订版首次启动仍要求R3设备准入free至少56GiB。旧67.482GiB是父锚定策略下的失败后容量改善条件，不是R3通用显存硬门；本次明确授权的修订版初次启动绑定新的无锚点策略，不继续套用该旧条件。后继自动恢复仍须依据新运行的真实资源失败、实际退出及完整持久断点，不将数值错误、状态绑定失败或未知停止信号自动重试。
