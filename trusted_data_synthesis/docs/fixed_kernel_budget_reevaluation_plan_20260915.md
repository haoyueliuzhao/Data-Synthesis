# 原检查点的高预算复评检验

## 授权与旧实验边界

用户在获知原 1,620 个开发集会话均未形成可识别 Final 后，明确要求“提高预算重新
评估检验”。本次建立独立预算敏感性复评，不重新训练，不修改九个已保存检查点，
也不回写原实验 `COMPLETE_NO_POSITIVE_DIRECTION` / `STOP_RETAIN_BASELINE` 结果。
原实验完整结果已经以 `9cff3a40b08f33f71717a8a8165d725d350cb251` 发布至 main。

原实验的客观原因分类为：1,601 个会话耗尽响应次数，19 个会话本地上下文准入拒绝。
两者都没有可供完整财务验证的 Final。有限样例还显示空查询循环和未闭合工具 JSON，
因此增加预算不保证改善结果，也不能先验认定预算不足就是唯一根因。

## 本次预算

| 项目 | 原预算 | 新预算 |
| --- | ---: | ---: |
| 每会话模型响应次数上限 | 32 | 64 |
| 每会话工具调用次数上限 | 32 | 64 |
| 每次响应的新 token 上限 | 2,048 | 4,096 |
| prompt 加预留输出的总上下文上限 | 24,576 | 32,768 |

真实基座配置 `max_position_embeddings=32768`、`rope_scaling=null`、
`use_sliding_window=false`。因此本次不使用 49,152 或 tokenizer 声明的 131,072 作为
模型支持证明，不启用 RoPE 扩展，不更换模型、精度、模板或工具语义。
新上下文条件为完整 prompt token 数 + 4,096 ≤ 32,768；不截断历史、不缩减预留量。

这是多项预算一起扩大的检验。即使观察到改进，也只能归因于这组预算变更的联合
影响，不能据此分别认定响应次数、单次输出长度或上下文哪一项发挥了因果作用。

## 固定配对 pilot 和全量升级条件

首先从原 180 道开发题的公开任务元数据中，按固定 salt
`higher_budget_pilot_20260915:v1` 及 task ID 的哈希排序选择三题，每个评估组一题，
来自三个不同公司来源。抽样规则不读取旧模型的输出、成功与失败类型或训练 loss。
任务 ID 和原九个模型的 checkpoint 身份在任何新 GPU 生成前写入独立冻结记录。

所有三臂、三个种子的旧检查点均参与，pilot 分母为 **3 题 × 9 个模型 = 27 个会话**。
对应的 27 个旧预算评分直接作为配对基线复用，不重新生成或重新评分旧会话。
保留失败、上下文拒绝和未完成分母，不挑选较好模型替代其他种子。

推进规则在复评开始前固定：

1. 先完整执行 27 个新预算会话，并在模型进程退出后用相同财务标准离线评分。
2. 若 pilot 完整收口且至少有一个会话财务合格，按同一预算自动补评每模型剩余
   177 题；pilot 的三题结果直接纳入总计 180 题，不重复生成或重算。
3. 若 pilot 没有财务合格会话，则结束此次小批预算检验并报告诊断结果。
   这只是后续资源投入的门控规则，不等于证明其余 177 题高预算也必然全零。
4. 若模型故障或 pilot 超过从首个新 GPU worker 启动算起的 90 分钟墙钟限制，
   保留失败/删失和部分产物，不自动重试、不把不完整分母写成通过。

本次仅用已经暴露过的开发题作事后预算诊断，不打开原 720 题确认集，
不进行新的 VTDO 方向选择，不自动重新授权或启动 B 训练。

## 保持不变与工程实现

- 原模型参数、训练报告、材料核、开发题公共版本、neutral 提示、工具执行语义、
  greedy 解码、EOS、模板、财务评分及来源/单位/实际期间/支持链标准保持不变。
- 原始冻结源码和已封存目录保持不变；新外部适配器只在隔离命名空间内修改显式
  预算消费者和本次子集目录，记录原代码及变换身份，不修改旧模块全局变量。
- 生成、prompt 准入、生成长度判定、回执核验、运行时响应上限、离线历史重放
  必须使用同一新预算。只提高 `max_new_tokens` 而不更新其他消费者是不完整实现。
- 三题子集获得单独目录身份并绑定原完整公开目录，不能篡改原目录内容后保留旧 ID。
- 基座仅由父进程完成一次必要内容准入，使用可信 multiprocessing spawn 对象传递；
  每个子进程保留对应小型 LoRA 文件及恢复后参数身份检查，不再九次扫描同一基座。
- 最多八个 GPU worker，每张卡最多一个本复评任务；仅使用原八个 GPU UUID。
  新增长上下文的实际峰值尚未实测，初始准入取每卡至少 **80,000 MiB** 剩余显存，
  不限制 GPU 利用率。显存快照不是预留，不能保证后续没有 OOM。
- 模型加载和每次生成的实际资源计数继续保存。GPU 不足时排队，不干预其他账号作业。

## 评估指标及解释规则

同时报告：运行时可识别 Final 形成率、完整轨迹财务合格率、无 Final 数、
响应预算耗尽数、上下文拒绝数、实际新 token 数、模型生成调用数及墙钟时长。
`context_rejected` 与相应 `provider_error` 是交叉标签，不重复相加。

“出现 Final”与“Final 财务合格”分别统计；形成不正确或不具备支持链的 Final
不能写成任务成功。若预算只提高 Final 形成率而未提高财务合格率，应如实分别说明。
三题 pilot 不提供完整 180 题效果估计，也不提供统计上充分的方案排序或确认结论。
原 0% 是原预算条件下的正式结果，高预算结果必须单独命名并注明事后探索性质。
