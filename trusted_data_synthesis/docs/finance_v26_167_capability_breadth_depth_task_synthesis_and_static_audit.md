## Audit Revisions

### 1. Historical tier is not capability depth

The old `DifficultyTier` values `easy_control`, `frontier`, and `hard_control` remain historical
global-complexity bundles. They jointly changed Evidence amount, Program shape, retrieval,
reconciliation, verification, recovery, distractors, Tool use, and stopping requirements. They
are retained only for source provenance and historical replay.

The new depth language is separate:

```text
d0_observability_anchor
d1_basic
d2_compositional
d3_stress
```

No old Tier is mapped, renamed, or aliased to an `ObservationDepth`. The selected sixteen source
groups happen to contain four old Easy, eight old Frontier, and four old Hard tasks; that
distribution has no role in source ranking, depth assignment, or future boundary estimation.
The Capability Survival Profile remains execution-failure localization rather than an ability
scale.

### 2. Breadth is restricted to contract-complete capabilities

The exact breadth Catalog contains only:

```text
context_conditioned_action
semantic_reconciliation
failure_recovery
state_dependent_stopping
```

Retrieval, calculation, and verification remain nuisance or supporting dimensions. They are not
promoted to new capability axes in this stage.

### 3. Matched groups replace cross-task tier comparison

Each `CapabilityObservationGroup` owns one core Finance question and four paired depth variants.
Within a group, all variants share exact source task, Evidence IDs and Versions, source records,
canonical result, Answer schema and projection, Oracle Program, Verifier structure, Tool
environment contract, Prompt and Grammar identities, model and Thinking binding, bounded
generation Policy, and resource Contract.

The matched group is the primary independent unit. D0-D3 are paired variants; future rollouts are
secondary repeated measures. A variant is never counted as an independent task for inference.

### 4. Fixed maximum skeleton and single-capability overlays

Every group uses a three-slot D3-sized maximum skeleton at all four depths. Lower depths retain
inactive slots as one of four explicit inert forms: unique legal action, identity normalization,
non-trigger recovery slot, or explicit nonterminal state. Slots are never deleted to create a
shallower task.

Only registered target-capability load changes. Every overlay carries a zero-valued nuisance
delta over Evidence count, distractor load, Program node count, Tool count, verification
structure, and resource ceiling. `DepthDeltaContract` requires componentwise nondecrease and a
strictly positive total delta between every adjacent depth. It does not assume empirical success
monotonicity.

The resulting primary-load totals are:

| Capability | D0 | D1 | D2 | D3 |
| --- | ---: | ---: | ---: | ---: |
| Context-conditioned Action | 3 | 6 | 10 | 15 |
| Semantic Reconciliation | 4 | 6 | 11 | 15 |
| Failure Recovery | 5 | 6 | 10 | 15 |
| State-dependent Stopping | 4 | 8 | 12 | 17 |

These totals summarize registered constructive load. They are not empirical ability scores and
must not be compared across capabilities as a common metric.

### 5. D0 is a real observability anchor

Each D0 contains the target mechanism rather than a zero-load control:

- Context has one real context-dependent decision with at least two legal actions.
- Reconciliation has one nonidentity normalization axis whose emitted reference is consumed.
- Recovery has one real typed failure followed by an action revision and success; the old
  zero-recovery Easy shape cannot serve as D0.
- Stopping has a visibly complete state and a legal tempting continuation that must not execute;
  source Program node count is not used as stopping depth.

Both D0 nontriviality and D0 mechanism necessity are noncompensatory static Gates.

### 6. Evidence Capacity selects 64 tasks before outcomes

Source selection reads the frozen v26.163 70-task frame and its twelve exact v26.164-exposed
source tasks before loading any v26.166 outcome-bearing file. It directly binds the v26.163
source-selection audit, requires all 70/70 frame candidates to remain after historical exclusion,
and imports the exact historical exclusion counts into Paired Freshness. After exclusion, each target family
contains seven eligible source tasks. The fixed v26.167 salt selects four per capability, enough
for the recommended design:

```text
4 capabilities x 4 groups x 4 depths = 64 static tasks
```

The fallback 48-task design is not activated. Groups 1-2 in each capability form Development;
groups 3-4 form reserved Confirmation. The sixteen groups use 99 distinct public Evidence IDs,
with zero pairwise Evidence, Evidence Version, or source-record overlap.

### 7. Paired freshness and exposure are group-wide

Freshness is checked on task ID, source-task ID, Evidence ID, Evidence Version ID, core semantic
signature, mechanism-instance signature, source-record ID, and group semantic identity. The
selected groups have zero overlap with the already exposed v26.163 source Population and zero
cross-group overlap.

Any exposure of one variant marks its complete group exposed. Partial variant regeneration is
forbidden. Development and Confirmation have separate Catalog files and disjoint group IDs. The
Development reader rejects a Confirmation Catalog, and Confirmation remains sealed until a later
Development postrun audit.

### 8. Role compilation must preserve depth

All 64 variants are passed through the existing credential-free Role task compiler. The compiler
preserves the source Evidence, Program, canonical result, and operation DAG, and emits 64 distinct
Role task-package identities. The model-visible public metadata is independently read back and
must reproduce exact overlay, primary-load, nuisance, and public-witness hashes.

Source-to-Role depth signature matches are 64/64. Each group freezes the exact Tool set from a
baseline Role compile, and every D0-D3 Role environment equals that set. Tool closure, source
Runtime replay, public witness, and mechanism necessity pass 64/64. Compiler intervention and
depth-erasure counts are zero. Runner consumption is not preflighted and model behavior is not
measured. This is static compilation evidence, not proof that the model behaviorally distinguishes
the four depths.

### 9. Coverage gaps default to unassigned

The 21 frozen v26.166 Coverage Gap rows retain their historical
`compiler_assisted_capability_coverage_research_candidate=true` field because predecessor
artifacts cannot be rewritten. A separate prospective disposition Catalog assigns all 21 rows
`unassigned`, authorizes zero Compiler candidates, and requires a later independent audit before
any upgrade. Compiler intervention count remains zero.

### 10. Future boundary selection is precommitted but not executed

The new `BoundarySelectionContract` freezes four statuses:

```text
below_observation_floor
above_observation_ceiling
boundary_bracketed
nonmonotonic_or_confounded
```

Development support is prospectively frozen at 2/6 and Confirmation support at 3/8. A future
Development scan would use two Development groups, four depths, six rollouts, and one
capability-neutral `structured_direct` condition per capability: 192 Jobs total. It may localize
floor, ceiling, bracket, or confounding only.

Only a separately audited bracket may later select two adjacent depths in the two already sealed
Confirmation groups, at eight rollouts per variant and at most 128 Jobs. Confirmation data may
not support a same-data VTDO claim. Neither online stage is executed or authorized by v26.167.
