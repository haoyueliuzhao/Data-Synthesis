## 空卡高缓存与共享卡断点

完全空闲卡的条件为设备无计算进程且空闲显存至少80000 MiB，通过连续观察与启动前复核后采用 `high_cache`。非完全空闲卡仍可按test24 GiB、前缀32 GiB、Static48 GiB、C-only/Full75 GiB的安全门槛采用 `shared_checkpointed`，不额外预留高缓存。不是把80000 MiB设为所有任务的唯一门槛。

两种模式在派发时明确登记，不在启动后静默互相降级。已经运行的seed137 C-only和Full保持原PID，不为安装新策略而重启或丢弃计算。共享路径保留原逐步持久模型、Adam、RNG、pi及训练顺序检查点；发生未提交计算失败时，必须核对断点和反馈状态后再恢复，不能只根据还有检查点文件便直接重试。

自动断点续跑限于已登记训练臂的CUDA OOM：Static的完整已提交检查点，或C-only/Full明确发生在当前outer反馈生成之前的类别梯度失败。必须证明失败进程及会话已退出、原科学实现未变、checkpoint及RNG完整，且所有历史反馈均完整封存、当前outer没有新反馈。每项训练最多自动恢复两次，冷却60秒后等待空卡高缓存模式；本次seed251的首次显式恢复另行登记，不计入这两次。每次均保留失败回执并在再次启动前复核证据。

反馈生成或logP回放中的失败、未封存反馈、未知异常、缺失或不一致的checkpoint，不在自动恢复范围内。终点评价也不沿用训练断点规则。遇到这些情况保存现场并停止新派发，不能靠重复生成或丢弃部分样本换取完成状态。

新的执行包装器仍调用原冻结训练和评价worker。原GPU准入及UUID映射完成后，在实际模型加载边界分配76 GiB的临时uint8 CUDA Tensor，再释放Tensor，使其成为同一PyTorch进程可复用的缓存。模型随后使用这个缓存；不是另起占位进程，也不永久持有一块使模型无法使用的Tensor。原loader只调用一次，参数及返回对象不改，不调用随机采样，不改变batch、精度、优化器或序列长度。

模型加载返回后再次核验缓存；如果第三方加载过程释放了缓存，最多补足一次，并记录真实的allocated、reserved及设备占用。没有后台线程在训练过程中反复申请显存。任务退出时进程资源正常释放，下一项任务再执行整卡准入。

这次是用户明确授权的执行资源策略变更：空卡增加高缓存占用，共享卡保留安全准入与完整断点。原科学worker文件及历史记录不改；旧worker自身的资源描述不能单独代表新包装器的缓存策略，实际资源行为以新协议和显存回执为准。

## 不等同于驱动硬隔离

对空闲GPU7执行驱动 `EXCLUSIVE_PROCESS` 设置时返回 `Insufficient Permissions`，当前账户也没有可直接使用的免密sudo权限。驱动模式因此没有改变。NVIDIA说明该模式只允许一个进程使用设备，设置需要root权限；本次没有启用它。[NVIDIA nvidia-smi文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)

高缓存占用会显著减少其他大任务可申请的余量，但不是驱动层访问控制；很小的外部任务仍可能利用余量，PyTorch也可能在内存压力下回收缓存。因此不能承诺其他进程永远无法进入。新队列会记录实际显存和同卡进程，未知失败仍停止新派发，不以自动重采样掩盖错误。
