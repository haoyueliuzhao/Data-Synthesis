# FinQA完整任务分片与持久类梯度补验

本轮落实用户2026年10月10日“参照审计修订并开展后续实验”的请求。采用一次新的有界补验：将完整训练任务分给GPU3、4、5、7，每完成一个任务即封存其全部状态的实际类梯度；全部任务齐全且分片进程退出后，由GPU7执行一次原序全局复算。继续读取V33已完成的response573累计gJ，不重做微观回放、不重采样、不重评分、不执行真实optimizer更新，原B继续暂停。

唯一新输出目录为 `v25_training_replication_01/replay_performance_04/`。V32、V33、V34的协议、停止条件和结果不回写。新任务缓存只能保存以后实际算出的梯度，不能追回V34未保存的3107行中间结果。本文区分设计、CPU验证和真实GPU状态；未完成的数值与资源验收不预记为通过。

## 一次完整pass的任务划分

本轮仍覆盖原744个训练任务、2468个完整包、1360个状态及4974个有效forward行，包含全部单状态任务。原始4978行中的4条零target行继续由原pool过滤，不为提速删长输入、材料或状态。

一个任务的全部状态、全部包和全部有效行交给同一个worker。任务视图只限制可见任务及其包，保持原全局registration对象；不重新构造局部均匀μ、π或任务集合的归一化。每个状态的包数及每包完整target-token分母保持原值，包和行顺序沿用原pool。

分片计划在GPU执行前按输入元数据确定：以每任务有效行的input-token数之和作为负载估计，按估计从大到小分配给当前累计负载最小的分片；并列按原任务序号及分片序号消歧。每个分片内部再恢复原任务顺序。这个估计只用于调度，不声称等于GPU时间；不根据新数值结果挑任务或调分片。

| 阶段 | 设备 | 工作 |
| --- | --- | --- |
| shard00 | 物理GPU3 | 其登记的完整任务集合 |
| shard01 | 物理GPU4 | 其登记的完整任务集合 |
| shard02 | 物理GPU5 | 其登记的完整任务集合 |
| shard03 | 物理GPU7 | 其登记的完整任务集合 |
| coordinator | 物理GPU7 | 四个分片进程全部退出后，一次全局复算 |

这不是四卡各算完整pass，也不是DDP平均梯度。不同任务只在后续全局G中结合；同一状态的包不跨卡分拆，不增加树形或异序浮点归约。协调器恢复原task、state及parameter顺序，使用原全局μ、实际π、真实Adam、损失分母与原prepare/update函数。

保持逻辑次序仍不是多设备逐位相等的证明；PyTorch并不保证数学等价或跨环境运算一定逐位一致。因此本轮保留实际G、虚拟θ、point、pullback、C与π的严格对照，不以CPU对照替代CUDA验收。[PyTorch 2.7数值精度说明](https://docs.pytorch.org/docs/2.7/notes/numerical_accuracy.html)

## 完整任务梯度缓存

每个任务使用按原任务索引生成的固定目录，不把任务名称直接当任意文件路径。一个完成记录必须同时包含 `gradient.pt` 与 `record.json`，以原子目录发布；临时目录、行计数及只有一半文件的目录不算完成。

任务缓存保存所有状态、全部参数坐标的实际CPU梯度Tensor，并绑定以下内容：

- 原point、实际pre-state摘要和原outer输入文件；
- 原任务及状态顺序、任务的全部原包顺序、完整包分母、行内容摘要和参数规格；
- 冻结数学源码、未改动的V34存储后端字节和本轮实现身份；
- Tensor文件SHA、语义摘要、逐Tensor摘要及完整任务标志；
- 实际计算前后状态检查、所属分片和该任务的存储审计。

任务完成前后核验参数、已有`.grad`、Adam、RNG、buffers和mode不变；冻结基座在模型加载时核验内容，任务间继续核验其存储与version。只在完整任务计算及这些检查完成后发布缓存。每个task的全部状态和参数必须齐全、CPU dtype和shape正确且有限，不接受缺状态、补零、非有限值或不同点的缓存。

缓存只允许首次完整提交，不覆盖已有完成目录。复用入口会先校验实际字节、参数坐标、顺序和绑定；有效完成任务直接跳过计算，缺失任务才可计算。最终协调器必须读齐全部744题，缺一题即停止，不对成功子集重新归一化。

本轮初次运行没有可继承的V34类梯度缓存，因此仍要产生全部4974行对应的完整任务梯度。若再次停止，已经完整提交的任务保留；当前未提交任务可能需要在未来获授权的恢复中重算。支持缓存复用不等于允许控制器自动重启或重置预算。

## 原存储后端与同点数值门

保存张量继续使用冻结的 `v34_layout_preserving_class_saved_tensors.v1`：绑定冻结owner保留原GPU view；支持的非重叠张量独立保存到CPU，取回时恢复原shape、stride和storage offset；不支持的布局在保存前选择保留原GPU表示。没有新增batch、精度转换、attention后端、激活去重或OOM后回退。保存位置改变必须满足原值合同，仍须通过实际GPU结果检查。[PyTorch 2.7保存张量hook说明](https://docs.pytorch.org/docs/2.7/notes/autograd.html#hooks-for-saved-tensors)

四个分片各自恢复同一实际pre-state和非空Adam，只调用原class_gradients进行所分配完整任务的计算，不执行局部Adam、局部C或局部π更新。冻结损失子模块在恢复真实RNG前完成导入，避免首次懒导入发生在状态不变检查区间内；没有在计算后重置RNG来掩盖变化。

协调器在CUDA初始化前校验并装配所有任务CPU梯度，读取V33真实 `response000573` 的gJ，并与原参考gJ核验；原参考只用于比较，不作为恢复结果替代品。随后恢复真实模型和optimizer，按原函数执行：

1. 从完整任务梯度计算G和虚拟θ，重新计算point_id。
2. 先封存gJ、G、θ和point的比较；任一不一致就停止，不进入后续分布计算。
3. 通过虚拟点资源边界和停止门后，执行唯一一次原pullback、C与π复算。
4. 独立保存实际计算出的G、θ、pullback、C、π及完整比较，再检查最终资源门。

没有feedback collector、重评分或真实optimizer.step入口。分母仍为700，原C/N公式和分布更新参数不变。同点失败不得通过修改point字符串或新建反馈目录处理。即使最终数值通过但资源失败，真实比较证据仍应保留，整轮仍按失败记录。

## GPU与全机内存边界

仅允许GPU3、4、5、7，最多同时4个GPU worker，每卡一个；CPU初始化中的已派发worker也计入。初次四卡派发要求四卡都无compute进程、每卡至少72GiB空闲，并核对UUID。不借用GPU0、1、2、6，不驱逐其他作业，不通过占位分配预留显存。

每个worker的allocated历史峰值从模型加载前开始记录，仍不得超过76GiB；规定边界设备free仍至少2GiB。继承V34的行边界检查，任务与模型释放边界也有记录。新协调器是新进程，其峰值独立记录；这不消除任何分片已发生的资源超限。所有分片结果均须通过，才可准入协调器。

| 主存准入或观测项 | 预登记值 |
| --- | ---: |
| 单分片进程RSS高水位上限 | 160GiB |
| 单协调器进程RSS高水位上限 | 192GiB |
| 全机有效可用内存余量 | 至少96GiB |
| 首次四分片准入 | 至少4×160＋96＝736GiB有效可用内存 |
| 协调器单独准入 | 至少192＋96＝288GiB有效可用内存 |

有效可用内存取Linux `MemAvailable` 与可见cgroup有限memory.max剩余空间的较小值。控制器观测本轮进程VmRSS/VmHWM，worker也在GPU资源记录中写入主存值，超限即停止全部后续工作。Pinned保存会占用主存，但这里没有独立pinned字节硬限，不能把RSS预算解释为锁页内存分配器的强制配额或绝不OOM保证。

启动前还要求可用磁盘不少于两倍完整类梯度原始Tensor估算量加32GiB余量，为原子写入及其他产物留空间。以上是准入估计和运行观测，不是真实资源预留；其他作业可能改变可用量，需在运行中继续执行资源门。

## 全流程时限和停止

总窗口从首个分片worker的首次派发启动起计4小时，四个分片、缓存封存核验、协调器等待与全局复算共用同一个截止时间。每个阶段不能重新获得4小时。首次启动前累计资源等待最多24小时；首个worker启动后，资源等待同时消耗总窗口。

正常4小时窗口最多同时四个worker，因此调度包络上界为16 worker小时，不是4 GPU小时。若触发停止，最多10分钟的安全退出宽限由所有活跃worker共享，不逐进程另计10分钟；宽限期不派发新任务或新阶段，实际收尾墙钟另行记录，不隐藏在16 worker小时口径里。计时窗口是停止上限，不是完成时长承诺。

任一数值、输入、显存或主存门失败，或全局截止时间到达，控制器向已核验PID、birth和命令的本轮worker同时请求安全边界退出；必要时在共同宽限后仅终止这些核验进程。已完整提交的任务缓存不删除，保留剩余名单；不自动重试当前任务、不再启动第二遍pass。

全部任务完成以后，先等待四个分片进程真实退出并释放其模型，再由单个协调器运行。协调器若来不及在原总窗口内完成，也按相同规则停止，不能因为已进入新阶段而放宽总时限。
