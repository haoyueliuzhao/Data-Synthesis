# Delayed-C 后续阶段：积极准入、持久保存与自动恢复

## 授权与范围

2026-09-21 用户要求：“调整后续其他任务，采取积极运行策略，做好保存与自动恢复运行”。

本次修订覆盖已经获准的两个剩余运行 `A_delayed_c_47`、`A_delayed_c_29`：剩余 SFT、已有反馈的梯度回放、固定最终 greedy 生成、独立 CPU 评分。seed11 的完成结果保持不变。

这是一项资源调度和保存机制修订，不是新的实验条件。没有启动 B、独立确认、其他种子或额外反馈轮次；没有重新采样或重新评分原先已封存的 720 条反馈。

原恢复实现、GPU5 控制器及原注册文件保持原样。新控制层在独立文件中实现，部署前记录源文件 SHA-256、Git 提交、原控制器和被接管工作进程的 PID、UID、出生时钟和完整命令行。

## 分阶段积极准入

| 阶段 | 原门槛 | 新的起始自身容量门槛 | 冷启动空闲门槛 |
| --- | ---: | ---: | ---: |
| SFT | seed47 已降至 32 GiB；其他仍为 60 GiB | 32 GiB | 33 GiB |
| 反馈回放 | 60 GiB | 50 GiB | 51 GiB |
| 最终 greedy 生成 | 72 GiB | 56 GiB | 57 GiB |
| 独立 CPU 评分 | 生成工作进程原先等待评分结束 | 不需要 GPU | 不需要 GPU |

“自身容量”沿用 `CUDA 空闲显存 + 本进程 PyTorch 已保留显存`。冷启动多留 1 GiB 给上下文/驱动等分配；实际启动仍可能遇到其他任务同时增长。

这些是积极尝试值，不是已经证明的全工作负载峰值上界。已观察到 seed47 恢复后的 SFT CUDA 峰值 allocated 约 18.71 GiB，早期 reserved 约 24.18 GiB，后续 reserved 也会变化。反馈曾有约 45.67 GiB 的本任务占用并遇到共享卡资源挤压；最终评测的最长上下文不能由短轨迹证明一定能装入 56 GiB。

因此发生真实 OOM 后，受影响阶段的容量门槛每次提高 4 GiB，最高 76 GiB；重试等待为 60、120、240、480、900 秒，之后最多每 900 秒尝试一次。阶段失败计数保留，避免在相同不足的门槛下快速反复 OOM。这个策略可能在后续资源继续紧张时再次转为等待，不能保证始终有进度。

取消原来“每个运行总共最多三次启动”的资源恢复限制。统计样本、有效训练步数、模型和数值验证规则没有因此放宽。最终未提交会话的额外生成尝试仍设独立上限，见后文。

## 不打断健康工作与自动恢复

- 首次部署只替换旧监督进程；正在工作的 seed47 和 seed29 先按原 PID 接管。
- 旧工作进程仅在明确记录了显存等待、且处于相应休眠边界时，才停止并用新阶段策略从断点恢复。不会对正在运算的健康进程进行周期性强制迁移。
- 每个运行有互斥锁；GPU 租约沿用原共享目录。只选择有足够空闲显存、且未被本实验其他工作进程租用的 GPU。租约不能阻止其他用户使用同一块卡，也不表示独占。
- 两个运行独立推进；一个数值或数据错误不会杀死另一个健康运行。已有外层梯度互斥规则保留；反馈外层的主机可用内存门槛设为 128 GiB，其他 GPU 阶段启动检查为 64 GiB。
- 新工作进程在持久单元之间等待约 60 秒仍没有容量，就退出并释放 GPU，由控制器等待或迁移到合适的卡。不会在 optimizer update 内主动退出。
- 外层守护进程对监督进程的 SIGKILL/SIGTERM 等非正常资源退出或明确资源退出码进行重启。监督进程重启后按进程身份接管仍存活的工作进程，不重新启动同一运行。
- 工作进程消失但没有应用失败报告时，按“疑似抢占/外部终止”处理，并记录这是推断；从最近持久断点继续。明确的数值、协议、数据完整性异常停止该运行并落盘，不能伪装为 OOM 或零奖励。

守护是本机脱离终端的后台进程，不是跨主机调度器。本次没有安装系统级开机服务；整机重启、守护本身被杀、磁盘不可写、工作树丢失等情形不能声称已自动处理。数据盘保留恢复材料和操作入口，必要时可重新运行 `--mode start`。

## 最终评测恢复与预算

每个剩余种子只允许 step400 的那个模型点、固定原有 180 个任务、原 greedy 解码后端、原 trajectory seed、原 source view 和原评分规则。

恢复流程先核对全部 400 步的有效 token 剂量及十遍 package 覆盖，再核对保存的最终参数。如果 checkpoint 已提交但相应更新 JSON 尚未提交，从 checkpoint 内嵌的同一报告补齐，不重复该优化步。

每个完整会话单独提交。恢复时检查任务、参数点、字节摘要、会话身份和生成 receipts；已经提交的会话直接复用，不重新生成，也不根据其得分选择是否保留。不同内容的重复已提交会话视为错误。

中断前尚未提交的会话可能重做。它已经执行的部分模型调用不能声称不存在：新流程在每次实际 `model.generate` 前保存调用意图，返回后保存完成计数。意图与实际调用之间仍有一个极小中断窗口，因此额外开销报告为保守上界，而不是伪造精确实际调用数。

- 两个运行各提交 180 条最终会话，成功会话仍各最多 5,760 次调用，总计 11,520。
- 每个运行允许未提交中断尝试最多额外 5,760 次调用意图上界，两个运行合计 11,520；达到上限停止，不能无限增加物理生成预算。
- 旧最终工作进程若在没有新调用日志时丢失，对未提交任务按每条最多 32 次计入保守上界；不填成零。
- 所有 180 条生成完全封存以后，才启动独立 CPU 评分进程。新 GPU 工作进程此时已经退出并释放 GPU，不再为 CPU 评分占卡。
- CPU 评分最多 12 路并行，每条结果独立保存；已经提交的评分不重做。如果提交评分后、汇总前中断，复用保存结果生成汇总。

新流程仍保留原 greedy `Decoder`、`generate_jobs`、参数点上下文、运行时和 `score_one`；修改的是单会话任务调度、计量和保存，不是解码或财务判定。

训练的有效剂量仍是三个种子各 400 步。原恢复累计物理完成 1,303 步的基线包含 seed47 的 103 步重放；新的失败也可能产生已完成但未提交 checkpoint 的工作。最终报告因此给出已知物理完成数下界、可确认的额外重复及不确定中断数量，不无条件沿用“总物理次数精确等于 1,303”。
