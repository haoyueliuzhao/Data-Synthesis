# Delayed-C：GPU5纯训练显存门槛修订及保存（2026-09-21）

## 原因与范围

用户先授权迁移，随后指出资源分配变化，并明确要求核对是否确实需要60GB、尝试恢复GPU5上的运行，最后要求资源紧张时做好保存、能运行就运行。此前GPU0迁移方案没有执行，没有因此停止任何实验进程；本修订采用GPU5原卡受控重启，只调整seed47的纯SFT准入策略。

60 GiB不是当前SFT阶段已测定的最低需求。早期说明`fixed_kernel_anchored_sources_plan_20260916.md`中的60 GiB准入沿用了评估峰值52.678 GiB加余量，并明确不是该检查的实测峰值。恢复版本又把60 GiB用于各计算阶段的持续容量检查，导致seed47在GPU5等待：本进程可用容量约46.7 GiB，低于统一门槛，但此前SFT进程显存占用观测约25—26 GiB。

上述25—26 GiB是运行观测，不是全程严格峰值，也不能作为反馈回放或最终生成的上界。因此只对已经完成外层反馈的seed47下调训练门槛，其他阶段不跟随下调。

## 修订后的准入与实测

| 阶段 | 本次策略 |
|---|---|
| seed47纯SFT | 本进程可使用容量至少32 GiB；冷启动空闲至少33 GiB，包含1 GiB驱动余量 |
| seed29反馈梯度 | 保持60 GiB，不修改其现有进程 |
| 最终生成/评测 | 保持72 GiB，不下调 |

运行中容量指`CUDA当前空闲 + 本进程PyTorch reserved`，不是要求在模型常驻后再额外空闲32 GiB。原卡重启前，用当前空闲加待退出的本实验进程显存估算可释放容量；原进程退出后再重新检查实际空闲并获取本项目GPU租约。

最初准备采用40 GiB；用户进一步明确“门槛设置可以激进一些，近期资源都比较紧张”，因此在实际启动前改为32 GiB。32 GiB是允许一定资源风险的工程准入修订，不宣称已证明所有训练批次峰值小于32 GiB。恢复后的每个真实optimizer更新会记录自worker启动以来的CUDA allocated/reserved峰值，包含模型载入和检查点操作；不额外跑训练探针。若资源再次不足，仍在已保存边界等待；OOM只按已登记的有限资源重试处理。

## 控制交接与数值不变性

- 新控制入口：`run_fixed_kernel_delayed_C_migration_20260921.py`。文件名保留迁移原型命名，但本次注册明确为GPU5原卡重启，运行元数据放在`delayed_C_recovery_20260921/gpu5_sft_capacity_20260921`。
- 只在seed47的显式GPU容量等待、主线程睡眠及完整检查点边界交接。向进程发送信号前，核对PID、UID、进程启动tick及完整argv；不使用批量kill或进程组终止。
- 冻结原协调器后核验最新参数/Adam/RNG检查点，再退出旧协调器和旧seed47。seed29原PID由新控制器接管，不向它发送暂停或终止信号。
- 新worker调用原恢复执行函数；只在seed47子进程内覆盖训练容量常量和增加内存日志，不修改原冻结源文件，不改变loss、数据、任务计划、dropout、Adam、分布更新或数值复现阈值。
- 本次占用既有启动上限中的第2次worker启动，不增加完整optimizer更新预算。由231步检查点继续时，下一个执行的是232步；已完成的201—231步不重算。原有103步恢复重放记账不变。
- 主机GPU共享不能保证独占：不终止其他用户任务，资源不足时等待，不以任务恢复为由跳过保存或数值检查。
