# 一、本轮审计

## 1. 当前声明与上一轮要求一致，没有扩大成功含义

本轮只回答：

> 对十二个既有首次 pending Observation，在指定提交 accept 的条件下，公开原有 Update 条件，能否提高一次提交即完成合法完整接受的比例？

报告明确排除了完整任务成功、未见任务泛化、自主接受意愿、一般知识修订和 VTDO 效用；没有因结果良好而自动追加后继完整会话。

因此，本轮有三个分别需要判断的对象：

| 对象          | 应成立的命题                      |
| ----------- | --------------------------- |
| **修复正确性**   | 公开说明补齐，但原合法／非法提交的判定标准不变     |
| **配对执行完整性** | 两组使用对应的同一观察态，真实响应原样评分，不替换失败 |
| **工程推进条件**  | 修复组达到事先登记的有限可用性门槛           |

不能用测试通过替代模型结果，也不能把单步接受结果升级为完整解决行为。报告没有混淆这些层次。

## 2. 源码落实：修复的是公开合同，不是评分标准

### 2.1 新合同确实给出了此前缺失的对象边界

`update_public_contract.py` 明确公开：

```text
accept：
proposed_claim 对应整个
/state/pending_observation/proposition

reject：
proposed_claim = null
```

同时公开 assessment、Observation 引用、完整有序 lineage、义务及 transition 字段的来源。它采用路径与条件表达式，**没有把当前正确响应整份填好交给模型**。

这里正确保留了两个区别：

$$
\text{完整 proposition}
\neq
\text{仅 output、单个数值或自建 Claim 外壳},
$$

$$
\text{canonical JSON 内容相等}
\neq
\text{原始响应字符串逐字相等}.
$$

所以，键顺序和空白可以变化，但不能借此改变字段、数值、JSON 类型、数组顺序或精度。此次修复没有把“完整命题接受”降级成一个 accept 标志。

### 2.2 两组确实调用同一个原准入分支

实际 `evaluate_update_readonly()` 的路径是：

```python
submitted = parse(raw)
require(submitted["kind"] == "update", ...)
PublicQARuntime._admit(..., submitted, challenge)
```

评分上下文只持有复制的 pending Observation 和 terminal 状态，没有 adapter、执行器、store 或 Claim 提交方法。`complete_accept` 还要求实际提交的 disposition 为 accept。**合法 reject 不会被算成接受成功。**

`evidence.py` 对两组都调用这一入口，没有依据 `arm=R` 放宽接受要求；模型身份和生成条件检查也进入最终成功事件。

此外，准备代码强制检查 `protocol.py`、`canonical_json.py` 的字节不变，以及原 Runtime `_admit`、独立测量 `_admission` 的 AST 一致性。报告记录这些检查通过。本次读取了检查实现，但没有另行执行这一组 Git/AST 比对。 

**因此，现有证据支持“通过率变化来自生成条件的公开呈现变化”，而不是“评分器改得更宽松”。**

### 2.3 局部接收端不再依赖旧 fixture 的隐藏构造知识

新的隔离接收端解释公开规则中的 `copy_from`、`by_disposition` 等表达式，不导入旧 `update_response()`，也不读取 Runtime 私有状态。

这正面解决了此前的测试盲点：旧 fixture 内置 `deepcopy(proposition)`，只能证明“知道规则的程序能通过”，不能证明规则已经充分公开。当前局部控制可以检查**仅依据公开表达式是否足以构造符合原标准的响应**。

118 项控制支持的是四种当前命题形态上的有限合同一致性，不是 118 个模型样本，更不是通用协议完备性证明。报告对此有清楚限定。

## 3. 直接反例检查：没有看到选择性取样、响应代写或结果混用

### 3.1 挑战选择没有挑选“后来成功的请求”

`plan.py` 对每个历史会话选择首次实际成功 Action 之后的第一次 pending-Observation 请求，而不是按后来的 Update 成败选择。

C03 因此使用 turn 3，而不是后来成功的 turn 20。十二个观察态覆盖四个 comparison、四个 lookup、三个 sum 和一个 ratio。 

这仍然是已知历史数据上的诊断校准，不是数据盲确认；但它没有出现根据本轮模型响应重新挑选挑战的情况。

### 3.2 O 组不是复用历史失败，R 组也没有读取 O 的输出

两组共享相同的新 accept-only 校准指令。因此，O 不是历史提示的逐字复跑，旧失败响应不能替代本轮 O 的实际调用。

每个配对的两份请求都在第一次发送前冻结；六对 O→R、六对 R→O，第二组不接收第一组响应作为示例或反馈。实际 runner 也按该顺序执行。

这已经足以支持本轮有限配对比较；没有必要再追加等长度无关文本控制或逐字段消融，才能接受当前完整修复包的结果。

### 3.3 实际失败形态与修复目标吻合

二十四条响应全部通过 JSON／结构 Schema，也全部选择 accept。

O 的十二条响应中，十一条 `proposed_claim=null`；另一条把正确 proposition 包在自行构造的 Claim 外壳内。它们均首先失败于原来的整对象接受检查。R 的十二条则通过了 proposition、assessment 和 transition 的完整检查。

所以，本轮排除了两个直接反例：

* 不是 R 通过 reject 避开完整命题提交；
* 不是把“JSON 格式正确”当作“语义接受成功”。

同时，O 的首错不能证明其后面的 assessment、transition 全部正确。报告没有作出这种过强解释。

### 当前可以保留的科学结论

现在不必继续把呈现缺口的作用仅表述为“可能有影响”。更准确的是：

**因此，本轮应收口。原先建议的六个完整会话，现在已经满足进入条件，不需要在中间再插入一次相同的公开合同审计。**

# 三、下一轮测量：重点看首次接受之后发生了什么

## 1. 主结果仍以完整会话为分母

对任务 \(x\) 的第 \(r\) 个会话：

$$
Y_{x,r}
=
\mathbf1[
\text{有效 Final}
\land V_{\mathrm{QA}}
\land V_{\mathrm{trajectory}}
].
$$

两个会话证据均完整且可判定时：

$$
\widehat q_x=\frac{Y_{x,1}+Y_{x,2}}2.
$$

六行均可判定时：

$$
\widehat q_{\mathrm{pilot}}
=\frac13\sum_x\widehat q_x
=\frac{\text{完整成功会话数}}6.
$$

始终分别报告 C/B/S 的分子／分母。未知或未启动不填成零，也不删除后重新归一化。

这些是新条件下的有限工程观察比例。**不得把新六会话与旧十二会话、本轮二十四单步调用合并成一个“总体成功率”。**

## 2. 增加一张“推进位置表”，但不拿它替代最终成功

每个会话记录是否实际到达：

| 位置                | 需要的实际证据                          |
| ----------------- | -------------------------------- |
| 首个合法 Action       | 模型提交被准入并发生执行                     |
| 首个 accepted Claim | 新的模型 Update 被准入且 commit          |
| 后继依赖消费            | 后续 Action 或 Final 真正引用并使用该 Claim |
| 完整任务输出            | 有效 Final 与独立 QA／轨迹验证             |
| 首个阻塞点             | 实际 Receipt、执行或终止记录               |

C 的首个 Claim 可以直接被 Final 消费；B/S 则需要后续操作。不能为了统一指标，强制 C 增加一个多余 Action。

这张表能分清：

* 仍停在原来的 Update 接口；
* 已通过首次接受，但后续新命题失败；
* Claim 已产生，却没有被正确消费；
* 运算完成，但 Final 失败；
* 完整闭环成功。

**这比单看调用量或总体成功率更接近本轮理论对象。**

## 3. Update 指标按实际 Observation 分开统计

建议同时记录：

* 新 pending Observation 数量；
* 每个 Observation 的第一次 Update 是否合格；
* 是否最终被合法 accept 或 reject；
* 为处理它用了多少次模型提交；
* 第一个拒绝字段或条件；
* 其 Claim 是否随后被使用。

不要把同一个 pending Observation 的十次错误响应当作十个独立任务失败。也不要将“最终接受”与“一次接受”混为同一个成功率。

对本轮已经修好的原规则，如果再次失败，应先区分公开合同是否真的出现在实际 HTTP 请求中，以及模型是否在规则已公开的条件下仍提交了错误内容。**前者是接口实现缺陷，后者才是当前条件下的模型违例。**

## 4. 广度与深度：从新实际执行计算，不预填结果

广度表继续区分：

```text
本轮选定并执行的三个类型
已有来源但本轮未测量的类型
当前来源未实例化的类型
```

不因为六会话全成功，就宣称十一类全部完成模型验证。

深度仍使用实际事件导出的结构依赖深度、语义操作深度和可观察选择依赖深度；完整轨迹与未完成前缀分列。

上一轮 B 只执行了首个 lookup，尚未测得完整语义深度三轨迹。下一轮只有在真实增长分支、合并及后续依赖完成后，才能记录对应完整深度。

**不能将 Update 复制次数、错误后重试次数或解释长度相加为推理深度。**三个任务之间的成功率差异也不是深度的因果效应，因为任务、来源和操作要求并未被单独控制。

## 5. Share 支持描述、商映射与训练表示保持分层

Share 的支持方式，应从有效 Final 向后追溯：

$$
\text{Final Claim}
\leftarrow
\text{percent}
\leftarrow
\text{ratio}
\leftarrow
\text{实际 denominator}.
$$

只有 ratio 实际消费 `relation_sum` 产生并被接受的总额 Claim，才记录完整重建支持见证。曾经调用 sum，最终却读取披露总额，不自动成为重建路线。

六会话最多形成三个同任务无序配对：

$$
3\binom22=3.
$$

只对实际 Qualified、且当前投影支持的轨迹比较。存在纠正或 reject 而投影规则尚不支持时，允许：

```text
Qualified = true
projection_status = undetermined
```

不要求本轮得到两类，也不继承旧 Share 的 Assignment、\((4/5,1/5)\) 或 P/Q 权重。

若有完整 Qualified 会话，同轮可以复用既有导出器和 tokenizer，生成**新条件下真实请求—准入原响应**的监督候选。未准入响应、失败会话前缀及本轮二十四个单步校准响应不混入这一正向池。

Token 检查不适配时保留原始候选和长度诊断，不截断，也不回写轨迹失败。没有 Qualified 会话时导出为空，不能以空数据集宣称正向表示通过。

**这些导出和有限比较是附加测量，不应成为“完整任务模型接入”通过的隐含新门槛。**

# 四、下一轮如何收口

建议分开“执行测量是否正确”与“模型取得多少成功”。

| 实际结果                          | 正确结论与下一步                     |
| ----------------------------- | ---------------------------- |
| 三个任务各至少一个完整成功                 | 获得三个代表任务的新条件完整可达见证，关闭本次接入问题  |
| Update 普遍通过，B 在后续依赖或 Final 失败 | 保留已修复结论，只定位新出现的具体失败          |
| 仍大量失败于整对象接受                   | 核对实际公开请求；区分呈现没有落地与模型仍违例      |
| 模型合法 reject，但未完成任务            | 记录真实选择，不强制改为 accept，也不冒称任务成功 |
| 六会话证据完整但成功很少                  | 接受有界负结果，不替换或补采样              |
| 证据不完整或 Host 自动修复响应            | 阻断相应测量，不能用正确答案补偿             |
| 有效轨迹投影未定                      | 保留资格，单独记录测量缺口，不删除纠正历史        |

**不设置 6/6 为工作流通过条件，也不要求 Share 两条路线都出现。**“三个代表任务均有完整见证”可以作为独立科学结果报告，而不是用来否定已经正确执行的失败会话。

若三个任务的完整可达见证获得，应停止重复相同接入试验，再转向新协议下的实际轨迹测量与任务面板建设；不继续为了把成功率调到满分而停留在接口校准。若失败，则只修复首个有实际证据的新阻塞点，不重新打开已经关闭的来源、Registry、旧商归并或训练权重恒等式。
