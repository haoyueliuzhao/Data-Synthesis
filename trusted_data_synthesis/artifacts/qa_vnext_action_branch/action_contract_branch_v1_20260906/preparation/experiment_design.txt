$$
\text{Action}
\rightarrow
\text{Observation}
\rightarrow
\text{显式 Update commit}
\rightarrow
\text{Claim 消费}

## 3. 当前明确缺口：Action 的“候选全集”与“选中候选”没有充分区分

### 3.1 源码要求的是全集，不是模型考虑的子集

当前 `Decision` 的公开 Schema 对字段主要约束为：

```python
candidate_action_ids: list[str] = Field(min_length=1)
selected_action_id: str
```

实际 Runtime 则要求：

```python
len(candidate_action_ids) == len(set(candidate_action_ids))
and set(candidate_action_ids) == set(current_available_action_ids)
```

也就是说，模型必须列出**当前 Request 中全部可用 Action 的 ID，且不得重复**；然后通过另一个字段选择其中一个。仅列出选中的 Action，或者只列某个义务下的一组候选，都不满足当前合同。

中性提示要求“在给定合法候选中选择”，但没有明确补上这个集合等式；当前新增 publication 又只覆盖 Update。结合源码与报告对实际 HTTP 的检查，**这里确实存在模型侧条件说明缺口，不只是我们对错误码的猜测。** 

一个直接例子是：

```text
当前 available_actions = {a, b, c, d}

candidate_action_ids = [b]
selected_action_id = b
```

其中“选中 b”可以合法，但“只声明 b 一个候选”仍会被拒绝。**动作选择合法，不等于整个 Action 提交合法。**

### 3.2 B 的失败证据与这个缺口精确对应

B01 的 26 次拒绝、B02 的 28 次拒绝，全部是遗漏当前可用候选 ID；没有额外虚构 ID，也没有重复 ID。

$$
26+28=54.
$$

两条 B 会话总计 64 次提交，其中只有五个 Action 和五个 Update 被准入，恰好剩余 54 次候选集合拒绝。

这支持的定位是：

> **当前 B 的主要执行预算消耗，发生在 Action 候选全集声明，而不是实际增长率或分支合并运算。**

但不能进一步断言：公开这条规则后，模型的所有 Action 字段和全部后续阶段必然正确。Runtime 在集合检查之后，还检查选中项、operation、inputs、parameters、obligation、basis 和 expected effect 等对应关系；首错统计没有验证这些后续条件都已满足。

### 3.3 这是接口语义，不是推理质量指标

需要防止把修复对象误认成研究目标：

$$
\text{列全候选 ID}
\neq
\text{模型认真比较了所有候选},
$$

$$
\text{候选数量更多}
\neq
\text{关键推理深度更高}.
$$

当前修复的目的，是让已要求的公开协议可理解、可执行，避免这一编码要求遮蔽后续真实行为。它本身不能被当作 VTDO 创新、Contribution 或更充分推理的证据。

# 二、QA 广度、深度与轨迹落实的实际判断

B01 获得三个 lookup Claim，B02 获得两个；这些 Claim 都没有被后续运算消费。实际增长率、分支合并和绝对差值均未执行。

## 2. S 的完整轨迹有效，但没有形成“重建总额被实际使用”的见证

两个 S 会话都执行并接受了 `relation_sum`，但后续 ratio 的 denominator 均直接引用披露总额 Evidence。最早产生的 total Claim 没有被使用；ratio Claim 和 percent Claim 则形成了真实的后续依赖和 Final。 

因此：

$$

\not\Rightarrow
\text{最终采用重建总额路线}.
$$

报告的 `disclosed_total` 描述正确，完整重建支持见证为零也正确。

这不应导致两个追溯修改：

**不能新增“所有已执行 Action 必须被 Final 使用”的条件，回头否定 S 的资格。**当前有效性合同没有据此拒绝它们。

**不能自动删除这次未使用的 sum，把 S 改写成历史最短 D 路线。**最终分母来源相同，不意味着完整行为图必然等价；实际执行和 accepted Claim 是否允许归约，仍由相应商规则决定。

当前 C 配对为 equivalent，S 因纠正历史而保持投影未定，正是合理的测量边界。没有新 Assignment、完整商分布或旧 State ID 继承。

## 3. S 的 Final 问题真实存在，但不是本轮新的全局阻断

S01 有两次、S02 有二十五次 Final 拒绝。失败响应与要求的结果投影不一致，包括额外外壳、高精度值、JSON number、百分号后缀或缺失单位，部分还存在 citations 错误；最终两条会话都被模型后续新提交纠正。

这里需要区分：

$$
\text{Update：接受完整原精度 proposition}

和

$$
\text{Final：按任务合同输出答案投影}.
$$

不能用一个统一的“都保留高精度”或“都量化六位”规则替代两个阶段的不同责任。

但**当前不能仅凭 Final 错误很多，就断言 Final 与 Action 一样存在未公开合同缺口**。报告已经说明其公开数值条件；本次也没有完成 Final 全部公开路径的独立核对。因此，这一项保留为已观察到的模型提交问题和后续诊断对象，不与当前 B 的首个阻塞捆绑成强制重构。

# 四、后续实验：Action 公开合同修复与 B 两会话完整检验

## 1. 下一轮主问题

> **在不改变合法 Action 集合、操作语义和验证标准的前提下，明确公开候选全集与选中项的对应要求后，模型能否完成原 B 任务的实际 Claim 消费、分支运算和有效 Final？**

这轮不以获得显著的提示词增益为目标，而是完成尚未闭合的 B 任务可达性检验。

因此，**无需再原样安排一轮二十四调用的 O/R 单步校准**。已有源码足以确定规则公开缺口；局部控制可以检验修复没有改变接受集合，真实完整会话则检验修复后的可执行性。

相应代价应明确：没有同期 O 组，就不对修复包的因果效应给出精确估计。可以报告新条件下的结果，不宣称两次运行之间的全部差异都由这一项造成。

## 2. 修复对象：公开当前全部候选，并明确它与“选择”不同

令当前 Request 的可用集合为：

$$
A(s)=
\{a.\mathrm{id}:a\in\mathrm{available\_actions}(s)\}.
$$

公开规则应明确：

$$
\operatorname{set}(\mathrm{candidate\_action\_ids})=A(s),
$$

$$
|\mathrm{candidate\_action\_ids}|
=
|\operatorname{set}(\mathrm{candidate\_action\_ids})|,
$$

$$
\mathrm{selected\_action\_id}\in A(s).
$$

尤其说明：

> `candidate_action_ids` 是当前接口要求的完整可用候选清单，不是“本次选中的一个候选”，也不是“模型愿意考虑的子集”。

完整清单来自**当前 Request**，不是初始 State 的列表、上一个 State 的列表，也不是仅属于某个 obligation 的候选组。

### 保持原语义，不引入额外限制

候选 ID 清单的顺序目前不参与该集合检查，所以修复后不能额外要求按某个固定顺序输出。

同时，`inputs`、`parameters`、`basis` 等其他字段有其原有的内容和顺序规则，不能因为候选清单按集合比较，就把所有数组都改成无序集合。

**不缩减 `available_actions` 来帮助模型通过，不让 Host 自动补齐遗漏 ID，也不把失败响应修正后重新评分为原响应成功。**

## 3. 在同一份 Action 说明中交代选中项对应关系，避免逐字段修补循环

本轮首错多数发生在 candidate 集合，但源码显示后续还要求所提交内容与选中 offer 对应。建议在同一份有限 Action publication 中把既有关系写清：

| 响应字段                                                | 公开来源或约束                              |
| --------------------------------------------------- | ------------------------------------ |
| `state_id`                                          | 当前 `state.id`                        |
| `candidate_action_ids`                              | 当前全部 `available_actions[].id`，完整且无重复 |
| `selected_action_id`                                | 当前可用集合中的一个成员，由模型选择                   |
| `operation / inputs / parameters`                   | 对应选中 Action 的完整内容                    |
| `obligation_id / subgoal / basis / expected_effect` | 对应同一个选中 Action，不能混用其他候选              |
| `selection_rule`                                    | 选中 Action 所允许规则中的一个成员                |
| Claim 引用                                            | 当前已接受且满足原依赖规则的 Claim                 |

这仍是**公开同一个 Action 已经执行的合同**，不是增加新的评价标准或扩大到自主规划。

公开路径和条件即可，不必生成一份填好所有字段的完整响应。模型仍负责选中 Action 并提交其内容；列出全部候选也不被解释为已经证明它逐一进行了内部推理。

建议使用新的 `public_action_contract` 身份及 Request 身份，保留现有 Submission Schema、数值合同和准入函数。Update publication 原样保留，不再次改动。

## 4. 反馈只指出当前公开约束的违例，不代写选择

对 `admission.alternative_set`，反馈可以给出：

```text
违反的公开 rule_id
当前可用 ID 的来源路径
missing_ids
extra_ids
duplicate_ids
```

这些信息都来自当前已经公开的候选集合和模型已提交内容，不涉及未来答案。

反馈不应：

* 自动选择下一 Action；
* 自动改写候选列表；
* 将一份修复后的响应补写成模型提交；
* 在模型未再次回答时继续执行。

对选中项内容不一致，只指出相应字段与当前 selected Action 的来源关系。**本次不同时修改 Final 的答案投影或 Share 路线偏好，以免多个生成条件混在一起。**

# 五、同轮准备与在线执行的最小安排

## 1. 零调用检查：使用现有真实 Request，覆盖动态集合变化

优先读取本轮 B01/B02 已持久化的 Request，选取包含二、三、四个可用候选的实际状态。它们已经存在，不需要重新执行旧 lookup 来制造测试输入。

局部检查应走原 Action 准入路径；测试接收端只能依据公开请求构造响应，不依赖旧 fixture 隐含知识。金融 `execute` 不运行。

最少检查以下边界：

| 局部控制                          | 预期结果           |
| ----------------------------- | -------------- |
| 完整候选集，选择任一合法项，内容对应            | 通过             |
| 仅声明选中项或合法子集                   | 拒绝             |
| 重复、额外、其他 State 的候选 ID         | 拒绝             |
| 仅改变候选 ID 清单顺序                 | 保持准入结果         |
| 集合正确，但 operation／basis 来自另一候选 | 拒绝             |
| accepted Claim 后可用集合变化        | 使用当前集合，不能沿用旧全集 |

动态情况下，可用集合不一定只会不断缩小：完成某个 lookup 后，新的 growth 可能变为可用。因此，不能将修复实现为“从初始四个 ID 中不断删除已执行项”。

这些是修复接线控制，不是新模型样本。**不再重做原 118 项 Update 审计、Registry 修复、来源构造或旧 D/S 商比较。**

## 2. 正式总体：只做原 B 任务两个新会话

| 项目                                         | 建议冻结值                                   |
| ------------------------------------------ | --------------------------------------- |
| Task                                       | 原 B：CDW FY2015/FY2016 分支合并任务            |
| 新会话                                        | 2 个，调用前完整登记                             |
| 初态                                         | 空 accepted Claims、无 pending、计数零、反馈 null |

| 总 Provider attempt 上限                      | **64**                                  |
| 每次 allowance                               | 107,520                                 |
| 总预留上限                                      | **6,881,280**                           |
| 自动网络重试、回退、失败替换                             | 0                                       |
| 新来源、新题型、Student/GPU                        | 0                                       |

这里沿用的是实验配置，不是对当前服务可用性或模型权重不变性的额外保证；实际响应身份仍按现有证据规则核验。

两会话从新初态开始，不接续 B01/B02 的三个或两个 lookup Claim，也不把本地控制输出作为模型前缀。

模型仍可选择任一合法执行顺序。**不为确保完成而强制指定“先收入再营业利润”的唯一脚本。**

新的完整请求逐次检查字节上限。若公开规则使某个后续状态超界，记录资源终止或准备缺口，不截断候选、Evidence 或 Claim 后继续宣称同一条件。

## 3. 为什么本次不再重复 C/S？

C/S 的完整接入已经有见证；当前缺少的是 B 的后续语义链。重复六会话会继续花费资源观察已完成对象，而不能让 B 的根本问题更清楚。

局部零调用回归足以检查新 publication 没有破坏既有单候选和 Share 多候选请求。新的在线预算集中在 B。

但如果 B 随后成功，结论应是：

> B 在新的 Action 公开条件下获得完整可达见证。

**不能把旧条件下的 C/S 四个成功与新条件下的 B 成功拼成“同一新条件六会话全部成功”。**以后测量统一任务面板时再使用统一生成条件；这不是当前修复前的额外门槛。

# 六、下一轮测量与收口规则

## 1. 主结果仍是完整任务成功，而不是 candidate 清单准确率

对两个新 B 会话：

$$
Y_r=
\mathbf1[
\text{有效 Final}
\land V_{\mathrm{QA}}
\land V_{\mathrm{trajectory}}
].
$$

两行均完整可判定时：

$$
\widehat q_{B,\mathrm{new}}=\frac{Y_1+Y_2}{2}.
$$

至少一个成功可以提供当前条件下的完整构造见证，但 **1/2 或 2/2 都不是稳定总体能力的精确估计**。

工作流通过不要求两个会话都成功；证据缺失、Host 代写或放宽验证，才会直接破坏相应实验声明。

## 2. 主要推进指标要从“接受”转向“实际消费”

下一轮至少逐会话报告：

| 推进位置            | 必须看到的真实事件                         |
| --------------- | --------------------------------- |
| Action 全候选集合准入  | 当前集合被完整声明，选中项合法                   |
| lookup Claim 接受 | 实际 Observation 经新模型 Update commit |
| 第一个非透明操作        | growth 真正执行，不只是模型在文字中提到           |
| Claim 依赖消费      | growth 使用当前 accepted lookup Claim |
| 分支合并            | 两个分支结果按原角色进入后继差值／绝对值链             |
| 完整任务            | 有效 Final、独立答案和轨迹核验                |

候选集合指标仍可记录，但不能救活没有完成的任务。例如：

```text
candidate-set 全部通过
但没有有效 Final
```

只能说明原接口瓶颈已经移除，完整任务仍未成功。

深度必须从实际执行图恢复；没有到达的部分保持未测量。模型重复提交相同 Action 或纠正 metadata，不增加语义操作深度。

## 3. 根据实际结果，只修首个新问题

| 结果                                 | 正确处理                               |
| ---------------------------------- | ---------------------------------- |
| B 至少一个完整 Qualified                 | 关闭当前 B 完整可达性缺口，停止重复同内容接入证明         |
| 全集约束通过，但后续 judgment／Claim／Final 失败 | 保留该修复，定位具体后继失败，不回头重审 Update        |
| 仍遗漏候选                              | 检查规则是否出现在真实 HTTP；区分未接线与模型在已公开条件下违例 |
| 新错误揭示另一条未公开的既有 Action 条件           | 在同一 Action 合同范围内修复，不把它解释成数学能力失败    |
| 证据完整但两个会话都失败                       | 接受有界负结果，不补样、不提高预算直到成功              |
| 有效轨迹存在，但投影未定                       | 保留资格，商测量独立标记未定，不删除纠正历史             |

若获得 Qualified B 轨迹，可复用已有导出器保存原请求—准入原响应，并做 Token 检查；这属于附加表示结果，不是本轮模型可达性的额外通过条件。

新商映射、类权重、Contribution 和 Student 训练仍不在这一轮。尤其不能因为“终于完成了深度三任务”，就跳过轨迹身份和训练／评价条件定义直接开始 VTDO 更新。
