# 二、v26.183 已经真实修复了什么

## 1. Source-derived reconstruction 不再只是对象自哈希

v26.183 的核心方向是正确的。当前链路已经包括：

```text
Operation Registry / Pattern / Renderer
→ Evidence parents
→ source-compiled Program / Plan
→ Surface / Task
→ deterministic generator replay
→ TrajectoryExecutionDescriptor
→ evaluator replay
→ Release selector replay
→ QAReleaseAuthorityBundle
```

报告明确强调：内容哈希是必要条件，但不再被视为充分条件，Loader 必须从 source-owned parents 重建对象再比较。

源码确实实现了这一点：

* Loader 重新实例化 `FinanceTaskPlugin`；
* 比较 Operation、Pattern、Renderer、Generator、Evaluator、Policy、Split 等 Contract；
* 按 Fixture index 重建 Evidence parents；
* 重新编译 Program 和 Semantic Plan；
* 重新生成每个选中表面的 Trajectory；
* 重新运行 `CandidateQualityEvaluator`；
* 重新运行 `select_diversity_aware_release()`；
* 比较完整 Selection。

这是相较 v26.182 最重要的机制进步。

## 2. Operation、Plan 和 Tool 语义明显增强

`tool_capability` 已经进入 Operation Semantic Contract、Canonical Node、节点键和 Plan 投影；Canonical Plan 也开始验证：

* Node key 唯一性；
* output node 与 topology node 配对；
* Evidence role position；
* Operation parent 存在；
* dependency acyclicity；
* topology、parameterized、semantic 和 Plan identities。

`RealizedTaskPackage` 现在还验证：

```text
task instruction == realization final_instruction
allowed_tools == evidence.search + Plan tool capabilities
answer_schema == Plan answer_schema
Program ID/hash == Plan source Program
Evidence / ProofGraph / Pattern Binding parents exact
```

因此上一轮指出的“完整重哈希后修改 allowed tools 或让 Surface 与 Task 脱离”问题，在正常对象路径上已经得到实质修复。

## 3. Trajectory 的表面父绑定明显增强

新的 `TrajectoryExecutionDescriptor` 绑定：

```text
realized_package_id
public_task_hash
EvidenceCorpus ID/hash
generation_input_hash
generator_contract_id
raw generated trajectory/hash
bound trajectory ID/hash
```

`bind_realization_execution()` 还要求传入 Trajectory 必须等于 Descriptor 中 raw output 重新绑定后的精确对象。

因此旧的：

```text
Surface A 的旧 ExecutionBinding
→ 直接替换到 Surface B
```

已经不能通过。

## 4. QualityAssessment 的内部决策关系已类型化

`QualityAssessment` 现在重新派生：

* universal/domain Gate 分区；
* fatal failures；
* Dimension 权重和为 1；
* weighted total；
* accepted/quarantined/rejected decision；
* failed-check uniqueness；
* Assessment content identity。

这修复了上一版中“修改 Decision 后重新计算 Assessment ID 即可洗成 accepted”的直接漏洞。

## 5. Release Selection v3 已能自重放

`DiversityAwareReleaseSelection` v3 嵌入：

```text
ReleasePolicy
SplitPolicy
全部 PersistedReleaseRecords
WeightAssignments
各类统计与 hard Gates
```

其 Pydantic validator 会重新运行 deterministic selector，并比较完整 payload，而不是只检查几个汇总字段。

当前正式工件中：

* 2 个 Fixture；
* 6 条 Release Record；
* 6 条被选中记录；
* 12 项攻击全部拒绝；
* Bundle、Selection、Artifact Root 与 Manifest ID 均与报告一致。



当前 `main` 也确实冻结在正式工件提交上，其父提交为报告绑定的实现提交。

所以，**当前这次固定输入的成功执行和字节结果可以保留为真实历史事实**。

# 四、P0：Archive、Manifest、Executed Tree 是三项并列断言，不是一个权威投影

报告称正式阶段：

```text
Git commit/archive
→ extracted exact tree
→ every-file manifest
→ from-snapshot execution
```

并给出了 commit、tree、archive SHA-256 和 34,374 个 Manifest 成员。

但源码实际做的是两项独立检查：

1. 对传入 Archive 文件计算 SHA-256；
2. 对另一个 `source_root` 目录逐文件比较 Manifest；
3. 仅检查 Manifest 中写着的 `source_tree_id` 等于调用者传入的字符串。

它没有：

```text
解析该 Archive
→ 从 Archive 自身派生文件集合
→ 从同一 Archive 解包到 source_root
→ 从文件模式和内容重算 Git Tree ID
→ 证明执行目录就是该 Archive 的投影
```

更直接的证据来自正式测试。测试构造了：

```text
source_tree_id = "a" * 40
Archive bytes = "archive fixture\n"
Source root = 只有一个完全无关的 tracked.txt
Manifest = 对该 tracked.txt 的描述
```

然后 `run_release_authority_preflight()` 仍然通过。

这证明当前 Contract 接受：

$$
\text{Archive A}
\quad+\quad
\text{Unrelated Root B}
\quad+\quad
\text{Arbitrary Tree-ID String C}
$$

只要三者分别内部自洽。

### 科学解释

当前正式运行很可能确实使用了正确的 `794a546...` Archive 和对应 Extracted Root；GitHub 也确认该 commit 的实际 Tree 是 `c4a99bd...`。

因此当前历史运行结果可以保留。

但是不能进一步声称：

> v26.183 的正式接口已经形式化保证 Archive、Git Tree、Manifest 和 Executed Root 是同一个源对象。

准确状态应为：

```text
current formal invocation:
    observed source identities mutually consistent

general source-projection contract:
    not closed
```

# 五、P0：Report 和旁路 Catalog 未形成顶层权威 Bundle

这是本轮最重要的新代码缺口。

## 1. Artifact Root 实际只覆盖六个文件

正式目录有九个文件，但 `artifact_manifest.json` 只列入并哈希了：

```text
attack_controls.json
direct_source_manifest.json
qa_release_authority_bundle.json
release_records.jsonl
release_selection.json
source_snapshot_manifest.json
```

没有列入：

```text
artifact_manifest.json
report.json
report.md
```

Manifest 自身不进入自己的 Root 是合理的 Merkle 设计；但这要求 `report.json` 成为一个具有外部可信身份的顶层锚。当前没有做到这一点。

## 2. Loader 只验证 Report 的两个字段

目录 Loader 只要求：

```text
report.artifact_root == recomputed root
report.artifact_manifest_hash == recomputed manifest hash
```

然后解析并重建 `qa_release_authority_bundle.json`。它没有验证 Report 中的：

```text
status
authority_bundle_id
release_selection_id
fixture_count
release_record_count
selected_record_count
frozen_task_type_count
frozen_renderer_profile_count
fully_rehashed_attack_count
fully_rehashed_attack_rejection_count
provider_calls
unrelated_exception_counted
```

是否与真实 Bundle、Selection 和 Attack Catalog 一致。

因此可以构造一个不需要修改 Artifact Root 的直接反例：

```text
status                    "passed" → "failed" 或任意字符串
provider_calls            0 → 999
fully_rehashed_attack_count 12 → 1
authority_bundle_id       → 任意值
release_selection_id      → 任意值
```

只要保留原来的：

```text
artifact_root
artifact_manifest_hash
source identity fields
```

当前 Loader 就会返回被修改的 Report。

`report.md` 甚至只检查“文件存在”，不检查字节或内容。

## 3. Sidecar Catalog 只做字节检查，不做语义父绑定

Loader 不解析或交叉比较：

```text
release_selection.json
release_records.jsonl
attack_controls.json
source_snapshot_manifest.json
```

与 Bundle 内嵌对象是否完全相同。

因此可以进一步构造完整重哈希攻击：

```text
修改 release_records.jsonl
修改 release_selection.json
修改 attack_controls.json
修改 source_snapshot_manifest.json
重新计算每个文件 SHA-256
重新计算 Artifact Root
重新计算 Artifact Manifest Hash
更新 Report 的两个 Root 字段
```

只要保持 `qa_release_authority_bundle.json` 不变，当前 Loader 仍会成功，因为它只对 Bundle 执行语义重建。

v26.183 注册的第 12 项攻击只覆盖：

```text
修改 Catalog 和 Manifest Root
但保持旧 Report Root
```



它没有覆盖真正的：

```text
Catalog + Manifest + Report 一起完整重哈希
```

攻击。

### 精确结论

当前正式九文件目录在 Git 中已经冻结，因此**当前历史字节集可以保留**。

但当前 Loader 只证明：

> 给定这个当前 Report Root，六个被列入 Manifest 的文件没有发生 stale-byte 修改。

它没有证明：

> Report、Markdown、Bundle、Selection、Records、Attacks 和 Source Manifest 共同组成一个不可替换的顶层 Release Authority Envelope。

# 六、P0：没有冻结 Exact Release Population

`build_qa_release_authority_bundle()` 默认使用：

```python
fixture_indexes = (1, 2)
```

所以当前正式结果确实是两个 Fixture、六条 Record。

但 `QAReleaseAuthorityBundle` 的 Schema 只要求：

```text
fixture_inputs 非空
fixture_input_id 唯一
fixture_index 唯一
```

Loader 随后遍历持久化 Bundle 中**调用者提供的那些 Fixture indexes**，分别从 Source 重建。它没有要求：

```text
fixture index set == {1, 2}
exact task/binding set equality
pre-outcome ReleasePopulationManifest
missing / duplicate / extra population = 0
```

因此从当前 validator 条件可以构造：

```python
build_qa_release_authority_bundle(
    ...,
    fixture_indexes=(1,),
)
```

重新计算 Selection 和 Bundle 后，Loader 会把它视为一个合法 source-derived Authority Bundle。

这作为“通用 Bundle constructor”并不错误；问题在于它不能承担“精确 Release population 已预先冻结”的科学主张。

当前真正冻结的是：

```text
某个 Bundle ID 当前恰好包含两个 Fixture
```

而不是：

```text
生产 Loader 只接受预授权的 exact two-Fixture population
```

### 必须增加

```text
QAReleasePopulationManifest
  population_id
  exact fixture_input_ids
  exact semantic_instance_ids
  exact task/binding identities
  source selection contract
  missing/duplicate/extra policy
  pre-outcome authorization parent
```

Loader 必须由外部授权获得 `expected_population_id`，不能从待验证 Bundle 自己读取。

# 七、P1：12/12 是当前事实，但攻击准入合同并非精确

当前正式 `attack_controls.json` 确实记录：

```text
12 个 counted fully-rehashed controls
12 个 target_validator_reached
12 个 rejected
unrelated RuntimeError not counted
```

这一历史观察可以保留。

但是正式 preflight 的准入条件是：

```python
if len(counted) < 11 or any(not item.rejected for item in counted):
    fail
```

不是：

```python
exact attack ID set == frozen 12 IDs
len(counted) == 12
missing / duplicate / extra == 0
```

这意味着未来少掉一项攻击，只剩 11 项，preflight 本身仍可通过。测试单独断言了 `len(counted) == 12`，所以当前提交没有发生该问题，但正式 Builder 的非补偿 Gate 本身仍不精确。

## rejection stage 也不是独立测量

`_capture()` 对 `QAReleaseAuthorityError` 会读取实际 `exc.stage`。

但对普通：

```text
ValidationError
ValueError
```

它直接执行：

```python
actual_stage = expected_stage
```

因此攻击工件中记录的：

```text
actual_stage = canonical_plan
actual_stage = surface_realization
actual_stage = quality_assessment
actual_stage = release_selection
```

并不是 Runtime 实际产生的 Stage，而是测试预先填入的 Expected Stage。

当前 Exception type 和 reason token 大多足以说明目标 validator 很可能被触达，但不能据此声称：

> rejection stage 已被独立测量。

这比旧版“任意 Exception 都算成功”已经好很多，但仍应改为每个权威入口都抛出：

```text
QAReleaseAuthorityError(
    reason_code=...,
    stage=...,
    target_validator_reached=True,
)
```

QAReleaseAuthorityAuthorization

正式 Builder 必须读取实际审计字节，而不是只在文档里写一个哈希。

## 2. Source projection

强制要求：

```text
exact Git commit
→ internally generated Git archive
→ mandatory archive path
→ internally extracted tree
→ manifest derived from extracted tree
→ recomputed Git tree identity
→ execution only from that tree
```

不能让调用者分别提供彼此无关的：

```text
tree ID
archive
source root
manifest
```

## 3. Exact Release Population Manifest

冻结：

```text
exact fixture/task/binding set
exact SemanticInstance set
exact population ID
missing / duplicate / extra = 0
selection provenance
```

Loader 必须接收外部可信的 `expected_population_id`。

## 4. 顶层 Release Authority Envelope

新增一个唯一顶层对象：

```text
QAReleaseAuthorityEnvelope
  Authorization

  PopulationManifest
  QAReleaseAuthorityBundle
  ReleaseSelection
  ReleaseRecords
  AttackAudit
  ArtifactManifest
  Report
  envelope_id
```

`report.json` 必须内容寻址，并逐字段从上述对象重建。

## 5. 所有 Catalog 必须语义交叉验证

Loader 必须解析并要求：

```text
release_selection.json
    == Bundle.embedded release_selection

release_records.jsonl
    == Selection.embedded release_records

attack_controls.json
    == exact frozen attack registry and results

source_snapshot_manifest.json
    == SourceProjection manifest
```

不能只做文件 SHA-256 检查。

## 6. 精确攻击集合

正式条件应改为：

```text
exact attack IDs == frozen 12-ID set
count == 12
missing / duplicate / extra == 0
all target validators actually reached
all typed exception type/stage/reason exact
```

并新增以下攻击：

```text
Report-only status/count/ID mutation
Report.md mutation
all Catalogs + Manifest + Report jointly rehashed
one Fixture removed with Bundle and Report rehashed
one extra valid Fixture added
external audit omitted or replaced
unrelated Archive paired with valid source Root
arbitrary tree ID paired with valid Manifest
one registered attack silently omitted
wrong validator emits same exception phrase
actual Pilot evaluator/profile substituted for fixture evaluator
```

## 7. Runtime 环境身份

至少冻结：

```text
Python version
Pydantic version
dependency lock hash
OS/kernel/libc
locale/timezone
container or environment root
```
