# 本轮审计与后续实验方案

**本轮可以接受为 `PASS_AS_SCOPED`：三个真实来源的参数化、十二会话执行和完整失败记录成立；但没有获得跨来源的完整有效轨迹，也没有获得双支持机制的迁移见证。**

当前首个需要修复的问题已经明确落在 **Final 的公开输出要求与实际验证标准没有完整对应**。这不是重新打开 Action、Update 或商映射问题，也不能据此否定此前单题上的双支持结果。

**下一轮建议：保持计算、来源和验证标准不变，补齐 Final 的公开规则与针对性反馈，再对原三个任务各运行两个全新完整会话，共六个。**不补写历史 Final，不恢复旧失败会话，不增加来源，也不进入训练。

本次完整阅读了报告，核对了冻结提交 `f697d953f749098eaecbd619becef35a61c39f6b` 中的来源绑定、参数化 adapter、公开协议、Final 验证及反馈代码，并抽查了一条报告引用的原始 Final 响应；另外独立复算了三个答案和主要计数。**没有重跑全部测试或重建正式实验目录。**

## 一、当前声明与实际完成情况

本轮要检验的是：

> 原先在一道题上成立的“直接使用披露总额”和“由分项重建总额后实际使用”，能否在其他真实主体和期间，通过同一条参数化链路得到完整有效行为。

这增加的是**同一种问题机制的实例广度**，不是新增三种题型，也不是增加推理深度。报告对此限定正确。

### 1. 十二会话全部完成，但完整成功为零

| 任务                |     中性组 |    软引导组 |    完整成功率 | 已发生的计算前缀             |
| ----------------- | ------: | ------: | -------: | -------------------- |
| T01：UNP 2016 收入占比 |     0/2 |     0/2 |      0/4 | 披露与重建两种分母均实际使用过      |
| T02：JPM 2014 收入占比 |     0/2 |     0/2 |      0/4 | 披露与重建两种分母均实际使用过      |
| T03：JPM 2015 收入占比 |     0/2 |     0/2 |      0/4 | 披露与重建两种分母均实际使用过      |
| **合计**            | **0/6** | **0/6** | **0/12** | **十二会话均已得到并接受百分比结果** |

十二个会话都是证据完整的提交预算耗尽，没有未知、未启动或被替换的会话。因此：

$$
\widehat q_{\mathrm{panel}}=0/12
$$

应当保留，不能因为最后的数值已经算出，就把这些会话重新计为成功。

反过来，**也不能把这次结果概括为“模型没有完成财务计算”**。实际失败发生在计算结果已经接受之后的最终提交阶段。

### 2. 计算链已经走通，完整回答没有走通

本轮实际发生：

$$
33\text{ 次操作}
+
33\text{ 次接受结果}
+
309\text{ 次 Final 提交}
+
9\text{ 次未准入 Action 提案}
=384.
$$

309 次 Final 中，308 次被 Final QA 拒绝，另一次因当前 State ID 不一致，在更早阶段被拒绝。不能将后者再算成执行过 Final QA。

人工理解的实际过程是：

> **读取并选择收入依据 → 执行求和或比率计算 → 接受中间结果 → 转成百分比并接受 → 反复提交不符合要求的最终答案 → 预算耗尽。**

所以，当前应区分：

* **实际计算与结果接受：已经发生。**
* **完整有效回答：没有发生。**
* **有效轨迹的商分布：没有对象可测量。**

本轮没有 Qualified 轨迹，因此成功条件下的 \(\pi\) 为 null。它不是“有十二条有效轨迹，只是新纠正历史无法映射”。

## 二、实现核对与直接反例检查

### 1. 来源参数化是真实实现，不只是替换旧题的数字

新 `BoundShareTaskAdapter` 接受独立的来源绑定，使用“目标组成项、另一组成项、披露总额、组成关系”四种角色。银行的 Noninterest revenue 没有被强行标成 freight；输入 Claim 也必须属于当前任务、来源和语义合同。

来源代码根据实际列头选期，保留原行名和上下文，并检查同一合并范围。它没有通过“总额减一项”生成另一项，也没有根据旧 QA 答案选择题目。

本次按报告数值独立复算：

| 任务  | 分项求和                     | 占比计算                       |         六位小数结果 |
| --- | ------------------------ | -------------------------- | -------------: |
| T01 | \(18,601+1,340=19,941\)  | \(18,601/19,941\times100\) | **93.280177%** |
| T02 | \(50,571+43,634=94,205\) | \(50,571/94,205\times100\) | **53.681864%** |
| T03 | \(50,033+43,510=93,543\) | \(50,033/93,543\times100\) | **53.486632%** |

这些是对报告输入的算术核对，**不单独证明组成关系合法，也不替代原始执行证据**。组成关系仍依赖报告所绑定的原表结构与上下文。

因此，上一轮提出的“Share 仍固定加载旧 UNP 2015 来源”这一实现限制，**在当前三来源入口范围内已经得到修复**。不能因为模型最终回答失败，就退回“参数化完全没有落实”的判断。

### 2. Final 的验证要求比公开结果 Schema 更具体

当前公开 `Final` Schema 中：

```text
result：一个任意字段的对象
citations：字符串列表
```

`result` 没有进一步声明 value 的类型、unit 的固定值，或允许哪些字段。外层禁止额外字段，并不意味着这个内层字典也只能包含两个字段。

但实际验证要求是：

| 项目                | 实际要求                              |
| ----------------- | --------------------------------- |
| `answer_claim_id` | 必须是当前已经接受的百分比结果 Claim             |
| `result`          | 必须恰好包含 `value` 和 `unit`           |
| `value`           | 按既定规则量化后的**字符串**                  |
| `unit`            | 必须为 `"percent"`                   |
| `citations`       | 无重复，且集合精确等于所选答案 Claim 的实际 lineage |
| 数值                | 还要与独立来源计算一致                       |

这些条件由 `public_share_answer()` 和 `BoundShareTaskAdapter.verify_final()` 实际执行。

这里需要作一个准确区分：

**六位小数要求已经公开。**题目和数值合同明确写了六位小数、舍入方式和量化单位。

**但完整的结果对象边界没有公开充分。**“必须是字符串”“只能有 value/unit”“不能把 Claim 的 metadata 一并放入 result”“引用必须精确对应实际答案 lineage”等要求，没有在模型可见的 Final 专用规则中完整表达。当前 Request 只增加了 Action、Update 的公开合同，没有对应的 Final 合同。

因此，不能把所有错误都归于规则缺失；模型确实也违反了已经公开的六位小数要求。但**已有的公开缺口是真实存在的，不能用“原则上让它遵守 Schema”替代具体说明**。

### 3. 原始响应提供了一个直接、具体的例子

抽查 T01_N01 第十步的原始 Final，可以看到：

```text
value = "93.280177"
unit  = "percent"
```

数值已经正确，引用也与实际 lineage 一致；但 result 还带有 metric、period、subject，因此仍会被当前严格对象比较拒绝。原始响应与报告记载一致。 

这说明至少这一条失败不能被归为“不会计算收入占比”。它是：

> **已经得到正确答案，但最终提交的表示范围不符合验证器要求。**

另一方面，本轮也存在完整未量化字符串、JSON 数值而非字符串、引用遗漏或替换等不同错误。278 条 result 有额外字段、53 条缺字段，这两项可以重叠；不能把它们相加当作互斥失败分类。

### 4. Final 反馈没有指出具体违反了哪项要求

当前反馈代码对非 Action 转交 Update 反馈，而 Update 反馈发现提交类型是 Final 后，直接返回：

```text
code = admission.final_qa
admitted = false
```

没有进一步指出是结果字段、类型、量化还是引用集合不符。

因此，本轮有两个相关但不同的问题：

**首次提交前，Final 的完整条件没有充分公开；被拒绝后，反馈又不足以区分具体违例。**

这能解释为什么应当修复 Final 接口，但**尚未证明修复后就一定成功，更没有证明它解释了全部 309 次提交**。效果仍须由新实验检验。

**Blocking defect：Final 的公开输出合同不完整。**

本轮正向候选、Token 记录和完整包均为零。**这不是长度政策失败，也不是“零条超长，所以全量表示通过”**，而是根本没有符合导出条件的完整有效轨迹。

# 四、后续实验：Final 公开规则修复与六个完整会话

## 1. 唯一主问题

> **保持任务、实际计算和正确性标准不变，完整公开最终回答的要求后，模型能否从初态完成这些跨来源任务，并提交有效 Final？**

这次不放宽验证器，也不让 Host 自动整理答案。

尤其不做以下替换：

> 模型随便返回一个数值 → Host 自动补 unit、删除 metadata、量化数值、修正引用 → 计为模型成功。

那会改变模型责任，不能用来证明当前公开协议已经可被模型遵守。

## 2. 一次补齐 Final 的完整要求

建议把 Final 的公开说明整理为下面这张规则表，并由实际 Request 提供：

| 模型需要决定或填写什么 | 应明确告诉模型的要求                                                           |
| ----------- | -------------------------------------------------------------------- |
| 使用哪个答案      | 从当前允许的已接受答案 Claim 中选择，不引用 Observation 或任意中间结果                        |
| 最终数值如何表示    | 使用该 Claim 的数值，按当前任务规定舍入到六位小数，作为字符串提交                                 |
| result 包含什么 | 只包含 `value`、`unit`；不要复制 metric、period、subject、definition 等 Claim 元数据 |
| 单位是什么       | `unit` 为 `"percent"`，value 中不附加百分号                                   |
| 引用什么        | 精确引用所选答案 Claim 实际使用的 Evidence；不加入仅仅看过但未使用的来源                         |
| 当前状态是什么     | 使用本次 Request 的 State ID，不自行改写或沿用其他轮次 ID                              |

这里最需要让模型理解的是：

$$
\boxed{\text{Update 接受完整原精度命题；Final 输出规定格式的答案投影。}}
$$

两个阶段的要求不同。**不能把“Update 必须完整复制命题”延伸成“Final 也应复制全部命题字段”。**

规则应提供字段类型、来源路径和转换要求，不提供预先算好的三道题答案，也不提供填好 ID 的完整响应。模型仍须选择答案、完成输出及支持声明。

### 保持原验证标准

当前正确的字符串、数值、单位和引用仍然正确；原来错误的输入不能因修复而变成合法。可以增加公开的结果子 Schema 和说明，但不能修改：

* 财务计算公式与舍入规则；
* 实际答案 Claim 的选择条件；
* Final 与独立来源计算的一致性；
* 引用必须对应真实支持的要求。

新公开规则进入 Request 后，应同步进入只读验证时的 Request 重建，避免执行器和验证器使用两种不同呈现。历史 Request、响应和资格不改写。

## 3. 反馈应指出错误类别，但不生成替代答案

建议 Final 被拒绝时给出有限、可操作的反馈：

| 错误             | 反馈示例的含义                                    |
| -------------- | ------------------------------------------ |
| result 多字段／缺字段 | 指出多了或缺了哪些字段                                |
| value 类型不符     | 明确要求字符串，而不是 JSON number                    |
| 未按规定量化         | 指明当前量化与舍入规则，不替模型填最终 value                  |
| unit 不符        | 指明允许的单位形式                                  |
| citations 不符   | 指出 missing／extra，相对于所选答案 Claim 的真实 lineage |
| State ID 不符    | 指向当前 Request 的 State ID                    |

这些反馈只依赖当前公开信息和本次提交，不涉及未来答案，也不改写原响应。模型必须通过**下一次新的提交**作出修正。

## 六、下一轮测量与收口方式

### 1. 主结果看完整任务，而不是只看 Final 字段正确率

每个任务两个会话，证据完整可判定时：

$$
\widehat q_i=\frac{\text{该任务完整 Qualified 会话数}}2.
$$

三任务的面板成功率按原等任务权重汇总。旧十二会话、历史 Share 和本地构造控制均不进入新分母。

同时记录三个推进位置：

| 位置            | 需要的实际证据                        |
| ------------- | ------------------------------ |
| 计算结果已接受       | percent Claim 已由真实模型 Update 接受 |
| 首次 Final 是否合格 | 不是把后续修正成功写成首次成功                |
| 最终任务是否完成      | 有效 Final，且答案与真实支持都通过独立验证       |

Final 的具体错误按字段记录，但**这些局部指标不能替代完整成功**。某会话的结果格式全部正确、引用却一直错误，仍是完整任务失败。

### 2. 双支持作为独立科学结果，不预分配类别

如果某任务的新两个会话分别完成有效 D 与有效 R，并有当前规则支持的确定语义差异，可以建立该任务的双支持见证。

如果两个都成功但都使用 D，只能说：

> 修复后该任务已有完整模型可达见证，本批样本尚未见证双支持。

不能按 N/E 标签直接赋类，也不能补采样直到两条路线都出现。

若有效轨迹存在但新纠正过程超出当前投影域，保留其资格与未定测量状态，不删除困难样本。**Final 修复通过、完整任务成功、双支持分离和全量分布闭合，是不同结论。**

### 3. 正向表示只处理新获得的有效轨迹

有 Qualified 会话时，复用既有原请求—准入原响应导出和 32,768 表示政策，保留新增 Final 说明及真实反馈。

没有 Qualified 会话时，导出仍为空，不重新分词失败前缀，也不以“没有超长行”宣称表示通过。

当前不重新实施类权重、Contribution 或 Student 对比。因为本轮首先要获得的是**跨来源完整行为**，而不是从尚未成立的有效集合中进行分布优化。

### 4. 不同结果对应的后续判断

| 实际结果                   | 正确处理                        |
| ---------------------- | --------------------------- |
| 三个任务均有完整成功             | 关闭当前跨来源完整执行中的 Final 接入问题    |
