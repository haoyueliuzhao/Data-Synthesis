# 本轮审计与后续实验方案

**本轮应接受为“执行证据完整、原始监督导出成立的有界实验结果”，但不能继续认定模型侧公开协议已经充分说明。当前存在一个已经定位、必须在下一次相关模型实验前修复的缺口：Update 的实际准入规则，没有完整进入模型可见请求。**

这两个判断同时成立：

> **十二会话的执行与 \(1/12\) 结果有效，应冻结保留；公开协议的充分性没有闭合，不能把主要失败直接归因于模型数学能力或任务深度。**

后续建议是：**保持验证标准不变，修复 Update 的条件语义公开，然后使用十二个既有观察态做一次二十四调用的单步配对校准。**先检验修复是否改善完整 Update 提交，不再直接重复十二个长会话，也不进入来源扩张、商分布优化或 Student 训练。

本次完整阅读了新报告，并通过 GitHub 读取了实验冻结提交 `bbc713c6ee1c6c3ef6c0ce57dd9c67c4bbc13955` 中的 `protocol.py`、`runtime.py` 和 `callbacks.py`，核对了报告所述接口差异；另外独立核对了提交、拒绝、用量和 Token 数量。**没有重跑仓库测试、读取全部原始 HTTP 工件或重建正式目录。**下文分别区分实际源码核对、报告中的执行证据和新方案。

## 一、本轮声明与实际结果：执行完成，但代表任务的模型闭环未普遍成立

本轮检验的是：在给定公开计划、合法候选与验证合同的条件下，模型能否通过统一 Runtime 完成 C、B、S 三个任务，并产生可独立核验、可原样导出的公开轨迹。它不是自主规划或 VTDO 效用实验。

实际结果如下：

| 任务        |     完整成功 | 完整已知失败 |   实际请求数 | 成功轨迹的解释范围   |
| --------- | -------: | -----: | ------: | ----------- |
| C：注册跨指标比较 |      1/4 |      3 |     118 | 仅 C03 完成    |
| B：分支合并    |      0/4 |      4 |     128 | 未取得完整深度三轨迹  |
| S：部分／整体占比 |      0/4 |      4 |     128 | 未取得完整有效支持路线 |
| **合计**    | **1/12** | **11** | **374** | 一个完整成功会话    |

十二个会话均已启动，未知和未启动数量均为零；十一个失败均有完整的 `submission_budget_exhausted` 证据，不是 HTTP 错误、超时或丢失记录。

因此：

$$
\widehat q_C=\frac14,\qquad
\widehat q_B=0,\qquad
\widehat q_S=0,
$$

$$
\widehat q_{\mathrm{pilot}}
=\frac13\left(\frac14+0+0\right)
=\frac1{12}.
$$

**这个比例应当保留。**公开呈现存在缺口，不会使已经发生的系统端到端结果失去定义；它限制的是结果能被解释成什么能力，而不是允许删掉失败会话或将分母改成一。

同样，失败会话没有有效 Final，因此 Final 条件 QA 为 null；但“完整 Qualified 会话”事件仍然可以判为 false。这两项没有矛盾。

### 数量核对没有发现内部冲突

本次独立复算得到：

$$
11\times32+22=374.
$$

也就是说，**C03 不是三次提交直接完成，而是用了二十二次提交，最终只有三条被准入。**

全部提交按声明类型分为：

$$
53\text{ Action}+320\text{ Update}+1\text{ Final}=374,
$$

实际准入：

$$
12\text{ Action}+1\text{ Update}+1\text{ Final}=14,
$$

所以未准入数为：

$$
374-14=360.
$$

这些与报告一致。

但这些统计的重点不是“调用数很多”，而是：**十二个会话各自都只实际执行了一个 Action，之后几乎全部停在首次 Observation 的接受边界。**

## 二、直接源码核对：公开规则与实际准入之间存在确定缺口

### 1. `protocol.py` 只声明了宽泛类型

当前 `Update` 中的字段是：

```python
disposition: Literal["accept", "reject"]
proposed_claim: dict[str, Any] | None
```

这里没有表达：

* accept 时必须提交什么层级的对象；
* reject 时必须为 null；
* proposed Claim 必须与哪一个现有对象相等；
* 这种相等采用什么规则。

`contract()` 虽然另有 `callback_submits_complete_claim=True`，但这本身也没有完整说明对象边界和相等条件。

**单独使用宽泛 Schema 不一定就是缺陷。**很多语义约束本来需要由运行时检查。这里的问题是：这条必要的接口约束也没有通过其他公开说明完整传给模型。

### 2. `runtime.py` 执行的是整对象规范化相等

实际准入条件为：

```python
canonical_json_bytes(submitted["proposed_claim"])
==
canonical_json_bytes(
    self.pending["proposition"] if accepted else None
)
```

也就是说，模型要提交的是**整个 pending Observation 的 proposition**，不是其中的数值、不是自行构造的扁平财务 Claim，也不是完整 Observation 外壳或 Host 将来创建的 accepted Claim。reject 则必须提交 null。

实际 `request()` 传出了 `response_schemas` 和 `update_transition_options`，但没有传出上述条件语义。报告对实际 HTTP 请求的检查也确认了这一点：完整 proposition 已经可见，缺少的是如何提交它的明确合同，而不是缺少计算数值。

### 3. fixture 已经在代码里知道正确答案结构

`callbacks.py::update_response()` 直接执行：

```python
copy.deepcopy(observation["proposition"])
```

并预先知道 assessment 的关系、lineage 和 obligation 如何填写。

因此，此前的离线控制能够证明：

> 按这套已知编码规则构造的提交，可以通过 Runtime。

它不能进一步证明：

> 一个只阅读当前公开请求的模型，已经获得了同样完整的编码规则。

这并不推翻此前 fixture 的执行结果，但**确实推翻“fixture 通过足以证明模型侧协议说明充分”的推论**。

## 三、失败定位：已经证明“规则公开有缺口”，尚未证明它解释全部失败

### 1. 不是 JSON 生成失败

本轮 360 次未准入的首个错误分区是：

| 首个准入错误                                   |  次数 |
| ---------------------------------------- | --: |
| `admission.exact_observation_acceptance` | 319 |
| `admission.alternative_set`              |  18 |
| `admission.public_judgment`              |  21 |
| `admission.selected_action_content`      |   2 |
| JSON／结构 Schema 错误                        |   0 |

完整命题接受占：

$$
\frac{319}{360}\approx88.61\%
$$

的未准入事件。Update 的实际准入比例为：

$$
\frac1{320}.
$$

这些是**重复提交事件的统计**，不能当作 320 个独立任务或 319 种独立缺陷。每份 Receipt 又只记录首先遇到的错误，因此不能推断其余字段都已经正确。

这意味着修复不能只补一句“不要返回 null”，然后等下一轮再发现 assessment 或对象包装问题。**应一次性公开当前 Update 的完整条件合同，但仍限定在这个接口对象内。**

### 2. 报告中的具体响应与该定位吻合

已经保存的例子包括：

* C01 的 accept 搭配 `proposed_claim=null`；
* B01 提交与 lookup 数值一致的 `12988.7`，却采用自建扁平 Claim，缺少完整 proposition 的包装；
* S01 提交 `21813` 及相应来源，但采用不同对象结构。

这些提交都在整对象相等检查处失败。

所以可以确定：

**本轮有真实的模型侧协议呈现缺口，也有与该缺口相符的实际违例。**

目前还不能确定：

**只要公开这条规则，所有 Update 都会通过，或十二个完整任务都会成功。**

另外 41 次 Action 准入拒绝不由 Update 缺口解释；即使修复 Update，后续更深的 Claim 消费、Final 和其他判断仍可能出现新错误。下一实验需要检验，而不是预先承诺。

### 3. C03 成功不消除缺口

C03 最终提交了一次符合规则的 Update，证明当前条件下合法输出并非绝对不可产生。但它此前有十七次 Update 拒绝，以及两次 Action 拒绝。

**“偶尔能够产生正确格式”与“接口规则已完整公开”是不同命题。**同样，失败很多也不构成对模型计算能力的普遍否定。

## 四、广度、深度和训练表示：本轮证据只支持到哪里？

### 1. 深度三尚未到达，不能归因为深度三太难

四个 B 会话都停在第一个 lookup 的 pending Observation，没有继续进入增长率、差值和绝对值运算链。其实际前缀语义操作深度为零，而不是三。 

因此，本轮不能回答“模型能否完成三层语义操作依赖”，更不能比较“深度一与深度三的能力差距”。**共同的早期接口阻塞，使更深阶段尚未得到检验。**

### 2. Share 有初始选择，没有完整依据路线见证

S01、S02、S04 实际执行了 `relation_sum`，S03 执行了 `share_ratio`；但是四者均没有 accepted Claim 或 Final。

可以记录两种初始行动选择，不能记录两条有效解决行为，更不能建立新的两个商类。

### 3. 广度表有价值，但成功见证仅覆盖一个选定任务

十一类的注册／来源状态没有因为本轮改变：三类本轮执行、五类有来源但未测量、三类当前来源缺失。三个被选任务中仅一个获得完整成功见证。

所以，本轮不是“广度没有任何进展”，而是：

> 真实模型执行已经覆盖三个代表任务的入口；完整有效行为目前只在其中一个任务上得到见证。

### 4. C03 的三条 Token 表示成立，但不是新的类条件训练集

实际导出 C03 的 Action、accept Update、Final 三条原始响应；它们分别对应零起始 turn 2、20、21，保留真实请求中的反馈，没有删除历史拒绝。目标 Token 总数为：

$$
694+763+407=1864,
$$

三个完整序列总长度为：

$$
14574+15291+14194=44059.
$$

与报告一致，均未超过 24,576 上限。

但当前没有同任务合格轨迹对，C03 又包含未准入纠正历史，投影保持未定。**只有一个 Qualified 会话，不等于已经测得一个商类；三条监督行也不等于三个有效轨迹。**

本轮成立的是 C03 上的原请求—原响应—Token 表示链。B/S 的正向表示、新的 \(M_\psi\)、类权重及 Student 效用均未建立。

**本轮应收口，不重复跑当前十二会话；下一步只修复这个明确接口对象，并测量修复效果。**

# 六、后续实验：Update 条件公开修复与单步配对校准

建议阶段暂名：

```text
finance_qa_vnext_update_public_contract_repair_and_paired_calibration
```

这是新方案，不是已实施修复，也不是本答复正在执行的 Provider 调用。

## 1. 主问题与不变项

主问题是：

> **在同一实际观察态、同一接受标准和同一模型条件下，明确公开 Update 的完整条件合同，能否提高一次提交即完成合法完整接受的比例？**

固定：

```text
Task、Evidence、Operation、实际 pending Observation
已接受 Claim、当前 State、数值和 lineage
完整命题相等标准
assessment 和 transition 的合法性要求
模型配置、采样参数、单次输出预算
```

只改变**公开说明的完整性**，不放宽实际接受集合。

这一点很重要：现在不是检验“把严格接口改成宽松接口能否提高成功率”，也不是把完整 Claim 提交改成一个 `accept=true`。那是另一种模型责任设计，应以后单独讨论。

---

## 2. 修复内容：一次公开完整 Update 合同

### 2.1 明确 proposed Claim 的对象边界

公开说明至少应表达：

| 条件                   | 必须公开的规则                                                      |
| -------------------- | ------------------------------------------------------------ |
| `disposition=accept` | `proposed_claim` 为整个 `state.pending_observation.proposition` |
| `disposition=reject` | `proposed_claim=null`                                        |
| 相等方式                 | 使用现有 canonical JSON 内容比较，不要求复刻空白或键顺序                         |
| 不允许的替代               | 单个数值、仅内部 output、自建扁平 Claim、完整 Observation 外壳                 |
| 内容保持                 | 不舍入、不改定义、不省略 lineage／operation／contract 等原 proposition 字段    |

**不要把“整对象相等”解释成原始字符串逐字相等。**键顺序和空白可以不同，但不能增加类型转换、数值容差或字段省略。

这些内容来自当前已经发生的 Observation，不是未来答案或私有 Oracle。公开其正确引用方式，不构成让 Host 替模型计算未来步骤。

### 2.2 同时公开 assessment 与 transition 的映射

源码在 proposed Claim 之后，还检查 assessment 的 relation、Observation 引用、Evidence lineage、履行义务及 transition 信息。当前首错统计并未证明这些后续字段都正确。

因此，本次应一并公开：

```text
accept/reject 各自的 assessment.relation
observation_refs 的来源
evidence_refs 应对应当前 proposition 的完整 lineage
fulfills_obligation 的条件关系
remaining_uncertainty_refs 的来源
newly_enabled_obligation_ids 的来源
next_subgoal 的允许集合
```

可以提供字段到公开 Request 路径的映射，不需要生成一份已填好、等待模型原样回显的完整响应。模型仍要作出并提交选择；Host 不在收到响应后补字段或替换内容。

这不是增加新的审计范围，而是把**同一个 Update 接口原来已经执行的规则一次说明完整**。

### 2.3 让错误反馈可理解，但不改变拒绝结果

建议失败反馈保留原错误码，并补充有限诊断：

```text
违反哪条公开规则
哪个字段路径不匹配
对应的公开来源路径
下一次提交需要满足的条件
```

例如：

```text
proposed_claim 必须对应
state.pending_observation.proposition；
当前对象缺少该 proposition 的外层字段。
```

反馈只能依据当前已公开信息和当前提交生成，不引用未来 Oracle，不改写旧响应，也不自动产生新的模型提交。

**请求说明和反馈应引用同一组有版本的规则，避免以后再次出现 renderer、fixture、Runtime 三处各自理解一种协议。**

---

## 3. 零 Provider 检查：检验“只读公开请求就能正确编码”

本次准备检查不要再次只调用旧 `update_response()`。它已经内置了正确构造知识，无法检验修复是否真正公开。

建议使用一个隔离的测试接收端：只读取新公开请求中的条件与路径映射，不导入旧 callback helper、不读取 Runtime 私有字段，再构造测试用 accept／reject。

检查以下有限对象即可：

| 控制                                           | 需要确认                                        |
| -------------------------------------------- | ------------------------------------------- |
| 根据公开规则构造完整 accept                            | 通过同一个冻结准入器                                  |
| 根据公开规则构造 reject                              | 为 null，assessment 和 transition 一致；不产生 Claim |
| null accept、扁平 numeric Claim、Observation 外壳  | 仍被拒绝                                        |
| 完整对象中改 value、lineage、operation contract 或父引用 | 仍被拒绝                                        |
| 仅改变键顺序和空白                                    | 不因表面形式被误拒绝                                  |
| 新反馈和公开规则                                     | 指向同一条件，不通过反馈补写提交                            |

用 C、B 的 lookup、S 的 sum／ratio 四种现有 proposition 形态覆盖即可。无需新增金融题、构造复杂修订或重跑旧 Registry／P/Q 实验。

**这一步证明的是公开合同可被正确实现，不是模型会使用它。**模型效果由下面的配对校准判断。

---

## 4. 配对总体：十二个既有观察态，每个新旧呈现各一次

### 4.1 使用既有 State，不重新执行 Action

从本轮十二个会话中，按同一规则选取：

> **首次实际 Action 执行后，第一次提供 pending Observation 的公开 Update 请求。**

这个规则不按后续是否成功、错误类型或响应长度选样。由报告可知，它覆盖：

* 四个 registered comparison 观察态；
* 四个 lookup 观察态；
* 三个 relation_sum 观察态；
* 一个 share_ratio 观察态。

这是已观察数据上的诊断校准域，不是未见任务泛化集。重复或相似 State 也不能被解释成十二种财务问题。

每个 State 构造两个新校准请求：

| 组别         | 呈现内容                                        |
| ---------- | ------------------------------------------- |
| **O：原呈现**  | 原公开请求及原条件说明                                 |
| **R：修复呈现** | 同一 State、Observation 和候选信息，加上完整 Update 条件说明 |

两组使用新的校准调用身份，但原历史 State 只作为只读挑战输入。响应不提交到旧会话、不追加旧 Claim，也不改变旧计数或 \(1/12\)。

### 4.2 校准只检验 accept 的编码，不混入接受意愿

建议两组共同加入明确的校准任务要求：

> 本次只检验对当前已验证 Observation 的完整 accept 提交。

这样可以避免模型通过合法 reject 绕开完整 proposition 提交，然后被误计为“接受接口改善”。

必须同时承认：**这项校准不测模型自主决定接受还是拒绝的能力。**它测试的是在指定 accept 的条件下，公开合同是否足以支持正确编码。

因此，O 组也不是对历史原会话的逐字复跑；两组共享同一个新增校准指令，只在 Update 规则呈现上不同。历史响应不能作为本轮 O 组的新样本。

### 4.3 调用预算固定为二十四次

$$
12\text{ 个观察态}\times2\text{ 个呈现}=24\text{ 次实际请求}.
$$

每个请求一次响应后停止：

```text
不运行金融 Action
不 commit Update
不形成完整新会话
不通过错误反馈继续第二次尝试
不自动重试，不替换失败调用
```

配对顺序在执行前固定：六对 O→R、六对 R→O；每个 C/B/S 任务组内部各两对采用一种顺序。各调用不读取另一组输出作为示例。

继续使用本轮精确模型候选配置和单次预算时，应在发送前重新登记生成条件；不宣称模型别名跨时间对应不可变权重。本轮的每次 allowance 为 107,520，因此沿用该上限时，校准总预留上限是：

$$
24\times107{,}520=2{,}580{,}480.
$$

它不是实际 Token 消耗预测。新请求若超过冻结字节界限，应在发送前拒绝，不静默截断。原预算定义见本轮报告。

## 5. 两组使用同一个评分器，防止“通过标准变宽”伪装为改善

定义：

$$
Y_i^a=
\mathbf1[
\text{结构合法}
\land\text{disposition=accept}
\land\text{完整 proposition 一致}
\land\text{assessment 合法}
\land\text{transition 合法}
],
$$

其中 \(a\in\{O,R\}\)。

两组响应都由**同一个冻结 Parser 和语义准入逻辑**评价。可以增加只读评估入口，但不通过修改旧 State 或实际提交来评分。

主要结果：

$$
\widehat p_O=\frac1{12}\sum_iY_i^O,\qquad
\widehat p_R=\frac1{12}\sum_iY_i^R,
$$

$$
\widehat\Delta
=\frac1{12}\sum_i(Y_i^R-Y_i^O).
$$

还应报告“仅 R 成功”“仅 O 成功”“两者成功”“两者均未成功”的配对数量，以及 C/B/S 和 proposition 形态的分层结果。

这些量解释为：

> 当前有限观察态、指定 accept、固定调用条件下的单步呈现对照。

不是完整任务成功率，也不是更广泛模型能力。

**本轮新错误反馈不参与这一单步对照的后续交互。**因此，在线差异主要归属于首次请求中的规则呈现；错误反馈可以完成本地正确性检查，但不能借这二十四次调用宣称其纠错效果已被单独验证。

---

## 6. 预先规定怎样收口，不以“出现正效应”为工作流通过条件

建议把三个判断分开：

| 对象             | 判断方式                                      |
| -------------- | ----------------------------------------- |
| **修复正确性**      | 原合法内容仍合法，原非法内容不因放宽而通过；公开规则能覆盖当前 Update 判定 |
| **配对执行完整性**    | 二十四调用及所有失败证据完整，无替换、无历史污染                  |
| **模型改善与后继准备度** | 根据实际配对结果和预先登记的工程门槛判断                      |

用于是否进入下一次有限完整会话，建议工程门槛可设为：

$$
R\text{ 组完整合法 accept}\ge10/12,
$$

且 C/B/S 各至少 \(3/4\)。**这是建议在执行前冻结的工程推进标准，不是统计可靠性下界，也不是本轮已有合同。**

其解释应当保持克制：

* R 达标且明显优于 O：支持当前显式呈现具有工程改善，进入有限完整会话。
* R 达标但 O 同样较高：修复后的接口可用性得到见证，但本次增益证据不足；不追加试次追求显著差异。
* R 未达标：记录首先剩余的具体条件错误，只修该接口问题，不增加来源或训练模型绕过。
* 某组发生完整记录的无响应：保留调用失败；若证据本身缺失，则保留未知，不补样。

**一次未达到模型门槛不意味着报告或执行证据无效。**同样，局部控制全通过也不允许宣布模型已经能够完整接受。

## 七、校准之后：恢复完整任务，而不是继续停留在复制接口上

修复及单步校准通过后，再开展**三个原任务各两个新会话，共六个完整会话**，恢复原来的 accept／reject 自由选择，采用同一个统一 Runtime 和冻结任务合同。

那时主要观察：

> 原本阻塞在第一个 Update 的会话，是否能够进入后续实际语义运算、Claim 消费和有效 Final？

不需要再重复来源、Registry 或确定性两类审计。也不要求 Share 两条路线都出现。

但这六会话是后继的另一种测量对象，不能从二十四次单步校准自动获得：

* 单步 accept 成功，不等于完整 branch 成功；
* 完整执行成功，不等于新的商映射已闭合；
* 能提交完整命题，不等于一般推理修订或自主规划能力。

**完整 proposition 复制是当前协议的接口要求，不是 VTDO 的科学贡献本身。**修复它的目的，是避免这个偶然编码瓶颈遮蔽真正要研究的依据选择、推导依赖和有效行为分布。

---

## 最终收口

本轮最准确的记录是：

```text
执行与证据：
  接受为完整、可核验的十二会话实验

经验结果：
  C/B/S = 1/4、0/4、0/4
  总体 = 1/12
  不重算，不补样，不回写

已成立的表示：
  C03 三条原始监督候选及 Token 检查

当前阻塞：
  Update 的模型可见条件说明
  与实际整对象接受规则不完整对应

必须修复：
  完整公开既有 Update 条件及相应反馈
  不放宽验证、不自动填字段、不修改历史响应

推荐下一实验：
  十二个既有观察态
  × 原／修复呈现各一次
  = 二十四次单步配对校准

暂不推进：
  来源扩张、训练、Contribution、VTDO 更新
  或当前十二会话的重复长运行
```

**本轮的问题不是“模型已经被证明处理不了复杂金融任务”，而是：任务执行在一个未完整公开的接受协议上反复受阻。下一步应先把这条已有规则清楚地交给模型，并用小规模、同标准的对照判断效果，再恢复对完整解决行为的测量。**
