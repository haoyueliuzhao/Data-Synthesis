## 5. Boundary Algorithm 和 Confirmation 隔离明显增强

* 唯一共同 supported → unsupported 相邻对：`boundary_bracketed`。

所有 512 个两组 × 四深度 × 两套阈值模式均被唯一分类。

Confirmation Catalog 也被写入独立 Root，Development Root 中只留下内容根和 receipt，没有 payload 或 payload path。报告对此做了准确限制：这是工件接口隔离，不是对仓库管理员的物理不可见性证明。

## 3. 机制行为不影响金融答案

当前实际结构相当于：

```text
独立完成一个两 Evidence、一 Operation 的 Finance Core
+
独立通过一个合成的 capability event graph
```

* Reconciliation 生成的 `normalized_ref_slot_01` 没有成为实际 TaskProgram operand；

* Recovery 的 failure/revision 不改变真实 Tool selector；
* Stopping checkpoint 不来自实际 Program closure／verification state。

> 不执行预注册事件，就不能满足这个机制事件合同。

> 不执行该机制，就不能正确解决这道金融任务。

这与任务级 Mechanism Necessity 是两个不同命题。

\boxed{

# 八、P1：内容寻址对象的交叉父绑定仍不完整

`ExecutableDepthPackage.validate_package()` 只检查了部分父子关系。

我构造了内容哈希全部重新计算的对象，而不是保留 stale hash。当前 Package Validator 接受了：

```text
1. witness contract 被改成错误 capability/depth，
   verifier contract 随之重算；

2. target load 被改成错误 capability/depth；

3. nuisance measurement 绑定到另一个 operational TaskPackage；

4. prompt binding 绑定到另一个 generation-condition ID；

5. signature 中的 witness/load/nuisance/prompt parent IDs
   被替换成无关对象。
```

上述五种对象均通过：

```python
ExecutableDepthPackage.model_validate(...)
```

我进一步重新计算 Group 与 Catalog identity，包含错误 Prompt Condition 的完整 Development Catalog 也能够通过验证。

原因是：

```text
phase1_v26_capability_executable_depth_rematerialization_models.py
325–367
```

没有完整检查：

* `witness_contract.capability_family/depth`；
* `depth_witness.witness_contract_id/verifier_contract_id`；
* `target_load.capability_family/depth`；
* `nuisance.base_operational_task_package_id`；
* `prompt_binding.fixed_generation_condition_id`；
* Signature 的全部 parent IDs 与实际子对象。

当前 30 个 destructive controls 会检测未重算哈希的原地修改，但没有覆盖“重新内容寻址后的 crossed parent”。

这不证明正式 v26.168 Catalog 本身已经错绑；正式工件当前是自洽的。但它说明未来 Runner 若依赖这些 Schema 做独立重建，仍有接受交叉绑定对象的风险。

至少需要：

### Context

先前 Action／Observation 必须实际改变后续 Candidate set 或正确选择规则：

$$
S_{t+1}=f(S_t,a_t,o_t).
$$

不能只写一个 `depends_on_slot` 字段。

### Reconciliation

只有已经产生的 normalization ref 才能被消费。Raw bypass 后必须：

* 无法执行目标 Operation；
* 或在 Verifier 中因原始语义不兼容失败。

### Failure Recovery

`revise_after_failure` 只能在匹配 typed failure 已经发生后出现。Avoid-failure 路径不能自动进入 Recovery state。

### Stopping

Tempting continuation 必须真正改变公共状态、消耗调用或形成 postcompletion violation。`stop_after_completion` 只能在真实 verification 完成后可见。

## 4. 将能力机制接入真实 Finance Program

四项能力应当改变真实任务对象：

```text
Context action
→ 决定实际 Operator／Evidence path

Reconciliation
→ 产生实际 TaskProgram operand reference

Recovery
→ 修正真实 Tool selector／blocked action

Stopping
→ 读取真实 Program closure 与 terminal verification
```

不能继续只把：

```text
finance_core_id
```

写进 Graph identity，而不让 Graph 的行为影响 Finance Task。

## 5. 重做 Mechanism Necessity

Counterfactual 必须保持 Graph 完整可执行：

```text
Baseline：
Task Base-valid + Mechanism-qualified

Counterfactual：
保留相同 Task、Evidence、资源和接口，
删除／绕过目标机制，
重新执行 Runtime + Task Verifier + Mechanism Verifier
```

并分别保存：

```text
counterfactual_base_valid
counterfactual_mechanism_qualified
counterfactual_qualified_valid
```

不能只保存固定：

```text
full_validity_passed=false
target_mechanism_necessary=true
```

* 重新计算 package/group/catalog identity；
* 仍然要求在语义父绑定处 fail-closed。

# 十二、最终结论

v26.168 不是一次无效修订。它已经把 v26.167 的：

```text
同一任务
+ 不同深度标签
+ 自报负担
```

推进到了：

```text
低 nuisance Finance Core
+ 不同的 typed Graph
+ 不同 Candidate 和 Transition
+ 不同 Depth Witness
+ 从图计算的目标负担
```

这是实质进展。

但目前仍有一道关键鸿沟：

$$
\boxed{
\text{“不同的 typed Graph”}
\neq
\text{“可信的模型能力任务”。}
}
$$

当前 Prompt 把参考候选和未来路径直接泄漏给模型；当前 Runtime 中所有选择都进入同一后继；能力事件没有真正作用于金融 Program；Counterfactual 主要证明事件合同的自洽性，而非目标机制对任务求解的必要性。

所以本轮最准确的结论是：

> **v26.168 已完成 executable-depth 数据结构和局部 Runtime 原型，但模型可见投影与任务级因果语义尚未通过。**

当前第一个根本阻塞点不再是：

```text
Depth 只有元数据
```

而是：

```text
Depth Graph 尚未成为无 Oracle 泄漏、
有真实行为后果、并与 Finance Task 因果耦合的模型执行环境。
```

在这一层闭合前，运行 192 个模型 Job 得到的将主要是模型识别结构化参考标记和执行线性微协议的结果，不能可靠解释为四项金融 Agent 能力的广度—深度边界。
