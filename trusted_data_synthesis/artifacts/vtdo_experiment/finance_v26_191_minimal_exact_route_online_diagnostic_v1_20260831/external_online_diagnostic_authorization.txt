对，**现在应该进行在线测试**。v26.190 已经把现有离线证据能回答的问题基本回答完了：192 个失败请求与历史 7,229 个成功请求之间，没有发现可持久化的固定请求合同差异；剩余不可观察面正是执行时凭证/账户路由、Provider 当时的服务状态，以及被丢弃的 HTTP 400 响应正文。继续做同类离线审计不会增加根因信息。

而且，DeepSeek 当前官方文档仍将 `deepseek-v4-flash`、`thinking={"type":"enabled"}`、JSON Output 和远高于 16,384 的最大输出范围列为支持能力；官方错误码将 HTTP 400 定义为请求格式错误，并明确要求依据错误消息修正请求。因此，**下一步最重要的观测量就是经过脱敏的 HTTP 400 error body，而不是再比较一次哈希**。([DeepSeek API Docs][1])

# 二、第一阶段：四个固定在线请求

## D0：账户与模型可见性

请求：

```http
GET https://api.deepseek.com/models
Authorization: Bearer <same current credential>
```

官方提供 `/models` 接口用于列出当前账户可使用的模型。([DeepSeek API Docs][2])

判定：

| 结果                         | 根因分类                 |
| -------------------------- | -------------------- |
| 401                        | 当前 API Key 无效        |
| 402                        | 账户余额问题               |
| 200，但无 `deepseek-v4-flash` | 当前账户没有该模型路由或模型不可用    |
| 200，包含 `deepseek-v4-flash` | 凭证、账户访问和模型可见性初步通过    |
| 400                        | 账户路由、网关或请求头异常，读取错误正文 |

这一步比直接发复杂 Prompt 更干净，因为它完全不涉及 Chat Completion body。

## D1：官方路径上的最小请求

当前官方文档将 OpenAI 格式的 Base URL 写为：

```text
https://api.deepseek.com
```

Chat Completion 路径写为：

```text
/chat/completions
```

([DeepSeek API Docs][1])

请求体只保留最小核心字段：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {
      "role": "user",
      "content": "Reply with the single word OK."
    }
  ],
  "max_tokens": 64
}
```

这一步用于判断：**当前凭证和当前服务是否能够完成最基础的 Flash Chat Completion。**

## D2：历史精确路径对照

使用与 D1 完全相同的请求字节，只把路径改为 v26.188 使用的：

```text
https://api.deepseek.com/v1/chat/completions
```

判定：

| D1  | D2  | 解释                      |
| --- | --- | ----------------------- |
| 200 | 400 | `/v1` 路径当前不再兼容，路由原因基本定位 |
| 200 | 200 | 两个路径均可用，排除路径别名          |
| 400 | 200 | 官方文档路径与当前实际服务存在异常差异     |
| 400 | 400 | 继续依据错误正文和后续字段测试定位       |

这里不能预先认定 `/v1` 已失效，因为历史 7,229 个成功请求确实使用了相同路由；它只是必须在线重测的一个动态面。

## D3：完整参数形状、最小 Prompt

在 D1/D2 中成功的路径上发送：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {
      "role": "user",
      "content": "Return JSON exactly as {\"ok\":true}."
    }
  ],
  "max_tokens": 16384,
  "response_format": {
    "type": "json_object"
  },
  "temperature": 0.6,
  "thinking": {
    "type": "enabled"
  },
  "top_p": 0.9
}
```

官方文档支持这些字段；在 thinking mode 下，`temperature` 和 `top_p` 应被忽略，而不是成为错误。JSON Output 要求 Prompt 明确要求 JSON，因此该控制也满足这一条件。([DeepSeek API Docs][1])

若 D1 成功而 D3 返回 400，问题就从“账户/路由”缩小为“完整参数组合”。

# 四、这次必须保存什么

v26.188 最大的信息损失是没有保存 HTTP 400 error body。v26.190 因而只能得到：

```text
not_localizable_from_persisted_artifacts
```



新诊断必须读取响应正文，但采用安全的 typed projection。建议只持久化：

```text
HTTP status
HTTP method
endpoint
diagnostic request ID
request-body SHA-256
request-body byte count
request field set
Content-Type
x-request-id / request-id（如存在）
error.type
error.code
error.param
经过凭证模式脱敏的 error.message
response-body SHA-256
response-body byte count
```

禁止保存：

```text
Authorization 值
API Key hash
Cookie
完整请求 Header
私有 reasoning_content
成功响应中的私有推理文本
未经检查的任意响应正文
```

若错误正文不是预期 JSON：

```text
保存 body SHA-256 和 byte count
保存经过密钥模式、Bearer 模式和长 token 模式脱敏后的前 4 KiB
标记 error_body_schema = unrecognized
```

这样才能既保持隐私边界，又不再次丢掉根因。
