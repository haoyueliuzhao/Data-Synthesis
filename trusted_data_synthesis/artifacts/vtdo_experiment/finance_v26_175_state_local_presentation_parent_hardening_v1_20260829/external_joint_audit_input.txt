## 1. 上一轮两个联合相位缺陷已被真实修复

```text

(display rank + Legend position) mod 3            396/396
```

并没有通过修改历史结果来“消除”它们。

新实现将每个语义值别名局部化到：

```text
Choice × field × Package × Component × Replica
```

并分别调度：

```text

Legend position
display-handle rank
value-handle rank
```

当前注册 Gate 覆盖：

* 单变量 rank 常量；

* 二变量 `< / = / >`；
* 二变量交叉排序；
* value rank 的 sum／range／median；

报告给出的 80 个 State stratum、23,918 次规则评估和零超基线 stratum，与源码中 `_v174_shortcut_stratum()` 的实现范围一致。

$$
\boxed{
\text{v26.173 已知的两个二变量确定性捷径已经关闭。}
}
$$

## 2. Mechanism Semantics 已从 canonical path 中重新分离

报告和源码现在均区分：

```text
reference_path_match
mechanism_semantically_qualified
```

其中 canonical path 只作为诊断，不进入 Mechanism Gate。

新机制定义为：

* Context：真实当前状态决策并完成任务；
* Reconciliation：真实产生、消费 normalized reference 并完成任务；
* Recovery：同 Rule、同 Failure Receipt，selector 改变、Retry 成功、时序正确并完成任务，不要求唯一 selector；
* Stopping：Runtime readiness、verified stop、无 postcompletion call。

在注册的 146 条单 Choice 非 reference 执行中：

```text

Base-valid                         24
Mechanism-qualified                32
Qualified-valid                    24
Base-valid / Mechanism-false        0
```

六条 Context、四条 Reconciliation、十四条 Recovery 的 Base-valid 非规范路径重新成为 Mechanism-qualified；20 条 same-Rule 非规范 Recovery 中，14 条 Retry 成功并同时 Base／Mechanism／Qualified-valid。

源码中的审计确实逐条执行这些非 reference Action，而不是只修改保存标签。

这一修复方向正确。

## 3. Failure Receipt 生命周期已经真正前移到 Prompt 之前

当前 Runtime 顺序已变为：

```text
到达当前 Recovery State
→ 执行真实 coarse selector
→ 产生 typed failure event
→ 构造 exact Failure Receipt
→ 将 exact Receipt 放入当前 Prompt
→ 校验模型选择
→ 在同一个 retained Runtime 上 Retry
```

Receipt 内容绑定：

```text
receipt_id
rule_handle
failed_selector_hash
error_code
source_tool_id
failure_event_id
```

缺失字段不再使用默认值补齐。

120 个 Recovery Prompt 全部实现：

```text
真实失败先于 Prompt                        120/120
Prompt Receipt 完整                        120/120
Prompt / Runtime Receipt identity         120/120
Failure / Retry Receipt identity          120/120
Rule / selector / error / Tool match      120/120
```

六类 Receipt 变异各自 20/20 拒绝。 

源码也确实在 `render_next_prompt()` 之前调用 `_prepare_current_recovery_failure()`，保留真实失败 Runtime 并将其 exact receipt 传给后续 Retry。

因此上一轮“Prompt Receipt 与真实 Runtime Receipt 不是同一对象”的 P0 已被关闭。

# 四、P0：仍存在一个 396/396 的三变量呈现捷径

这是当前第一个根本阻塞点。

## 1. 根因：reference 始终先规范化为 source slot 0

源码先计算 reference 在原始 Choice 列表中的索引，然后构造：

```python
normalized_source_indices = (
    reference_index,
    *other_indices,
)
```

也就是：

$$
\text{normalized choice }0=\text{reference}.
$$

随后 Candidate、Action、Legend、Display 和 Value 的 rank 都从一套全局固定的六 Replica schedule 中读取。不同 Package 和 Component 只改变 opaque ID 字节，不改变这套 rank 关系。

三个候选时的相关源码调度为全局常量：

```text
candidate schedule
action schedule
legend schedule
display schedule
value0–value3 schedules
```

而不是为每个 State 独立抽取一套调度。

---

## 2. 一个简单三变量规则即可恢复 reference

对每个 Candidate 定义：

$$
p=\text{Candidate position},
$$

$$
a=\text{action\_id 的词法 rank},
$$

$$
l=\text{Legend position}.
$$

计算：

$$
s=(-2p+2a-3l)\bmod 6,
$$

选择 \(s\) 最大的 Candidate。

对源码中的六个 Replica，三个 normalized Choice 的分数分别为：

| Replica | \(s(\text{reference}),s(\text{alt}_1),s(\text{alt}_2)\) | 唯一最大项     |
| ------: | ------------------------------------------------------- | --------- |
|       0 | \(4,3,2\)                                               | reference |
|       1 | \(2,0,1\)                                               | reference |
|       2 | \(3,0,0\)                                               | reference |
|       3 | \(4,3,2\)                                               | reference |
|       4 | \(3,0,0\)                                               | reference |
|       5 | \(2,0,1\)                                               | reference |

因此：

```text
三候选 State                         66
每 State Replica                      6
每个 exact stratum 恢复              6/6
总恢复                              396/396
结构随机基线                          2/6
```

该规则完全不读取：

* Finance Task；
* Resolution Rule；
* semantic value；
* Failure Receipt；
* Operation 参数；
  -模型结果。

它只使用三个公开 rank 通道。

这一**窄统计陈述**没有问题。报告自己也明确拒绝一般非干扰主张。

# 五、P1：Mechanism 审计仍只是单组件一阶扰动

报告称：

```text
complete new 146-row nonreference surface
```

但源码中的构造方式是：

```python
for component:
    for nonreference choice:
        execute_selected_path(
            selected_by_component={
                current_component: current_nonreference_choice
            }
        )
```

也就是说，每次只替换一个 Component，其余 Component 全部继续使用 reference。

因此，当前 146 行完整覆盖的是：

$$
\boxed{
\text{全部合法 single-Choice nonreference substitutions}
}
$$

而不是：

$$
\boxed{
\text{全部非 reference trajectory combinations}.
}
$$

当 D3 最多包含四个目标组件、每个组件最多三个 Choice 时，一个 Package 的完整组合上限只有：

$$
3^4=81.
$$

所以在本地零调用条件下，穷举多组件组合是可行的。

### 当前风险

两个分别合法、分别保持 Mechanism 的非规范选择组合后，可能出现：

* 依赖 receipt 交叉；
* normalization output 别名冲突；
* record／scope 组合不一致；
* 单步均 accepted，但组合后 task closure 失败；
* 单步均 semantic，但组合后的 mechanism predicate 不再成立。

当前报告和测试均没有覆盖这一交互面。

这不是已经证明存在的 Runtime Bug，因此定级为 **P1 证据范围缺口**，但报告中的 “complete nonreference surface” 应改为：

```text
complete legal single-choice nonreference surface
```

# 七、P2：Receipt 拒绝后的零 Retry 是代码路径推论，不是执行计数

Receipt Audit 对六类变异调用：

```python

```

确认其 `accepted=false`，随后将：

```text
retry_after_receipt_rejection_count = 0
```

写入审计结果。

生产 Runtime 的控制流确实是在 acceptance 失败时先 typed reject，理论上不会调用 Recovery Retry，因此目前没有证据表明存在真实 Retry 缺陷。

但报告中“Retry after those rejections is zero”的最强执行证据，应来自：

```text
变异 Prompt
→ production step()
→ typed rejection
→ 实际 Runtime event audit
→ retry invocation count = 0
```

而不仅是对 acceptance classifier 的调用。

因此这是 **P2 证据深度不足**，不是阻塞当前设计的独立 P0。

# 八、理论解释边界仍然正确

$$
P(A_k=1\mid A_1=\cdots=A_{k-1}=1),

$$
P(\text{整个 Package Qualified}).
$$

这不是 v26.174 的缺陷，而是后续结果解释必须遵守的理论边界。
