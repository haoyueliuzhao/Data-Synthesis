# 四、P0：reference 通过有序 `choice_legend` 直接泄漏

这是当前最明确、单独就足以阻塞 Runner 预检的问题。

## 1. `choice_legend` 是模型可见对象

源码中：

```python
class CausalPublicDecisionState:
    choice_legend: tuple[PublicChoiceLegendEntry, ...]
```

它被直接放入：

```text
CausalPublicPrompt.state
```

因此模型可以看到：

```text
choice_handle
→ 完整 public operation semantics
```

Candidate envelope 虽然被轮换，但 `choice_legend` 本身没有按 Replica 轮换。

---

## 2. 构造逻辑始终先放 reference operation

`build_component()` 的主要顺序是：

```python
legend = tuple(choice_entry(item) for item in spec.operations)

reference_choice_handle = legend[0].choice_handle
```

随后 public-only selector 会再次验证 reference，但当前 80 个正式状态中，选择结果始终仍是第一个 legend entry。

独立扫描结果：

```text
目标状态                                             80
reference 是 choice_legend[0]                       80/80

六 Replica 呈现                                     480
“读取 legend[0] 并映射回 Candidate”命中 reference   480/480
```

也就是说，一个完全不理解金融任务的策略只需执行：

```python
reference_handle = prompt.state.choice_legend[0].choice_handle
return candidate whose choice_handle == reference_handle
```

就能得到 100% 的 reference Action。

Candidate 的屏幕位置虽然平衡了，但 reference path 已经通过另一条模型可见序列泄漏。

---

## 3. Legend 语义长度还存在第二条捷径

除了固定首位，还有：

```text
reference operation 的序列化语义长度在 32/80 个状态中唯一
```

其中：

```text
assess_dynamic_readiness   12/12：reference 最短
select_operator             8/8：reference 最短
select_projection           4/4：reference 最长

```

所以即使单纯随机化 legend 顺序，一个：

```text

```

策略仍能在相当一部分状态中识别 reference。

## 3. 因此报告中的结论需要收窄

报告称 26 条行为证明：

> task correctness and target-mechanism occurrence are not aliases. 

更准确的表述应是：

> task correctness 与**注册的规范机制路径合同**不是同一个对象。

当前尚未证明：

> task correctness 与广义的 Failure Recovery、Context-conditioned Action 等机制是否发生不是同一个对象。

这很重要，因为后续能力观测会使用：

$$
V_{\mathrm{qualified}}
=
V_{\mathrm{base}}
\land
Q_{\mathrm{mechanism}}.
$$

若 Q 只接受一条 canonical reference path，就会把：

```text
任务正确
+ 目标能力真实发生
+ 但采用另一条合法实现
```

的轨迹误排除出 Qualified 集合，系统性低估模型能力支持。

### 建议拆成两个对象

```text
reference_path_match
mechanism_semantically_qualified
```

例如 Failure Recovery 的 Mechanism Gate 应关注：

```text
typed failure 是否真实发生
selector 是否实际改变
retry 是否成功
任务是否闭合
```

而不是要求唯一冻结 selector。

精确 reference path 可以继续作为 Witness 或 path-adherence 诊断，但不应自动等同于能力机制本身。

# 六、P0/P1：D2／D3 尚未形成模型交互意义上的动态组合深度

报告称组件具有 dynamic dependencies，代码也记录了：

```text
dependency_component_keys
```

但当前本地 Runtime 的执行方式仍然是：

```python
execute_runtime(
    selected_by_component={
        component_1: choice_1,
        component_2: choice_2,
        ...
    }
)
```

也就是说，所有组件选择先一次性给定，然后 Runtime 执行和检查顺序。

## 1. Prompt 并未由前序模型选择动态生成

当前 Package 保存的是：

```text
baseline_prompts
```

每个 Component 的 Prompt 都提前独立构造。

独立统计：

```text
声明的 dependency links                         80
具有 dependency 的 components                  48
显式 predecessor-conditioned prompt variants    0
```

并没有形成：

```text
模型选择 a_t
→ Runtime Observation o_t
→ 公共 State S_{t+1}
→ 再生成下一 Prompt
```

这样的真实 Agent 交互链。

---

## 2. Stopping 的存储顺序甚至不是拓扑序

`_stopping_specs()` 返回：

```python
(final_decision, *readiness_components)
```

但 `final_decision` 又声明依赖所有 readiness components。

正式 32 个 Package 中存在：

```text
12 条 dependency link
其 dependency 在 Package 顺序中位于 dependent component 之后
```

本地 Runtime 为 Stopping 单独先计算 readiness，再处理 final，因此静态执行仍能通过；但未来 Runner 若按 Catalog 顺序调用模型，就会先询问 stop，再询问 readiness。

---

## 3. 当前更像“累计微决策数量”

D0–D3 当前大致是：

```text
D0：1 个目标微决策
D1：2 个目标微决策
D2：3 个目标微决策
D3：4 个目标微决策
```

即使模型每一步能力完全不随深度变化，单步正确率恒为 \(p\)，完整成功率也会机械地变成：

$$
q_d \approx p^{d+1}.
$$

因此未来观察到成功率随深度下降，不能自动解释成：

> 模型的潜在能力边界位于 D1 与 D2 之间。

它可能只是在测量连续多次选择均正确的乘法负担。

### 下一阶段必须冻结

* 组件拓扑顺序；
* 每一步实际 reached current state；
* 前序选择与 Observation 的公开 receipt；
* 后续 Prompt 从该 receipt 重新生成；
* 每个深度新增组件的真实条件依赖；
* 不允许一次性预提交整条 choice vector。

在这之前，`D2_COMPOSITIONAL` 的名称仍然偏强。
