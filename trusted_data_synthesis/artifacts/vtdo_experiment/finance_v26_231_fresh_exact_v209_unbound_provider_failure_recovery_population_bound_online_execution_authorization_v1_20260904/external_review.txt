### 1. 来源分区不是循环自证

实现从 v26.226 的完整 Manifest、`execution_summary.json` 和每一个实际 `job_failures/job_XXX.json` 开始。它先依据实际 `failure_kind` 将三个 Host failure 排除，只接收 `unbound_provider_failure`，之后才把独立构造的候选形状与 v26.229 保存对象比较。

独立导出的精确分区为：

```text

unbound Provider failures   33
actual failure files        36
candidate selector calls     0
```

33 个 Provider ordinal、来源集合摘要及 33 个 source-row 实际字节全部匹配。

因此，没有发生：

```text
直接读取 v26.229 的 33 行
  -> 再用同一批行证明 v26.229 正确
```

### 2. 请求重放真实到达了历史失败调用点

独立 Capture Transport 只接受 55 个已经持久化的成功 public projections。当前缀耗尽时，它记录最后一个 `TransportDispatch`，随后立即抛出本地停止异常：

```text

不创建失败调用 InvocationRecord
不派生 terminal
不写 Raw / Result / Trace / Outcome
不调用 Provider
```

实际实现逐调用核对 request canonical bytes、SHA-256、字节数、certificate、pre-transport Receipt，以及成功前缀的 response hash。

最终结果为：


## 二、响应可识别性边界正确

v26.230 没有把“请求可以重构”混同为“历史响应可以恢复”。

### 31 个 `ReasoningBudgetExhaustedError`

这 31 行只授权以下结论：

```text
normalized public string length = 0
normalized public string hash   = SHA256(empty)
finish_reason                    = length
```

不能据此恢复：

* Provider 原始 content 字段是 `null` 还是空字符串；
* 原始 HTTP response bytes；
* private reasoning 内容。

### 2 个 `JSONDecodeError`

ordinal 62 和 139 的公开内容长度、hash 与 finish reason 只是诊断量。规范化字符串和原始 response envelope 均未持久化，所以 exact JSON syntax 保持不可识别，没有被猜测或补写。实际代码也只把 reasoning-budget 行标为 `failure_semantics_identifiable=true`，而 JSON-decode 行保持不可识别。

正式划分为：

```text
ReasoningBudgetExhaustedError      31
JSONDecodeError                     2
failed requests reconstructible    33
raw response bytes persisted        0
raw response bytes guessed          0
historical terminals created        0
```

### Scope limitation

以下对象仍未评估，但不否定本轮：

1. Recovery 请求能否获得成功响应；
2. 扩大 Completion 或 rollout budget 后的模型行为；
3. 两个 JSON-decode 行的历史响应内容；
4. Recovery 后是否能继续完成剩余 Runtime Program；
5. Recovery outcome 应如何进入新的经验 estimand；
6. Capability、State frequency、Contribution 或 VTDO。

v26.230 只声明六个直接 replay dependency members，并明确不声称超出冻结源码快照的通用 runtime-environment closure。这是主动保留的范围，不是当前缺陷。


上一轮提出的 replay dependency closure 加固已经由 v26.230 完成，不应继续围绕同一 source-authority 问题重复审计。

## 七、当前允许与禁止的结论

### 允许

可以正式声称：

> v26.226 的 33 个 `unbound_provider_failure` 构成一个精确、来源可审计的集合；其 55 个成功调用前缀和 33 个最后失败请求可以在零 Provider 调用下重建；v26.229 据此构造的 33 个全新非执行 Recovery Jobs 已通过独立审计。

### 禁止

不能声称：

* 33 个失败 Job 已恢复；
* 31 个 reasoning-budget Job 增大预算后必然成功；
* 两个 JSON-decode 历史响应已恢复；
* 33 个 Job 已拥有历史 terminal；
* v26.226 已形成完整的 192-Job empirical evidence set；
* 可以把未来 Recovery outcome 直接回填到 v26.226；
* 可以计算新的 Capability、frequency、Contribution 或 VTDO；
* QA 链路、训练或 Release 已获得授权。

报告自身也将成功恢复、历史响应、完整经验集和所有下游结论明确排除。

尤其是 v26.226 仍然是：

```text
192 attempted Jobs
156 complete Jobs
36 failure records
execution_status = incomplete
```

它原有的一次性 replacement authorization 已经消耗，不能用于 Recovery。

## 八、后续主链实验

作为本次外部审计，**唯一获授权的下一阶段**应为：

```text
fresh_exact_v209_unbound_provider_failure_recovery_population_bound_
online_execution_authorization_only
```

该阶段只能构造一份新的、尚未消费的一次性在线授权，不能直接调用 Provider。v26.230 的历史 Transition 仍保持 `next_stage_authorized=false`，不会被追溯修改；新的阶段需要绑定本次外部审计字节及单独的 operator directive。

授权阶段必须至少冻结三项内容：

| 必须冻结的对象                                                            | 原因                                                                 |
| ------------------------------------------------------------------ | ------------------------------------------------------------------ |
| exact v26.229 Recovery Contract、Population 和 33 个 Recovery Job IDs | 防止替换或扩大来源人口                                                        |
| Recovery 执行语义                                                      | 明确是“只重发失败调用”还是“从失败点继续执行至终止”                                        |
| 新资源与调用预算                                                           | 31 个 reasoning-budget 行若改变 `max_tokens`，即形成新的恢复条件，不能冒充原 v26.226 条件 |

还应明确：

```text
55 个历史成功调用只允许本地重放，不应再次调用 Provider
在线调用上限不能默认等于 33
```

因为其中 3 个失败在 `first_action`、25 个在 `subsequent_action`、5 个在 `final`。若恢复 Action 后继续至 Final，后续实际 Provider 调用数可能高于每 Job 一次，必须由新的 Recovery Execution Contract 预先限定。

## 最终结论

> **v26.230 主链实验通过。当前首个未闭合对象已经从“Recovery Population 是否可信”前移到“如何为该精确 Population 定义并签发一次性 Recovery 在线执行授权”。可以进入 authorization-only 阶段；Provider 调用和 Recovery 执行本身仍未授权。**
