## 一、最终判定

v26.172 是一次**有实质进展但尚未达到 Runner 预检资格**的修订。

$$

$$
\boxed{

## 2. canonical path 与机制语义已经拆开

现在分别保存：

```text
reference_path_match
mechanism_semantically_qualified
```

其中 `reference_path_match` 只是规范路径诊断，不进入机制 Gate。

报告定义的机制语义包括：

* Context：真实应用当前状态决策并闭合任务；
* Reconciliation：真实产生并按序消费 normalized reference；
* Recovery：真实 typed failure、selector 改变、成功 retry、事件顺序与任务闭合；
* Stopping：Runtime readiness、verified stop、无后续 postcompletion call。

在 32 个 baseline 与 146 个合法非 reference 执行上，报告得到：

```text

semantic-mechanism-qualified        66

Base=true,  semantic=false           0
Base=false, semantic=true            8
Base=false, semantic=false         112
```

原来的 26 个 `Base=true / canonical-path=false` 行全部变成 semantic mechanism true，说明它们只是偏离了 canonical path，而不是没有发生目标机制。

这项修订方向正确，也修复了 v26.171 对非规范 Recovery 路径的系统性误排除。

# 四、P0：共享语义值表与稳定索引形成新的 reference 捷径

这是本轮最直接的 presentation blocker。

## 1. 源码中的编码方式

源码：

```text
src/trusted_synthesis/core/task/
dynamic_capability_depth.py
```

关键路径：

```text
_value_catalog()       376–400
make_dynamic_prompt()  444–527
```

`_value_catalog()` 对每个参数字段执行：

```python
catalogs[field] = tuple(
    unique[key] for key in sorted(unique)
)
```

也就是说，参数语义值按 canonical bytes 确定性排序。

随后每个 Candidate 的参数被编码为稳定的两位索引：

```python
indices.append(f"{index:02d}")
```

六个 Replica 虽然会改变：

* Legend row 顺序；
* Candidate row 顺序；
* display handle；
* Candidate action ID；

但不会改变：

* 参数值 Catalog 的排序；
* 每个语义操作对应的 `value_indices`。

所以 reference 的“参数索引指纹”在所有 Replica 和同类任务之间保持稳定。

## 1. Candidate legality 已知道某些动作不属于当前状态

源码：

```text

661–705
```

对 `revise_selector` 明确要求：

```python
arguments["rule_handle"] == facts["rule_handle"]
and selector != failed_selector
```

否则：

```text
state_precondition_valid = false
mechanism_relevant       = false
```

这一逻辑是合理的。

---

## 2. 机制资格却不检查 Rule 或 receipt 身份

源码：

```text
dynamic_capability_depth.py
708–775
```

Failure Recovery 的 semantic Gate 只检查：

```text
存在 typed_selector_requires_refinement
存在 selector_changed=true 的 recovery_succeeded
```

它不检查：

* 被修改的 Rule 是否就是当前失败 Rule；
* typed failure、revision 与 retry 是否绑定同一个 receipt；
* selected operation 的 `rule_handle` 是否真正被 Runtime 消费。

结果是，当前 Runtime 仍可能：

1. 对当前状态的 Rule A 产生 failure；
2. 模型选择一个声称修改 Rule B 的 Candidate；
3. Runtime 忽略 Candidate 中的 Rule B，只使用其 selector；
4. selector 恰好使任务成功；
5. semantic Recovery Gate 判定为 true。

## 3. 对 20 条错误当前 Rule Candidate 的精确结果

```text

state_precondition_valid=false               20
mechanism_relevant=false                     20

Base=false, semantic=false                   14
Base=true,  semantic=true                     6
```

也就是说，有六条轨迹同时满足：

```text

```

如果未来仍使用：

$$

=

\land

$$

这六条轨迹会被判为 Qualified，尽管 Candidate Legality Contract 已经明确声明其对当前状态 mechanism-irrelevant。

这不是单纯字段命名问题，而是不同合同对同一轨迹给出了相互冲突的准入结论。

### 所需修订

至少需要：

1. 将 `state_precondition_valid` 作为 Action acceptance 或 semantic mechanism qualification 的硬前置条件；
2. 让 Runtime 真正使用 selected Candidate 的 `rule_handle`；
3. 使 failure、revision、retry 绑定同一个：

   * `rule_handle`；
   * failure receipt；
   * failed selector；
4. wrong-current-rule Candidate 应产生：

   * typed target mismatch；
   * 或 mechanism false；
   * 不能产生 semantic mechanism true；
5. 在正式行级结果中交叉绑定：

   * Candidate legality report；
   * mechanism report；
   * Qualified report。

# 六、P1：当前动态交互证据仍是“完整 baseline trace 的逐步投影”

报告对这一层的措辞其实比较谨慎：它称其为 local reference fixture，并明确说不是模型选择或在线 Transport 行为。

源码中的 `_reference_trace()` 位于：

```text
phase1_v26_capability_dynamic_depth_hardening.py
454–520
```

其过程是：

1. 先调用 v26.171 Runtime，一次性得到完整 baseline result；
2. 对每个 Component 构造当前 Prompt；
3. 用本地 public-only selector 选择 reference；
4. 从已经完成的 baseline result 中筛出该 Component 的 event；
5. 将这些已有 event 包装成当前 Observation receipt；
6. 再生成下一 Prompt。

这能证明：

* 拓扑顺序可构造；
* 当前 Prompt 能绑定前序 receipt；
* reference trace 可以按步骤重新呈现。

但它尚未证明：

```text
当前 Action Commit
→ 实时改变 Runtime
→ 当前 Tool / Program 执行
→ 生成真实 Observation
→ 从实际 reached state 生成下一 Prompt
```

尤其没有覆盖非 reference Action 后的真实动态分支。

### 结论

这一点不要求否定 v26.172 历史静态结果，但未来 Runner 不能：

* 读取完整 baseline；
* 读取静态 reference Trace；
* 通过过滤 baseline events 生成 Observation。

Runner 预检必须实现真正的：

```python
step(runtime_state, selected_action)
    -> observation
    -> next_runtime_state
    -> next_prompt
```

# 九、理论解释：当前修订主动收窄是正确的

v26.172 已经明确将 D0–D3 定义为：

```text
bounded sequential target-decision depth
```

而不是：

```text
latent ability boundary
```

并承认随着目标决策数量从一增加到四，即使单步能力不变，完整 Package 成功率也可能因重复决策的乘法负担而下降。

形式上，若每个目标决策的条件正确率都为 \(p\)，而深度 \(d\) 包含 \(d+1\) 个决策，则：

$$
P(\text{complete success}\mid d)
\approx
p^{d+1}.
$$

所以未来即使观察到：

$$
q_{D0}>q_{D1}>q_{D2}>q_{D3},
$$

也不能直接解释成：

> 模型潜在能力边界位于某两个深度之间。

当前设计最多测量：

> 在固定 Finance Core 上，模型承受连续一至四次目标微决策的 bounded sequential completion ability。

后续报告至少必须同时保留：

* 每一步条件成功率；
* 首个失败 Component；
* Component-specific hazard；
* 完整 Package 成功率；
* 任务级 Base 与机制资格。

不能只看最终 `Qualified / 6` 后套用旧 boundary bracket 算法。

```text
group
```

内的：

* fixed index vector；
* min/max index；
* semantic payload length；
* catalog lexical order；
* choice-handle order；
* action-ID order；
* argument-field order；
* tokenized length。

判定标准应是“相对于冻结基线不存在系统性恢复”，而不是“没有达到全局 480/480”。

## 3. 关闭 Recovery 合同矛盾

强制：

```text
selected Rule
==
current failed Rule
==
failure receipt Rule
==
retry Rule
```

任何 `state_precondition_valid=false` 的 Candidate 均不得：

* 进入 semantic mechanism qualified；
* 进入 Qualified；
* 被解释为有效 Recovery。

## 4. 实现真正的 step Runtime

下一版静态 fixture 应调用与未来 Runner 相同的：

```python
initialize(package)
step(state, action)
render_next_prompt(state)
finalize(state)
```

reference fixture 只能提供选择，不得提供已有的完整 Runtime events。

## 5. 补齐父对象重建

Package 与 Runner Input Validator 必须独立重算：

```text
reference operation
display/source handle mapping
Prompt state token
Observation effects
receipt links
mechanism report
reference path
topological order
```

并增加完整重哈希后的交叉父对象测试。

还不能写成：

> 已完成模型可见语义表去泄漏、Recovery 机制准入闭合和生产级动态交互。

## 对当前 Runner 预检授权

$$

$$

$$

当前有六条 state-precondition-invalid、mechanism-irrelevant 的 Recovery Choice 同时得到 Base=true 与 semantic mechanism=true。
