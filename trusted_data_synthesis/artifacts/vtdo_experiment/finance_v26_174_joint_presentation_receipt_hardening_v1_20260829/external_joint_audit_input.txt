## 3. 为什么当前 Shortcut Gate 没有发现

* 两两 rank 组合；
* rank 与 position；
* min/max/median 组合；
* 低阶线性组合；
* 模 Choice-count 的 affine／modular rule；
* action-ID、display-handle、Legend、Candidate 的交叉排序。

只有单变量和低阶联合规则均不超过结构基线，才能授权模型调用。

# 五、P0：Mechanism Qualification 回退为精确参考路径 Gate

v26.172 明确区分：


并规定 Failure Recovery 只要求：

* 真实 typed failure；
* selector 改变；
* Retry 成功；
* 事件顺序正确；
* 任务闭合；

而**不要求唯一 selector 或唯一 record path**。

v26.172 还确认：


均应为 semantic-mechanism true，只是不匹配 canonical path。

## 4. same-Rule 非规范 Recovery 的直接反例

对 20 条：

```text

```

的 Recovery Action：

```text

Base-valid                   14/20
Mechanism-qualified           0/20

```

这些轨迹：

* 对正确当前 Rule 执行修正；
* selector 确实改变；
* 真实 Retry 成功；
* 任务结果正确；
* failure/retry 顺序成立；

却因为不是 `current_rule.equals` 而被 Mechanism Gate 拒绝。

所以 v26.173 修复了：

```text
wrong Rule 不能冒充 Recovery
```

但同时重新引入了：

```text
只有唯一 canonical selector 才算 Recovery
```

### 科学影响

这会系统性低估：

$$
P(Q_{\mathrm{mech}}=1)
$$

并把合法的有效轨迹从 Qualified 集合中删除。未来所谓“能力深度下降”可能只是：

> 深层任务要求连续命中更多唯一 reference choice。

而不是：

> 模型没有执行目标机制。

### 必须修订

Mechanism Gate 应再次回到 family-specific causal predicates：

```text
Context：
真实应用当前状态决策并完成任务；
不把无关紧要的 Record 顺序等同于机制失败。

Reconciliation：
真实产生和消费 normalized references，并完成任务。

Recovery：
同 Rule、同 Failure Receipt；
selector 发生改变；
Retry 成功；
任务闭合；
不要求唯一 canonical selector。

Stopping：
Runtime-derived readiness；
verified stop；
没有 postcompletion call。
```

`reference_path_match` 继续保留，但只能作为独立诊断字段。

# 六、P0/P1：模型可见 Failure Receipt 没有成为真实 Runtime 父对象

报告声称 Recovery revision 必须绑定：

```text
current failed Rule
failure-receipt Rule
retry Rule
```



但源码实现只部分满足该主张。

## 1. 当前 Prompt Receipt 与 Runtime Receipt 并非同一个对象

正式 120 个 Recovery Prompt 均包含：

```text
actual_failure_receipt
```

但重算结果为：

```text
Prompt receipt 含 rule_handle                     0/120
Prompt receipt hash == Runtime failure_receipt_id 0/120
Runtime failure/retry 内部 receipt lineage       120/120
```

也就是说，Runtime 内部新生成的 failure 与 retry 共享同一新 receipt，这部分是正确的；但它并不是模型作出 Recovery 选择时看到的那个 receipt。

---

## 2. `rule_handle` 缺失时默认通过

Action Acceptance 中存在：

```python
receipt.get("rule_handle", current_rule) == current_rule
```

源码位置：

```text
semantic_table_trace_hardening.py
798–811
```

如果 Receipt 没有 `rule_handle`，系统直接回退到当前 Rule，因此缺失字段不会 fail-closed。

对 20 个 Reference Recovery Component 做变异：

```text
原始 reference accepted                     20/20
删除 actual_failure_receipt                  20/20 accepted
修改 receipt hash                            20/20 accepted
修改 receipt error                           20/20 accepted
显式插入 wrong rule_handle                    0/20 accepted
```

这证明当前接受条件只对“显式错误 Rule”敏感，并未绑定：

* exact receipt identity；
* exact failure error；
* exact failed selector；
* exact public receipt hash。

---

## 3. Runtime 在模型选择后重新制造 Failure

当前 `_execute_recovery_step()` 的顺序是：

```text
模型选择 revision
→ Runtime 重新执行 coarse query
→ 新生成 typed failure
→ 新生成 failure receipt
→ 再执行 selected selector
```

这不是严格的：

```text
模型先看到真实已发生 Failure
→ 基于该 Failure receipt 选择 Recovery
```

因此，当前最准确的说法是：

> Recovery Step 内部维护了 failure/retry lineage。

还不能说：

> 模型选择被精确绑定到此前可见的当前 Failure receipt。

### 必须修订

更干净的实现是：

```text
initialize
→ 真实执行 coarse query
→ 产生 typed failure
→ 持久化 exact public receipt
→ render Recovery Prompt
→ model selects revision
→ step validates against exact receipt
→ retry
```

并要求 Receipt 至少绑定：

```text
receipt_id
rule_handle
failed_selector hash
error_code
source Tool
```

缺少任何字段都必须拒绝，不能使用默认值补齐。

# 九、理论解释边界

v26.173 新增了未来字段：

```text
per-step conditional success
first failed target Component
target-Component hazard
complete Package success
task Base validity
Mechanism qualification
```

并明确：

```text
D0-D3 = bounded sequential target-decision depth
```

不从静态构造推断潜在能力边界。

这一收敛是正确的。

即使所有工程缺陷都修复，若 D0–D3 分别需要一至四次目标决策，而单步条件成功率恒为 \(p\)，Package 成功率仍可能自然表现为：

$$
P(\text{package success at depth }d)
\approx p^{d+1}.
$$

所以未来不能只用最终：

```text
Qualified / 6
```

构造“能力边界”。

必须同时报告：

* 每步条件成功率；
* 每个 Component 的到达分母；
* 首个失败位置；
* Component-specific hazard；
* Package-level Base；
* Package-level Mechanism；
* Package-level Qualified。

当前 Step Runtime 为这些估计提供了工程基础，但新发现的呈现联合泄漏、Mechanism 语义回退和 Receipt 身份缺口必须先关闭。
