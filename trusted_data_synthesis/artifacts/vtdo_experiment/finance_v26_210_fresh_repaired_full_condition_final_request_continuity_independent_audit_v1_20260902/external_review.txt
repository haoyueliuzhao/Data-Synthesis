# 一、本轮确实修复了 v26.208 的首个阻塞点

## 1. Final Provider 请求恢复了冻结的 JSON-explicit envelope

v26.208 的错误路径是：

```text
raw Final Prompt
  -> direct user message
  -> request
```

v26.209 改为：

```text
current Runtime result
  -> current raw Final Prompt
  -> v26.192 JSON-explicit envelope
       prompt_core
       prompt_kind = final
       provider_output_protocol
  -> canonical user message
  -> request
  -> certificate
  -> receipt
  -> shared transport seam
```

并继续绑定冻结的 Prompt Contract、Prompt Schema、v26.193 evidence set 和 v26.206 callsite census。

源码并非只在报告中声明修复。Final 编译器实际调用冻结的 `v192._render_prompt(...)`；新增测试也直接检查生成对象只有：

```text
prompt_core
prompt_kind
provider_output_protocol
```

并验证 `provider_output_protocol.contract_id` 等于冻结 Contract。

因此，上轮的：

```text

```

已经被直接关闭。

# 二、Correction 几何修订是必要且正确的

v26.209 进一步发现，v26.208 除了 Final envelope 缺失以外，还把原本属于诊断 side branch 的 120 个 typed rejection/Correction 当成了单条线性主轨迹的一部分。这造成了：

```text
phase                    match    mismatch
first Action               192           0
subsequent Action           216          72
Correction                   48          72
Final                         0         192
```

这并没有改变上轮“首个直接代码缺陷是 Final envelope”的判断，但说明 v26.208 的控制几何也需要恢复。

v26.209 的实现方式是正确的：

```text
main state
  -> reference Action
  -> commit into main path

copy of pre-Action state
  -> registered invalid Action
  -> typed rejection
  -> reference Correction
  -> commit only inside side branch
```

Correction branch 不再污染 reference main state，后续 reference Action 和 Final 因而重新与 v26.206/v26.193 完全一致。

对应源码修改也清楚地把 `branch_origin = copy.deepcopy(state)` 放在主 Action 之前；主状态始终提交 reference Action，invalid Action 和 Correction 则仅在 `branch_origin` 上执行。

此外，typed rejection 不再通过模糊的 `action_accepted` 属性猜测，而是要求实际返回 `PublicTypedRejectionObservation`。这是一个合理的窄修正。

所以本轮的 792 次调用应解释为：

```text
192 条 reference main paths
+ 120 个注册 Correction side-branch calls
= 792 个注册 callsites
```

而不是 192 条都实际经历了所有登记 rejection 的线性 Provider 轨迹。

# 三、动态非参考路径控制补足了“只会重放历史请求”的风险

v26.209 不仅比较注册 reference 路径，还保留了一个非参考 accepted-prefix 控制：

1. 从三候选 State 中选择一个当前合法、非 reference 的 Action；
2. 得到不同于 reference successor 的下一 State；
3. 下一次调用绑定新的非参考 State；
4. 继续完成该动态路径；
5. 从当前动态 Result 构造 Final JSON-explicit envelope；
6. 动态 Final request 必须与同一 Job 的 reference Final request 不同。

这说明 Runner 并不是简单读取历史 v26.193 Final request，而是根据当前 accepted prefix 动态重建合法 Final 请求。

该控制只能证明：

```text
dynamic nonreference construction is executable
```

不能证明：

```text
all model-reachable prefixes have been exhaustively enumerated
```

v26.209 没有越过这条解释边界，因此这一控制的科学定位是恰当的。

# 五、唯一明确问题：Markdown 中动态调用数写错

上传报告写道：

> “The control uses two Action dispatches and one Final dispatch.”



但正式 `dynamic_nonreference_branch_audit.json` 记录的是：

```text
diagnostic_action_dispatch_count = 4
diagnostic_final_dispatch_count  = 1
diagnostic_transport_dispatch_count = 5
```

这是因为所选 witness path 有四个 Action Component：第一个使用非参考 Action，后续三个继续完成当前动态路径，最后再发出一次 Final。

因此建议只修改叙述性 Markdown：

```diff
- The control uses two Action dispatches and one Final dispatch
+ The control uses four Action dispatches and one Final dispatch
```

或者更不易再次产生歧义地写为：

```text
The control uses one nonreference first Action, all remaining
current-prefix Action calls, and one Final call, for five
transport dispatches in total.
```

该问题属于：

```text
DOCUMENTATION_ERRATUM
```

而不是：

```text
FORMAL_GATE_FAILURE
```

正式动态工件、Gate、identity、Manifest 和 Artifact Root 不应因此修改或重算。只需修正文档及可能复制了该句的状态摘要。
