# 三、P0：Runtime 的纠错粒度与 Outcome 行不一致

这是当前最早、最本质的后继阻塞点。

## 1. Runtime 的 correction bound 是逐 Component 的

生产 Runtime 保存：

```python
public_feedback_by_component:
    dict[str, list[PublicTypedRejectionFeedback]]
```

当前纠错编号为：

```python
correction_attempt_index =
    len(feedback_for_current_component) + 1
```

一个 Component 的纠错成功后，Runtime 进入下一个 Component；下一个 Component 的 feedback list 又从空开始。也就是说，一个 D2／D3 Package 完全可能形成：

```text
Component A：
  first response rejected
  correction accepted

Component B：
  first response rejected
  correction accepted

Component C：
  first response accepted
```

并最终 Qualified。源码明确以 `public_feedback_by_component` 维护这种状态，且 correction attempt 是当前 Component 局部计数。

---

## 2. `CapabilityOutcomeRow` 只有一个纠错槽

当前行只有：

```text
correction_invoked
correction_feedback_id
corrected_action_accepted
correction_terminal_reason
```

没有：

```text
correction_count
correction_feedback_ids
component_attempt_rows
每个 Component 的首次响应结果
每个 Component 的纠错结果
有序 correction lineage
```

因此，一个 Job 若在两个 Component 上分别纠错，当前 Outcome 行不能无损表达：

* 两个 Feedback；
* 两个 correction commit；
* 两个首次失败；
* 各自的 Component identity；
* 纠错顺序。

这不是简单少一个统计字段，而是：

$$
\boxed{
\text{生成政策允许的轨迹类型超出了 Outcome schema 的表达能力。}
}
$$

---

## 3. \(q_{\text{first}}\) 的含义因此仍不唯一

当前合同写成：

$$
q_{\text{first}}
=
\frac{\sum\text{first\_attempt\_qualified\_valid}}{192}.
$$

但对于多步 Job，`first_attempt` 可能有三种解释：

1. 只指整个 Job 的第一个模型响应；
2. 指每个 Component 的第一次响应；
3. 指完整的零纠错生成政策。

只有第三种适合与 bounded-correction policy 比较：

$$
q_{\text{first}}
=
P(\text{完整 Job 在零纠错政策下 Qualified}),
$$

$$
q_{\text{bounded}}
=
P(\text{完整 Job 在冻结的逐 Component 有界纠错政策下 Qualified}).
$$

最小实现可以定义：

```text
first-policy Qualified
=
final Qualified
and correction_count == 0
```

而每一步的首次响应质量另行记录为 reached-component conditional success，不能再用一个 Job-level `first_action_*` 代表整条多步轨迹。

# 四、P0：经验 Outcome 行尚未绑定唯一 Job

## 1. 当前 `CapabilityOutcomeRow` 明确是 fixture-only

源码固定：

```python
fixture_only: Literal[True] = True
```

并且不包含：

```text
job_id
manifest_id
source_package_id
source_package_artifact_id
replica_index
raw_execution_id
result_id
attempt_trace_id
```

这完全可以作为本地 schema fixture，但不能直接成为未来经验 Outcome 行。

报告本身也明确说明：

```text
No future Job object or empirical row is materialized.
```

未来 192 只是前置冻结的分母几何，而不是已经形成的 Job 集。

---

## 2. estimator 只验证行数，没有验证 exact Job set

`evaluate_capability_estimands()` 当前只检查：

```text
eligible row count == expected eligible count
eligible row count == input row count
```

随后直接对布尔字段求和。它没有检查：

```text
row_id uniqueness
job_id uniqueness
exact Job-ID set equality
每个 Package × Replica 恰好一行
missing / duplicate / extra = 0
```

因此，在当前 core API 层面：

```python
evaluate_capability_estimands(
    [same_eligible_row] * 192,
    expected_eligible_job_count=192,
)
```

能够通过长度和 eligibility 检查并产生估计量。

这不会污染当前五条 fixture，因为 `OutcomeRowFixtureAudit` 额外要求五个不同 `row_id`。但它意味着：

$$
\boxed{
\text{固定“192”并不等于固定了 192 个唯一经验 Job。}
}
$$

在 Runner preflight 前，必须将 Outcome denominator 绑定为 exact Manifest Job set，而不是只绑定数量。

# 五、P0：ABI 无效仍可能被标记为已接受和 Qualified

当前 validator 强制：

```text
accepted => state_precondition_valid
```

却没有强制：

```text
accepted => first_response_abi_valid
```

因此，以下完整重哈希行可以通过现有通用约束：

```text
first_response_abi_valid                    false
first_action_state_precondition_valid       true
first_action_accepted                       true

first_attempt_base_valid                    true
first_attempt_mechanism_qualified           true
first_attempt_qualified_valid               true

correction_invoked                          false

final_base_valid                            true
final_mechanism_qualified                   true
final_qualified_valid                       true
```

`Qualified = accepted ∧ Base ∧ Mechanism` 和 final conjunction 都成立，且无 correction 分支的字段相等约束也成立；唯一缺失的就是 ABI 对 acceptance 的前置约束。

当前五条 fixture 全部采用：

```text
first_response_abi_valid = true
first Action rejected
correction_invoked = true
```

所以没有覆盖该分支。Fixture 构造可以从源码直接确认。

下一合同至少必须加入：

$$
\neg ABI_{\mathrm{valid}}
\Rightarrow
\neg Action_{\mathrm{accepted}}
\Rightarrow
\neg Qualified_{\mathrm{first}}.
$$

还应明确 ABI 无效时 Base／Mechanism 是：

* policy-level 显式失败；
* 还是 Verifier 不可评估。

不能让一个 `false` 同时承担这两种含义。

# 六、P1：五个 fixture 的名称没有绑定其因果形状

`fixture_kind` 是 Literal 标签，但 validator 没有按 kind 验证：

```text
same-current-invalid
different-current-invalid
stale-or-foreign
reference correction
nonreference correction
```

对应的 Action identity、第二响应关系和 terminal lineage。

例如 same-current 与 different-current 两条 fixture：

* 使用相同的 generic terminal reason；
* 没有保存第一次和第二次 Action ID；
* 没有字段证明两次 Action 相同或不同；
* 主要依靠 `fixture_kind` 字符串和不同 feedback hash 区分。

所以当前五条 fixture 可以支持：

> 五种预期字段组合能够通过序列化和通用约束。

不能单独支持：

> 五种真实 Runtime disposition 已经与 Outcome row 建立因果映射。

下一步应让 scripted Runner trace 生成 Outcome row，而不是手工用 `_fixture_values()` 填充。

此外，当前 fixture 集全部从“首次响应被拒绝并调用 correction”开始，没有覆盖：

```text
首次直接成功且无 correction
ABI-invalid terminal
首次 Action accepted，但后续任务仍失败
同一 Job 在两个不同 Component 上分别 correction
```

这些才是未来经验合同真正容易出错的分支。

# 七、P1：exact-Catalog scan 的“完整”需要收窄解释

扫描到目标 Component 前，`_state_at_component()` 始终用：

```python
public_only_select_hardened_action(prompt)
```

执行前序 reference/public-only Choice。

所以当前 480 行准确表示：

```text
32 Package
× 80 Component
× 6 Replica
under one public-only/reference predecessor prefix
```

而不是：

```text
所有合法 nonreference predecessor history
下的所有 reached current Prompt。
```

这不一定改变当前 rejection branch 计数，因为若干 acceptance 条件主要读取冻结 Component facts。但“完整 unchanged exact Catalog scan”应收窄为：

> complete reference-prefix component/candidate acceptance scan。

未来 Runner preflight 应补充以下二者之一：

1. 对全部 scripted accepted prefix classes 重建 reached-state surface；
2. 独立证明 Action Acceptance 对允许的 predecessor history 不变。

# 十、最终结论

v26.178 并不是又一次“修了一个地方、证据仍完全无效”的阶段。它已经真实关闭了 v26.177 的三个证据身份问题：

$$
\boxed{
\text{Host 反事实真实执行}
+
\text{诊断对象真实重物化}
+
\text{Outcome fixture 真实构造}
}
$$

因此应当保留其成果，不再回退到 Public Feedback、Presentation 或任务构造层。

当前阻塞已经非常集中：

$$
\boxed{
\text{局部 fixture Outcome}
\;\not\Rightarrow\;
\text{完整的 192-Job 经验 Outcome}
}
$$

具体缺口是：

1. Runtime 可以在多个 Component 上分别纠错，Outcome 行却只有一个 correction 槽；
2. Outcome 行不绑定 Job、Package、Replica 或 Manifest；
3. estimator 不检查 192 个唯一 Job 的 exact set；
4. ABI 无效仍可能被通用 validator 接受为成功 Action；
5. fixture 没有覆盖无纠错成功和多 Component 纠错。

所以最新审计结论不是继续做另一个庞大的理论修订，而是：

> **保留 v26.178，并用一个 credential-free、Job-bound、multi-step 的 Runner preflight，将现有局部机制真正装配成未来 192-Job 实验对象。**

该 preflight 通过独立审计后，才决定是否执行在线 Development；在此之前，模型行为、能力深度、频率、State、VTDO 和训练仍保持未授权。
