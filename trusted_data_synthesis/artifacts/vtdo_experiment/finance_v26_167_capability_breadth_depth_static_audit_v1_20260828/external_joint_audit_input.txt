# 本轮理论修订、项目代码与任务合成方案联合审计

## 一、审计结论

本轮“**能力广度 × 能力深度**”修订是必要的，而且定位到了当前实验最上游的真实缺口：

$$
\boxed{
\text{能力是否可观测，首先取决于任务集合是否覆盖了能力边界。}
}
$$

但是，当前 v26.166 的历史审计与其 prospective 后继必须分开判断：

| 审计对象                                     | 结论                  |
| ---------------------------------------- | ------------------- |
| v26.166 对现有 48 个 Cell 的结果分层              | **通过**              |
| 10/8/3/27 的支持分类及不越级解释                    | **通过**              |
| 当前 27 个多状态 Cell 不直接升级为 VTDO Arm          | **通过**              |
| 将无支持与弱支持记录为 Coverage Gap                 | **基本通过**            |
| 现有 Fresh Confirmation Protocol           | **不通过，不足以承载能力观测修订** |
| 旧 Easy／Frontier／Hard 作为能力深度              | **不成立**             |
| 当前任务集合用于判断能力强弱                           | **证据不足**            |
| 当前直接进入 fresh VTDO admission confirmation | **不建议执行**           |

v26.166 正确冻结了：

```text
valid_support_absent                 10
single_valid_observation              8
observed_single_state_support         3
observed_multistate_support          27
```

并且只允许 27 个 Cell 获得 `state-support existence`，当前 VTDO-admitted Cell 仍为零。

但其后继确认协议仍然只按：

```text
mechanism
tier
generation_condition
```

分层，没有匹配任务组、能力深度、D0 观测锚、深度变换合同和每层独立任务数。

因此，最准确的决策是：

$$
\boxed{
\text{保留 v26.166 全部历史工件，}
}
$$

但：

$$
\boxed{
\text{不要直接消费当前 }
fresh\_vtdo\_admission\_confirmation\_preflight\_only.
}
$$

应通过新的外部审计决策，将 prospective 后继收敛为：

```text
capability_breadth_depth_task_synthesis_and_static_audit_only
```

该阶段必须零 Provider 调用，只构造和审计新的任务观测体系。

# 四、对本轮理论修订的最终审计

“广度 × 深度”是正确修订，但其角色必须被严格限制为：

$$
\boxed{
\text{任务观测设计}
}
$$

而不是：

* 完整 Agent 能力分类学；
* 模型潜在能力向量；
* 通用 IRT；
* 自动课程学习；
* 动态难度优化；
* 全任务覆盖理论。

它只需要解决一个有限问题：

> 对四个现有目标能力，任务集合是否包含最低可观测锚、过渡区和压力层，并且深度变化主要来自目标能力负担，而不是其他能力和任务实例同时变化？

这项上游修订应当优先于现有 fresh VTDO confirmation。

# 五、详细任务合成方案

## 1. 三种概念必须分开

建议正式冻结：

| 对象                        | 含义                |
| ------------------------- | ----------------- |
| `DifficultyTier`          | 历史全局复杂度标签，仅用于历史重放 |
| `ObservationDepth`        | 新的、单能力受控深度        |
| `EmpiricalBoundaryStatus` | 模型在当前深度梯度上的经验观测结论 |

新增：

```python
class ObservationDepth(str, Enum):
    D0_OBSERVABILITY_ANCHOR = "d0_observability_anchor"
    D1_BASIC = "d1_basic"
    D2_COMPOSITIONAL = "d2_compositional"
    D3_STRESS = "d3_stress"
```

禁止将旧：

```text
easy_control
frontier
hard_control
```

重命名后直接作为新深度。

---

## 2. 使用“匹配核心 + 深度覆盖层”

对能力 \(k\) 和匹配任务组 \(g\)，先构造共享金融任务核心：

$$
b_{k,g}.
$$

再构造四个深度变体：

$$
x_{k,g,d}
=
\operatorname{ApplyOverlay}
\left(
b_{k,g},
\Delta_{k,d}
\right),
\qquad
d\in\{D_0,D_1,D_2,D_3\}.
$$

同一组的四个任务必须共享：

```text
capability_family_id
核心金融问题
Evidence IDs 与 Evidence Versions
canonical expected result
Answer Schema
Oracle Program skeleton
Verifier Contract
Tool environment
Prompt / Action / Final Grammar
model / Thinking profile
bounded generation policy
resource ceiling
```

只有 `DepthDeltaContract` 注册的目标能力字段允许变化。

---

## 3. 推荐使用固定最大骨架，而不是让总任务长度一起增长

为了真正隔离目标能力，建议先构造能够承载 D3 的最大公共骨架：

```text
MatchedTaskSkeleton
```

D0–D3 使用相同：

```text
Evidence 数量
Program node 数量
Tool set
操作总槽位
Verification 结构
Final Answer
Candidate 数量上限
资源合同
```

不同深度只改变：

```text
哪些槽位需要目标能力
目标能力槽位的依赖与歧义程度
```

例如 D0 中未启用的槽位不是被删除，而是变成：

* 唯一合法动作；
* identity normalization；
* 不触发的 recovery slot；
* 明确非终止状态。

这样可以避免：

```text
D3 更难
```

只是因为：

```text
D3 有更多 Evidence、更多 Tool、更多 Program node。
```

形式化为：

$$
L_k(x_{d+1})>L_k(x_d),
$$

而对非目标负担：

$$
N_{-k}(x_{d+1})=N_{-k}(x_d),
$$

或仅允许预注册的极小容差。

注意：要求的是**构造负担单调**，不是强迫经验成功率严格单调。

# 六、四项能力的深度设计

## 1. Context-conditioned Action

### 目标负担

```text
context-sensitive decision-slot count
candidate semantic ambiguity
context dependency depth
delayed public-context update
irreversible choice count
```

建议使用固定三槽决策骨架：

| 深度 | 激活方式                                |
| -- | ----------------------------------- |
| D0 | 1 个真实上下文决策槽；两个公开合法候选；其余槽唯一可选        |
| D1 | 1 个决策槽，但有 3–4 个近似合法候选；需组合两个公开字段     |
| D2 | 2 个上下文决策槽；第二个依赖第一次 Tool Observation |
| D3 | 3 个决策槽或两个不可逆槽；含延迟上下文更新与候选语义接近       |

必须固定：

```text
Evidence
最终答案
Tool set
Program 总槽位
Verification
Recovery
Stopping
```

D0 不能退化为单 Candidate，否则没有测量目标能力。

---

## 2. Semantic Reconciliation

### 目标负担

```text
non-identity normalization axes
target-record count
normalization-reference consumption
downstream fan-out
raw-evidence bypass constraints
```

建议使用固定记录数和固定 normalization operation 数：

| 深度 | 激活方式                                          |
| -- | --------------------------------------------- |
| D0 | 所有记录都通过 normalization；仅 1 个语义轴需要非 identity 变换 |
| D1 | 2 个非平凡语义轴，例如单位和期间基准                           |
| D2 | 多个目标记录；normalization refs 被两个下游节点消费           |
| D3 | 定义、单位、期间等多轴同时变化；多节点持续消费；raw bypass 无法通过       |

其余记录在低深度执行 identity normalization，从而保持：

```text
记录数
Operation 数
Program 长度
Tool set
最终答案
```

一致。

不得通过增加检索难度或 distractor 数量来冒充 Reconciliation 深度。

---

## 3. Failure Recovery

### 目标负担

```text
typed failure count
recovery branching factor
recovery dependency depth
failure-type diversity
downstream consequence
```

固定一个最多容纳三次 Recovery 的骨架：

| 深度 | 激活方式                                                |
| -- | --------------------------------------------------- |
| D0 | 1 次真实 typed failure；只有 1 个明显合法修正                    |
| D1 | 1 次 typed failure；2 个表面合理恢复候选，只有一个满足 Retry Contract |
| D2 | 两阶段恢复；第二次动作依赖第一次修正后的公共状态                            |
| D3 | 两种 typed failure；多个恢复候选；恢复路径影响后续 Program 与验证        |

必须固定：

```text
Evidence
Oracle Program core
最终答案
检索条件
Verification
资源上限
```

当前 legacy Recovery Easy 的 source-level `required_recovery_count=0`，因此不能直接充当新 D0。新 D0 必须具有真实且模型拥有的：

```text
typed failure → revision → success
```

链。

---

## 4. State-dependent Stopping

### 目标负担

```text
near-terminal state count
completion-predicate count
verification/completion separation
tempting-continuation count
delayed final-readiness depth
```

固定一套具有多个公共检查点的骨架：

| 深度 | 激活方式                                                 |
| -- | ---------------------------------------------------- |
| D0 | 一个明确完成状态；完成后仍有一个可见但不应执行的合法动作                         |
| D1 | 一个 near-terminal 与一个 terminal；必须等待 Verification      |
| D2 | Verification 与 Completion 分离；存在两个表面合理的 near-terminal |
| D3 | 多个近似完成检查点；多个合法 continuation；全部条件满足后才可 Final          |

必须固定：

```text
Evidence
最终答案
主 Program
Tool set
Recovery
检索条件
```

不能再用“Program 从 1 节点增加到 5 节点”作为 Stopping 深度的主要来源。

# 八、任务组规模与划分

## 推荐方案：64 个静态任务

$$
4\text{ capabilities}
\times
4\text{ matched groups}
\times
4\text{ depths}
=
64\text{ tasks}.
$$

每项能力：

```text
Development groups      2
Reserved Confirmation   2
```

即：

```text
Development tasks       32
Confirmation tasks      32
```

但 Confirmation 最终只执行由预注册规则选中的两个相邻深度。

## 最小降级方案：48 个任务

若静态 Evidence Capacity 不足：

$$

$$

每项能力：

```text
Development groups      2
Confirmation group      1
```

这个方案可以作为 pilot，但确认的任务级独立性更弱。

选择 64 还是 48，只能由模型调用前的静态 Evidence Capacity Audit 决定。

# 九、组级新鲜性与暴露规则

匹配任务故意在组内共享 Evidence，因此不能沿用“所有任务间零重叠”的旧新鲜性规则。

## 组间与历史

必须在以下通道零重叠：

```text
core semantic signature
Evidence identity
Evidence Version
mechanism instance
source record
group semantic identity
```

## 组内

允许并要求共享：

```text
core semantic signature
Evidence set
canonical answer
Verifier
Program skeleton
Tool environment
```

但要求：

```text
variant task ID 不同
depth ID 不同
overlay ID 不同
DepthDelta ID 不同
```

统计单位为：

$$
\boxed{
\text{matched group 是一级独立单位}
}
$$

D0–D3 是组内配对变体，rollout 是二级重复。

## Exposure Block

同组 D0–D3 必须：

* 在任何 Provider 调用前共同冻结；
* 使用预提交的调用顺序或随机化计划；
* 不根据浅层结果修改深层任务；
* 任一变体曝光后，整组标记为 exposed；
* Development 代码不能访问 Confirmation Payload；
* Confirmation 组在 Development 结束前保持 sealed。

# 十、两阶段在线观测协议

## 阶段 A：牺牲性广度—深度扫描

使用两个 Development group。

每项能力冻结一个**能力中性的观测条件**，D0–D3 和两个 group 完全相同。

不要同时运行：

```text
Unconditional
structured_direct
search_then_structured
search_then_open
```

否则深度又会与 Path 条件混合。

观测条件必须通过：

```text
target_authority_preservation
target_mechanism_noninterference
```

Context-conditioned Action 可能需要 neutral-unconditional 条件；其他能力可以使用经审计的 `structured_direct`。不能为了统一形式而消除目标决策。

推荐分母：

$$
4\times4\times2\times6
=
192\text{ Jobs}.
$$

本阶段只测量：

* D0 是否存在非零且可重复的有效支持；
* D3 是否仍全部过易；
* 支持大致在哪两个相邻深度下降；
* 梯度是否非单调或组间冲突。

禁止：

* State Distribution 选择；
* VTDO；
* Contribution；
* Student；
* Compiler intervention；
* 根据当前 27 个 Cell 选任务。

---

## 阶段 B：预注册边界确认

在 Development 执行前冻结 `BoundarySelectionContract`。

推荐定义组级支持：

```text
supported(group, depth):
    N_qualified >= m_dev
```

例如 pilot 可预注册：

```text
m_dev = 2 / 6
m_confirmation = 3 / 8
```

这只是建议的设计默认值；最终必须在任何模型调用前固定，不能由 Development 结果调整。

每项能力只允许四种结论。

### 1. `below_observation_floor`

两个 Development group 的 D0 均未达到支持要求。

允许结论：

> 当前最低任务深度仍未建立该能力的可观察支持。

禁止结论：

> 模型完全没有该能力。

### 2. `above_observation_ceiling`

两个 group 在 D3 仍达到支持要求。

允许结论：

> 当前深度上限不足以定位能力边界。

当前 VTDO 主线不必继续无限构造更难任务。

### 3. `boundary_bracketed`

存在相邻深度：

$$
D_d,\ D_{d+1},
$$

且两个 Development group 均表现为：

```text
lower depth supported
upper depth unsupported / weak
```

并且没有更深层重新出现稳定支持。

只执行 Reserved Confirmation 组中的这两个深度。

推荐确认分母：

$$
4
\times2\text{ depths}
\times2\text{ confirmation groups}
\times8
=
128\text{ Jobs}.
$$

### 4. `nonmonotonic_or_confounded`

如果：

* D0 失败但 D1/D2 成功；
* 两个 matched group 呈相反趋势；
* 深层重新恢复且跨组可复现；
* Nuisance Signature 不一致；

则停止。

不能把它解释为模型“非常随机”，也不能重新排列深度或调支持阈值。

# 十一、确认之后仍不能直接做 VTDO

即使能力边界确认通过，也只说明：

```text
在固定能力 × 深度上，
有效支持可被稳定观测。
```

不应复用同一 Confirmation 数据完成：

```text
状态选择
→ 状态重加权
→ VTDO 效果主张
```

正确顺序是：

```text
Breadth–Depth Development
→ Boundary Confirmation
→ 冻结能力 × 深度准入规则
→ 全新 State-Support Population
→ valid-only Mapper
→ 最小锚定状态重加权
→ Equal-token Student
```

能力边界任务和 VTDO State-Support 任务应是不同的新鲜总体。

# 最终结论

当前不足不是“任务数量不够”这么简单，而是：

$$
\boxed{
\text{现有任务集合缺少匹配、单轴、含低难度锚的能力深度梯度。}
}
$$

旧 Easy／Frontier／Hard 同时放大了多种任务负担，跨 Tier 又使用不同金融实例，因此无法判断零有效支持究竟来自：

* 目标能力不足；
* 当前任务下限过高；
* 非目标能力负担；
* 单一任务实例；
* 多能力共同越界。

下一步不应继续围绕当前 27 个多状态 Cell 做确认，也不应新增更多泛化理论。

应先构造：

$$
\boxed{
4\text{ 个现有能力}
\times
4\text{ 个受控深度}
\times
\text{多个匹配任务组}
}
$$

并通过 Joint Compilation 证明：

$$
\boxed{
\text{深度变化确实只来自目标能力负担，}
}
$$

然后用 Development 扫描和 Reserved Confirmation 定位有限的经验能力边界。

只有在新鲜任务上确认某个固定能力—深度区域同时具有：

```text
有效支持
任务级复现
状态多样性
```

后，才允许进入最小的有效状态重加权实验。
