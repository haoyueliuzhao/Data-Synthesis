# 四、P0：Base Validity 与 Mechanism Qualification 实际使用同一 reference 判定

这是当前最根本的问题。

源码位置：

```text
src/trusted_synthesis/core/task/
public_semantic_capability_depth.py
```

关键逻辑位于约 783–874 行：

```python
checks[component.component_key] = (
    semantic_key == component.reference_semantic_key
)

base_valid = program_valid and all(checks.values())

mechanism_qualified = all(
    selected_key == component.reference_semantic_key
    for component in components
)
```

因此，每个目标组件的：

```text
selected == reference
```

同时进入：

* Base Validity；
* Mechanism Qualification。

这意味着：

$$
V_{\mathrm{base}}
$$

和：

$$
Q_{\mathrm{mech}}
$$

在目标选择层没有独立性。

任意非 reference Choice 都会被直接设为：

```text
Base-invalid
Mechanism-unqualified
Qualified-invalid
```

无论真实 Program 是否仍然正确。

这违反了当前理论已经冻结的基本分解：

$$
V_{\mathrm{qualified}}
=
V_{\mathrm{base}}
\land
Q_{\mathrm{mech}},
$$

其中 Base 应表示任务正确性，Mechanism 才表示目标机制是否出现。

# 五、P0：“Real Task Execution”尚未覆盖完整公开任务有效性

## 1. 当前 Base 只验证 Raw Program 输出，没有执行 Public Answer Projection

六个使用 `compare` 的 Finance Core 中，真实 Executor 输出均为：

```json
{
  "difference": "...",
  "higher_ref": "evidence:finance:..."
}
```

但公开任务明确要求：

```text
higher_ref 必须是 Italy / Sweden / 某个公开日期标签
```

源 `TypedAnswerProjectionContract` 已经保存了：

```text
内部 Evidence ID → 公开标签
```

映射，但 v26.170 的 `SemanticExecutionResult.base_valid` 没有应用该投影，也没有检查：

* 公开答案字段值；
* Final Grammar；
* Citation；
* Reference Identity；
* Answer Semantics。

结果是：

```text
compare Finance Cores                         6
Raw higher_ref 仍为内部 evidence ID           6
应用公开 Answer Projection                    0
```

所以报告中的：

```text
Base-valid baselines 32/32
```

不是项目既有 Verifier vNext 意义下的完整 Base Validity，而只是：

```text
local raw-program-and-reference-contract valid
```

报告自己也限定这些执行只建立本地构造性，不是模型行为。
但字段命名仍然会造成证据层级越级。

建议改名为：

```text
local_program_contract_valid
```

在完整 Answer Projection、Final、Citation 和公共语义检查接入前，不要使用正式 `Base-valid` 名称。

## 2. 多个目标组件没有实际进入 Program 执行

`execute_semantic_runtime()` 实际处理：

```text
select_operator
select_records / select_scope
select_projection
reconcile_record
revise_selector
stop_or_continue
```

但没有执行分支处理：

```text
consume_outputs
assess_readiness
```

因此：

### Reconciliation `consume_outputs`

模型选择的：

```text
output_handles
```

没有进入所构造的 `TaskProgram`。

`build_selected_program()` 始终创建：

```text
一节点 Program
+ 两个 Evidence InputRef
```

并没有执行公开 Task 中的 normalization nodes，也没有让 terminal Operation 消费 normalized output references。

这解释了为什么：

```text
reconciliation.consume 的 4/4 增量反事实
仍然 Program-valid。
```

### Stopping `assess_readiness`

Readiness Choice 不改变 Program、Verification 或 terminal 状态；它只通过 exact-reference component check 决定 Base 值。

所有：

```text
24 个 assess_readiness 非 reference alternatives
```

均仍然 Program-valid。

### Failure Recovery

`deterministic_failure_observed=true` 是预填 Public State Fact；Runtime 没有先真实执行失败查询再生成 Observation。Recovery 选择会修改 record selection，但 failure 本身不是本轮 Program 执行的结果。

### 结论

当前是：

> 真实执行一个一节点 Finance Program，并在其外部附加若干选择合同。

还不是：

> 每个目标能力组件都通过真实 Runtime 因果地改变 Finance Program 与任务结果。

# 六、P0：可见 `padding` 产生了新的 reference 捷径

报告写道，每个 Candidate 的规范 JSON 编码被填充为等长，并认为 Replica 之间只改变 action ID、顺序、位置和等长 padding。

但当前：

```python
PresentedPublicCandidate.padding
```

本身被序列化进模型可见 JSON。

因此，虽然三条 Candidate 的**总字节数相同**，模型仍然可以直接看到：

```text
padding 字符串有多长
```

这恰好反向暴露了原始语义 Payload 的长度。

独立统计结果：

```text
target States                                  80
有唯一 reference-padding 长度的 States         34
replica presentations                         480
暴露唯一 reference-padding 长度的 presentations 204
```

更严重的是，存在稳定的 decision-kind 捷径：

```text
assess_readiness：
  选择 padding 最长项 → 12/12 State 正确

stop_or_continue：
  选择 padding 最长项 → 8/8 State 正确

select_projection：
  选择 padding 最短项 → 4/4 State 正确

select_operator：
  选择 padding 中位项 → 8/10 State 正确
```

一个只读取：

```text
decision_kind + padding 长度
```

而不理解金融语义的策略，就能在至少：

```text
32 / 80
```

个目标状态上确定 reference。

### 判定

$$
\boxed{
\text{Position balance 通过}
\not\Rightarrow
\text{Presentation neutrality 通过}
}
$$

当前 Replica Presentation Audit 没有检查：

* padding-only selector；
* raw semantic length；
* padding rank 与 reference 的关联；
* tokenized padding cue。

这是进入模型 Runner 前必须修复的 P0。

# 七、P1：目标能力隔离仍主要由声明字段完成

当前：

```python
TargetComponent.target_capability_component: Literal[True]
```

而：

```python
IsolatedTargetLoad.non_target_choice_state_count: Literal[0]
```

`TargetIsolationAudit` 随后只是统计：

```text
组件数量
Literal[True]
Literal[0]
```

它没有独立判断某个组件的 Decision Kind 是否真的属于目标能力。

一个直接反例是：

```text
Semantic Reconciliation D3
新增组件：
  reconciliation.operator
  decision_kind = select_operator
```

`select_operator` 本质上更接近 Context／Operator Selection，而不是新增的 Reconciliation 负担。

当前四类梯度实际上是：

```text
Context：
operator → records → projection → scope

Reconciliation：
mapping 1 → mapping 2 → consume → operator

Recovery：
revision 1 → revision 2 → revision 3 → revision 4

Stopping：
readiness 1 → readiness 2 → readiness 3 → stop
```

所以当前 `1 / 2 / 3 / 4` 更准确地表示：

```text
注册的 target-labeled microdecision 数
```

而不是已经验证的单能力深度。

此外，所有组件 Prompt 都是独立预构造的；没有组件依赖字段或由上一个模型选择产生的动态 Public State。因此 `D2_COMPOSITIONAL` 并没有真正证明 compositional dependency。

# 八、P1：Reference 与 Source 父绑定仍可被完整重哈希后绕过

v26.170 的 Public Task 重建比 v26.169 明显增强：Catalog 会从 exact Finance Core 重建 `PublicSemanticTask` 并比较规范字节。报告中的 32 个 instruction mutation 全部拒绝是成立的。

但当前破坏性审计只覆盖了 Public Task mutation，没有覆盖以下父对象。

我构造了重新计算所有受影响身份的变异对象，当前 Validator 接受：

### 1. 错误 Reference Choice

将一个 Stopping readiness 组件的 reference 改为错误 verdict，随后重算：

```text
Component ID
Replica Presentation IDs
Baseline Result
Package Artifact ID
Group ID
Catalog ID
```

最终结果：

```text
Catalog accepted                      true
public-only selector agrees           false
baseline program_valid                true
baseline base_valid                   true
baseline mechanism_qualified          true
```

也就是说，Package Validator 没有从 Public Prompt 重新计算 reference。

### 2. 交叉 `source_program_verification_hash`

将一个 Package 的：

```text
source_program_verification_hash
```

替换为另一个 Package 的值并完整重哈希，Catalog 仍被接受。

### 3. 伪造 Source Public Hash

修改：

```text

source_public_evidence_semantic_hash
```

### 判定

正式 v3 Catalog 当前是内部一致的；这里不是声称正式工件已遭污染。

问题是：

$$
\boxed{
\text{Schema 尚不能独立保证所有语义父绑定}
}
$$

下一阶段若依赖这些强类型对象做重建，仍存在 crossed-parent 被接受的风险。

# 十、P2：Candidate Grounding 不是 Candidate Legality

当前 Candidate Grounding 检查的是：

> 参数中的每个 scalar 是否曾出现在 Public Task、Current State 或 Operator Catalog。

这只能证明**词汇来源公开**，不能证明参数组合是该 Operation 下的合法动作。

直接统计发现：

```text
12 个 select_operator Candidate
不属于对应 operation.allowed_operator_ids
```

例如某些 Operation 只允许：

```text
compare, difference
```

但 Candidate 中仍加入：

```text
growth
```

若这些本来就是故意的错误选项，可以保留；但应明确称为：

```text
publicly grounded distractors
```

而不是：

```text
public legal-action candidates
```

否则会把“排除明显非法选项”的能力混入目标能力深度。

# 十一、当前结果应该如何解释

## 可以支持

v26.170 已经可信建立：

1. 一个内容寻址的 Public Finance Task Projection；
2. 一个不直接读取 Host reference 的确定性 public-only selector；
3. 80 个具有三个公开语义选项的目标状态；
4. 一个真实执行一节点 Finance Program 的基线；
5. 六 Replica 的候选位置平衡；
6. Public Task 与 Finance Core 的规范重建；
7. 零 Provider、零模型行为的静态构造证据。

## 不能支持

当前还不能支持：

1. 完整 Finance Base Validity；
2. Base 与 Mechanism 的独立判定；
3. 48 个新增组件的任务级因果必要性；
4. 纯单能力 D0–D3 深度梯度；
5. 无呈现捷径的模型可见任务；
6. Semantic Reconciliation 的真实 normalization-output consumption；
7. State-dependent Stopping 对真实执行状态的判断；
8. 192 个 Job 的成功率能够解释为能力边界。

如果现在执行模型，观察到的深度曲线将至少同时受到：

$$
\text{每步 reference 选择准确率}
$$

$$
\text{组件数量的乘法效应}
$$

$$
\text{padding 捷径}
$$

$$
\text{异质微决策类型}
$$

共同影响。

即使每个微决策的真实能力恒定为 \(p\)，Package 级成功率也会近似：

$$
q_d \approx p^{d+1},
$$

从而机械地产生随深度下降的曲线。这不能自动解释为潜在能力边界下降。

# 十二、建议的修订顺序

当前报告授权的唯一后继是：

```text
capability_observation_public_semantic_execution_
development_runner_preflight_only
```

并禁止后继修改 Public Semantic、Target Component、Candidate 和 Presentation Salt。

由于本次发现恰恰要求修改这些对象，因此**不应消费当前后继授权**。

建议新的零调用阶段：

```text
capability_observation_validity_separation_
presentation_deleak_and_causal_component_reaudit_only
```

## 1. 重新分离 Base 与 Mechanism

正式定义：

```python
base_valid = (
    task_program_verified
    and answer_projection_complete
    and terminal_verification_complete
    and public_answer_semantically_valid
    and postcompletion_control_passed
)

mechanism_qualified = target_mechanism_verifier(trace)

qualified_valid = base_valid and mechanism_qualified
```

禁止把：

```text
selected == reference
```

直接加入 Base。

对于反事实，应允许出现：

```text
Base=true, Mechanism=false
```

这正是验证两者真正独立的必要测试。

## 2. 让每个组件通过真实后果影响任务

### Context

Operator、Record、Projection、Scope 必须分别影响：

```text
实际 Program
实际 Evidence operands
实际 Answer Projection
实际公开查询范围
```

### Reconciliation

必须真实执行：

```text
normalization nodes
→ 产生 normalized operation refs
→ terminal operation 消费这些 refs
```

`consume_outputs` 不能只作为 reference equality check。

### Recovery

必须先真实产生：

```text
typed failed Observation
```

再根据模型选择修改实际 selector；不能只在 State Facts 中声明 failure 已发生。

### Stopping

Readiness Receipt 必须由已执行 Program 和 Verification 动态生成。Wrong verdict 必须改变可停止性或终局，而不是只触发 exact-reference check。

最稳妥的方案是：

* 不在模型可见 Candidate 中序列化 `padding`；
* 或完全固定公共 Candidate Schema 与值宽度；
* 不把字节等长本身误当作中性。
