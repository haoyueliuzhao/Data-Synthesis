# v26.191 最新在线测试审计

## 总体判定

$$
\boxed{\text{v26.191 Minimal Exact-route Online Diagnostic：PASS}}
$$

**没有发现能够推翻本轮在线诊断结论的 Blocking defect。**

本轮已经可信地定位了**当前时点、当前精确冻结 Prompt**的 HTTP 400 原因：

$$
\boxed{
\texttt{response\_format=json\_object}
\quad+\quad
\text{Prompt 未显式要求 JSON}
}
$$

更准确地说：

```text
当前 D4 请求的直接拒绝原因：
    已定位

v26.188 历史 192×HTTP 400 的高度可信解释：
    同一 Prompt / response-format 不匹配

v26.188 当时服务端返回的精确历史原因：
    仍未恢复
```

这个边界与报告一致，没有把当前复现错误地包装成历史响应正文恢复。本次仍以 Git 树、不可变工件、脱敏恢复记录和服务器复核为实验依据。

## 一、在线诊断链条有效

本轮使用全新的工程诊断身份，没有复用 v26.188 Job ID，也没有把诊断请求混入旧 192-Job Capability 分母。最终只执行 6 次 HTTP 请求、自动重试为零，旧 Job 重跑与 RecoveryJob 均为零。

六步结果构成了很清楚的定位链：

| 步骤                                 |  结果 | 排除或定位的因素                                    |
| ---------------------------------- | --: | ------------------------------------------- |
| D0 `GET /models`                   | 200 | 当前凭证可访问 API，目标 Flash ID 可见                  |
| D1 官方 `/chat/completions` 最小请求     | 200 | 当前官方路由正常                                    |
| D2 历史 `/v1/chat/completions` 同字节请求 | 200 | `/v1` 路径别名当前仍可用                             |
| D3 完整七字段 + 最小 JSON Prompt          | 200 | model、Thinking、16K、JSON mode、sampling 组合可接受 |
| D4 精确首个 v26.188 Prompt 和请求体        | 400 | 当前冻结 Prompt 触发请求合同拒绝                        |
| D5 同 Prompt UTF-8 长度、显式要求 JSON     | 200 | 长 Prompt 与完整参数形状本身可接受                       |



其中 D4 的正式 typed error 是：

```text
Prompt must contain the word 'json' in some form to use
'response_format' of type 'json_object'.
```

该错误对象绑定了 HTTP 400、195 字节响应正文及其 SHA-256；没有保存未经检查的原始正文、Authorization、Cookie 或私有推理。

DeepSeek 当前官方 JSON Output 文档也明确要求：设置 `response_format={"type":"json_object"}` 时，system 或 user Prompt 中必须包含 “json” 字样，并说明期望的 JSON 输出形式。([DeepSeek API Docs][1])

因此，**当前 D4 的拒绝原因已经由 Provider typed error 直接给出，不只是从 D4/D5 的相关性推测出来的。**

## 二、D5 控制的解释需要保持准确

D5 与 D4 并不是只相差一个单词的严格单变量反事实。D5 使用的是另一段安全合成文本，因此：

* 它能排除“Prompt UTF-8 长度过长”；
* 它能证明完整七字段请求形状与长 JSON-explicit Prompt 可以成功；
* 它不能单独证明 D4 其余所有文本内容都无影响。

但这不构成当前结论的缺陷，因为 D4 的服务端错误消息已经直接、具体地指出缺少 JSON 指令；D5 在这里承担的是**长度与完整参数组合的辅助控制**，而不是唯一的因果证据。报告也明确说明 D5 请求体因转义字符更少而短于 D4，没有把二者描述为完整请求字节等长。

## 三、历史解释边界处理正确

v26.191 没有追溯修改 v26.188：

```text
q_job                           0/192
q_semantic_given_model_endpoint null
```

也没有把 D0–D5 诊断行混入 Capability Outcome。

报告对证据层级的区分是合理的：

1. **当前直接观测**：精确首个冻结 Prompt 因缺少 JSON 指令被拒绝；
2. **冻结源码事实**：报告记录所有 192 个首 Prompt 都存在相同词法缺失；
3. **历史解释**：该共享缺失强烈支持 v26.188 全量 HTTP 400 的共同原因；
4. **仍不可恢复**：v26.188 当时的原始 HTTP 400 response body，以及 Provider 服务端执行时状态是否与现在完全相同。

因此，正式字段继续保持：

```text
historical_exact_cause_recovered = false
```

是正确的。

换言之，当前允许说：

> 现在可以用同一冻结请求内容稳定复现相同类型的拒绝，而且错误消息精确指向缺少 JSON 指令。

但仍不应说：

> 已经恢复了 2026 年 8 月 31 日 v26.188 每一个请求当时的原始服务端错误正文。

## 只允许修改

在所有使用：

```json
{"response_format": {"type": "json_object"}}
```

的模型可见 Prompt 中加入统一、明确的协议指令，例如：

```text
Return exactly one valid JSON object matching the response ABI.
Do not return Markdown or surrounding prose.
```

这应当加在**共享 Provider-facing protocol envelope**，而不是改写金融任务问题文本。这样修复的是输出协议，不会改变任务语义。

## 必须重新冻结

由于 Prompt 字节和 Prompt identity 会变化，以下对象必须使用新身份：

```text
Prompt Schema / renderer version
Prompt hash
request-body hash
generation profile binding
Runner input package
Job ID
Raw / Result namespace
Development Manifest
```

旧 v26.188 的 192 个 Job、Outcome 和 \(0/192\) 结果继续原样冻结，不能改名为修复后结果。

## Credential-free preflight 应检查

1. 全部 192 个首 Prompt 均包含明确 JSON 指令；
2. 所有可到达的后续 Action、Correction 和 Final Prompt 同样满足该条件；
3. `response_format=json_object` 与 JSON-visible instruction 始终成对出现；
4. State、Candidate 顺序、Component Schedule、任务、答案、证据和 Validity 语义不变；
5. scripted reference Runner 能走完整 Action→Observation→Final 链；
6. Provider 调用为零；
7. 独立物化 `prompt_json_contract_census.json`，进入正式 Artifact Manifest。

这里不能只修第一个 Prompt。否则第一轮 Action 成功后，后续 Action 或 Final Prompt 仍可能因同一 JSON-output 合同再次被拒绝。
