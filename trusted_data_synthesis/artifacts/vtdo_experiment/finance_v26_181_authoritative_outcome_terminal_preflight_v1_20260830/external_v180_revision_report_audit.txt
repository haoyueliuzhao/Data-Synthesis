# 三、v26.180 已经真实证明了什么

## 3.1 v26.179 的窄成果可以保留

v26.180 独立重建了 v26.179 的 18 个正式文件，并保留：

```text
32 authoritative Runner Packages
6 Replicas per Package
192 prospective Job identities
192 unique Job / Raw namespace / Result namespace
772 source Choice combinations
4,632 local Replica runs
14,388 reached accepted-prefix States
41,124 Candidate acceptance evaluations
11 scripted branch controls
```

但最强 estimator 解释被正确收窄为：

```text
exact_job_key_set_and_wrapper_parent_estimator_gate
```

这只能说明 Job wrapper 和 Manifest key set 得到了约束，不能说明每个 Outcome 真正来自对应 Job 的 Raw、Result 和 AttemptTrace。

## 3.2 六类 parent-authenticity attack 确实被实际送入旧 estimator

源码不是只写入六个 aggregate 常量。它实际：

1. 从 192 条 scripted rows 构造六组变异行；
2. 对 Outcome、Raw ID、Result ID 和 AttemptTrace 做交叉、复用或旋转；
3. 为每条变异行重新计算 `row_id`；
4. 将每一组传入未修改的
   `evaluate_empirical_capability_estimands()`。

旧 estimator 只检查：

* 192 条 row；
* row ID 和 Job ID 唯一；
* Job ID exact-set；
* Manifest、Package、Replica 和 namespace wrapper 字段；

它不读取或验证任何真实 `RawExecutionDescriptor`、`JobResultDescriptor`，也不验证 Result、Trace 和 Outcome 的内容父关系。

因此以下结果是可信的：

| 攻击                            | 旧 estimator |
| ----------------------------- | ----------- |
| Outcome 跨 Job 旋转              | 接受          |
| 192 个 Job 共用一个 Raw ID         | 接受          |
| 192 个 Job 共用一个 Result ID      | 接受          |
| Raw 和 Result parents 跨 Job 旋转 | 接受          |
| Result 与 Outcome/Final 无关     | 接受          |
| 192 个 Job 共用一条 attempt trace  | 接受          |

每组仍可返回：

$$
q_{\mathrm{first}}=192/192,\qquad
q_{\mathrm{bounded}}=192/192
$$

这些数值只是攻击控制输出，绝不是 Capability estimate。

## 3.3 Final 和 first Action 的异常逃逸是真实 Runtime 控制

Final 控制实际将一个完成态 Qualified payload 改成：

```text
final_response_abi_valid = false
```

重哈希后仍然得到：

```text
endpoint_kind = completed_qualified
final_qualified_valid = true
bounded_policy_qualified_valid = true
```

另一个控制通过 v26.179 的本地 Runner 执行完整 Component 路径，再向 Final parser 提交 `{}`。当前工件记录的实际异常是 Pydantic `ValidationError`，且没有返回 typed Outcome。

unknown first Action 控制也真实生成了一个当前 Candidate 集与历史 Action 集都不存在的 24 位 Action ID。它通过 ABI 和 State token 后，在 Runner 中以：

```text
ValueError:
ABI-valid first response references an absent current Action
```

逃逸，没有产生 `ComponentAttemptOutcome` 或 exact Outcome row。

## 3.4 报告正确保持了 fail-closed 边界

v26.180 没有 Provider 调用、Development outcome、经验 Outcome row、经验估计、Mapper、State、frequency、Contribution、VTDO 或训练操作。静态审计通过没有被用来补偿 online Gate 失败。 

这一点完全符合当前 theory-first 审计要求。

# 四、新发现的关键问题

## P0：Final-parser 控制的“parser 正确拒绝”没有被形式化保证

这是本轮最重要的新发现。

v26.180 的控制函数大致是：

```python
def parse_malformed_final(...):
    invocation_count += 1
    parse_qualified_final_response({})
    raise ValueError(
        "malformed Final unexpectedly crossed the exact Final Grammar"
    )
```

外围随后：

```python
try:
    execute_trace(...)
except Exception as exc:
    error = exc
```

最终只检查：

```text
returned_trace == false
error is not None
invocation_count == 1
```

随后无条件写入：

```text
invalid_final_parser_rejected = true
```

问题在于，它没有要求：

```text
type(error) == ValidationError
```

也没有区分：

```text
A. parser 正确拒绝 {}，抛出 ValidationError
B. parser 错误接受 {}，随后 sentinel ValueError 被触发
```

A 和 B 都会满足当前控制的后置条件，并使 static Gate 通过。源码中的 `FinalAbiTotalityAudit` model 也只要求异常 type/message 非空，测试没有断言异常类型必须为 `ValidationError`。

### 科学解释

当前正式工件记录的是 `ValidationError`，所以：

```text
本次实际 parser 确实拒绝了 malformed Final。
```

这一历史观察可以保留。

但不能进一步声称：

```text
v26.180 的 Final-parser audit contract
能够 fail-closed 地证明 parser rejection。
```

这与此前 repeatedly encountered 的 evidence-generation identity 问题同构：**当前事实恰好为真，不等于测量合同已经保证该事实必须由其命名机制产生。**

### 必须修复为

```python
parser_rejected = False
try:
    parse_qualified_final_response(...)
except ValidationError as exc:
    parser_rejected = True
    parser_error = exc
else:
    raise AssertionError("malformed Final was accepted")

assert parser_rejected
assert runner_returned_typed_outcome is False
assert escaped_exception_phase == "final_parser"
```

并增加完整重哈希攻击：

```text
ValidationError -> sentinel ValueError substitution
parser_rejected=true but exception phase != final_parser
parser accepted but later Runtime branch failed
exception type/message changed while audit ID chain is recomputed
```

因此，“25 个 static audit Gates 全部通过”目前只能理解为**当前 audit builder 按其现有条件完成**，不能理解为每个命名 estimand 都已形成不可伪造的形式化证明。

也就是说，“pass”表示：

源码确实把“旧 estimator 接受攻击”“异常未形成 typed row”“online Gate 正确失败”作为 static pass 条件。

| 层级                               | 判定       |

## P1：后继的 authoritative parent binding 规范仍然过于抽象

报告仅规定后继新增：

```text
RawExecutionDescriptor
JobResultDescriptor
Job-bound AttemptTrace parent
constructor-only empirical Outcome row
exact evidence-set estimator
```

方向正确，但不足以保证权威父绑定。

尤其是“constructor-only”本身不能成为 Python 中的可信边界：即使不公开正式 constructor，Pydantic model 仍可能被直接构造；真正的安全条件必须在 estimator 入口重新验证。

后继至少必须冻结以下一一对应关系：

$$
\begin{aligned}
\text{Manifest Job}
&\leftrightarrow \text{RawExecutionDescriptor}\\
&\leftrightarrow \text{JobResultDescriptor}\\
&\leftrightarrow \text{JobBoundAttemptTrace}\\
&\leftrightarrow \text{EmpiricalOutcomeRow}.
\end{aligned}
$$

每一层都应满足：

```text
exact Job set equality
exactly one object per Job
missing / duplicate / extra = 0
ID = hash(canonical bytes)
parent ID = independently recomputed child parent
namespace/path belongs to exact Job
no cross-Job aliases
no arbitrary caller-supplied authoritative IDs
```

estimator 不应只接收 Outcome rows，而应接收完整 descriptor catalogs，或从这些 catalogs 独立重建 Outcome row。当前旧 estimator 只比较 wrapper 字段，正是六类攻击能够通过的根本原因。

当前六类攻击足以否定旧 estimator，但不能反过来定义“新 estimator 已完全安全”。

后继还应加入：

```text
相同 Raw 内容、不同伪造 Raw IDs
相同 Result 内容、不同伪造 Result IDs
唯一 Trace IDs，但 Trace canonical bytes 完全重复
ComponentAttemptOutcome 的截断、拼接和重新排序

final_result_id 与 JobResultDescriptor 不一致

outer terminal row 缺失、重复或与 Raw terminal 不一致
Result 和 Final 正确，但 Provider/Transport artifact parent 被替换
```

这里必须区分：

```text

```

与：

```text
unique、内容寻址且具有权威父链的对象
```

前者不能代替后者。

# 七、唯一合理的下一实验

下一 stage 名称仍可保持：

```text
capability_observation_empirical_outcome_authoritative_parent_binding_
and_terminal_totality_preflight_only
```

没有必要再拆出多个微小 stage；但**当前 transition 不能原样消费**。新的外部授权必须把以下对象同时设为非补偿条件。

## 7.1 权威终止注册表

从冻结 Runner、Provider、Transport、Measurement Support、Policy、Resource、Privacy、Instrument、model identity、Thinking、Usage 和 Grammar 合同中自动派生 exact terminal registry，而不是手写六类列表。

每类必须是：

```text
reachable
registered_but_unreachable_under_frozen_runner
not_applicable_with_independent_exclusion_witness
```

三者之一，不允许静默遗漏。

## 7.2 权威证据 DAG

```text
Manifest Job
→ RawExecutionDescriptor
→ JobResultDescriptor
→ JobBoundAttemptTrace
→ EmpiricalCapabilityOutcomeRow
→ ExactEvidenceSetEvaluation
```

要求每个父关系都由 canonical bytes 独立重建，不能只比较字符串 ID。

## 7.3 Exactly-one terminal projection

对 192 个 Job 中的每一个，都必须产生：

```text
exactly one JobResultDescriptor
exactly one terminal AttemptTrace
exactly one EmpiricalOutcomeRow
```

包括：

```text
Provider 无 payload
Transport failure
Privacy rejection
Resource or policy terminal
Instrument failure
model identity / Thinking / Usage failure
Action ABI invalid
Action reference invalid
typed State-precondition rejection
Final ABI invalid
completed invalid
completed Qualified
```

任何 Python/Pydantic/ValueError 异常逃逸都使 Gate 失败。

## 7.4 Final parser 的语义控制

明确要求：

```text
malformed Final
→ exact Final parser invocation
→ ValidationError caught at parser boundary
→ typed final_response_abi_invalid JobResult
→ task Verifier not invoked
→ Base / Mechanism / Qualified follow frozen null/false policy
→ exactly one empirical Outcome row
```

不能以“Runner 最终抛了某种异常”替代“Final parser 正确拒绝”。

## 7.5 Unknown first Action policy

在 Provider 执行前冻结：

```text
first_action_reference_invalid
→ immediate typed terminal
```

或：

```text
first_action_reference_invalid
→ exactly one public correction
→ then typed commit/terminal
```

二者必须明确选一，并绑定进 Runner、Outcome Contract、Manifest 和 estimator identity，不能继续处于 `correction_policy_frozen=false`。

## 7.6 独立 destructive audit

新 estimator 必须拒绝本报告第四部分列出的扩展攻击；所有攻击都要：

```text
重构对象
重算对象 ID
重算所有下游 parent identities
重算 Transition 和 Report
```

不能只做 stale-hash mutation。

## 7.7 授权边界

本阶段仍然必须保持：

```text
Provider calls                    0
Development model outcomes        0
formal empirical rows             0
formal empirical estimates        0
Confirmation access               0
Mapper / State / frequency        0
Contribution / VTDO               0
Student / training                0
```

source、Task、Component、Candidate、Schedule、presentation、model、Thinking、Grammar、Policy、resource、correction bound、threshold、validity 和 192-Job Manifest set 均不得改变。原报告对此边界的规定是正确的。

# 八、最终审计决定
