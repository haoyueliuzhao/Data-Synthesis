# 四、P0：D0–D3 当前没有改变可执行任务结构

这是本轮最重要的代码发现。

## 1. Overlay 实际做了什么

在：

```text
phase1_v26_capability_breadth_depth_task_synthesis.py
_compile_role_signature()
```

中，D0–D3 Overlay 主要被用于：

1. 追加到任务 Instruction；
2. 写入 `mechanism_public_state`；
3. 写入 `mechanism_private_state`；
4. 参与 TaskPackage 与深度签名的内容哈希；
5. 形成不同的 Role TaskPackage ID。

它没有实际改变：

* `task_program`；
* Program 节点或依赖边；
* Runtime 状态转移；
* Candidate Builder；
* Candidate 数量和合法动作集合；
* Tool 行为；
* typed failure 触发逻辑；
* normalization operation；
* terminal readiness；
* Mechanism Verifier 的事件数量要求；
* Public Witness 的操作序列。

也就是说：

```text
D0 TaskPackage ID != D3 TaskPackage ID
```

是成立的，但主要因为 Instruction 和元数据不同，而不是因为可执行任务机制不同。

---

## 2. 对 16 个 group 的实际差分结果

我重建了全部 16 个 group 的 D0–D3 Role 记录。每个 group 内四个深度都只有：

```text
1 个唯一 Program hash
1 个唯一 Tool set
1 个唯一 expected answer
1 个唯一 generic mechanism-event set
1 个唯一 Public Witness 操作序列
```

差异主要是：

```text
overlay_id
primary_load
depth label
instruction text
task-package identity
```

例如：

### Context group

D0–D3 均保留相同五节点 Program、相同 Tool 序列、相同最终答案和相同：

```text
context_action_selected
```

事件要求；Overlay 虽然声称激活 1／1／2／3 个上下文槽，但 Runtime 中并没有出现对应数量的模型拥有决策点。

### Failure Recovery group

D0–D3 均运行同一条：

```text
一次 typed failure
→ 一次 revision
→ success
```

Witness。D2／D3 元数据声称有两次或三次 Recovery 负担，但 Runtime 中没有新增第二、第三个真实失败—修正槽。

### State-dependent Stopping group

D0–D3 均使用相同完成路径和相同停止事件；没有生成随深度增加的 near-terminal checkpoint 或 tempting continuation 状态。

### Semantic Reconciliation group

D0–D3 均执行相同 normalization／Operation 序列，没有按照 Overlay 增加非 identity axis、消费 fan-out 或 downstream dependency。

## 3. 为什么 64/64 Role Depth Signature 仍然能通过

当前 `RoleExecutableDepthSignature` 主要重新读取：

```text
overlay
primary_load
nuisance signature
public witness hash
```

而这些字段本来就是编译前写入 Instruction／metadata 的对象。

因此：

$$
\text{source overlay}
=
\text{role overlay readback}
$$

只能证明：

> 编译器没有丢掉深度标签。

它不能证明：

> 编译器保留了不同深度的可执行行为要求。

报告对外声称 64/64 source-to-role depth signature 一致，同时也承认 Runner 对 Overlay 的消费尚未预检、模型行为尚未测量。

源码审计表明，问题比“尚未在线测量”更前置：

$$
\boxed{
\text{当前连静态可执行状态图都没有随深度改变。}
}
$$

所以现阶段不能把四个 Variant 称为四个 executable capability depths。

建议新增：

```text
ExecutableCapabilityDepthOverlay

ExecutableDepthSignature
```

Overlay 必须实际改变：

```text
Public Action states
```

## 3. 四项能力的实际深度实现

### Context-conditioned Action

D0–D3 必须分别产生实际的：

```text
1 / 1 / 2 / 3 个模型拥有的 context-sensitive decision states
```

并冻结：

* 每个决策点的 Candidate 集；
* 合法动作数；
* 歧义类别；
* 后续依赖；
* 不活跃槽位必须只有唯一合法动作。

### Semantic Reconciliation

固定 normalization 最大骨架，但随深度改变实际：

```text
nonidentity axis count
active target-record count
normalized-ref downstream consumption
fan-out depth
raw-bypass constraints
```

所有 active normalized refs 都必须被 Runtime Operation 真正消费。

### Failure Recovery

实际生成：


# 最终判断

v26.167 **成功修复了任务观测体系的形式框架**：

$$
\boxed{
\text{旧 Tier 与新 Depth 分离}
+
\text{matched group}
+
\text{组级新鲜性}
+
\text{Development / Confirmation 分离}
}
$$

但尚未修复最关键的内容层：

$$
\boxed{
\text{不同 Depth 必须对应不同的模型可执行能力负担。}
}
$$

当前 D0–D3 更接近：

```text
同一 executable task
+ 不同 depth instruction
+ 不同 declared load
+ 不同 content identity
```

而不是：

```text
同一 Finance core
+ 固定 nuisance
+ 真实增加的目标能力决策与验证义务
```

最直接的反证是：

* 每组 D0–D3 的 Program、Tool、Witness 序列和事件合同基本相同；
* 现有 Public Witness 实际只有 48/64 完整通过；
* 16 条 Reconciliation 缺少被消费的 normalization reference；
* D0 仍可继承旧 Hard source 的高 Evidence／Program 负担。

因此本轮结论不是“修订失败”，而是：

> **修订完成了元数据、身份和实验治理层，但 executable depth construct 尚未完成。**

当前第一个根本阻塞点是：

$$
\boxed{
\text{Executable Depth Rematerialization}
}
$$

而不是模型调用、阈值、rollout 数量或能力边界统计。只有修复这一层，未来 192 个 Development Job 的结果才有资格被解释为能力广度—深度观测，而不是模型对四种深度描述文本的反应。
